# InfoData Constitution

## Core Principles

### I. Code Quality First (针对金融数据处理项目)
每个组件必须遵循Python最佳实践：清晰命名、模块化设计、完整文档字符串和PEP 8合规性。重构遗留代码优先于添加新功能。所有新代码必须包含类型提示（兼容Python 3.7+）并遵循单一职责原则。金融数据处理的代码必须包含数据验证和错误恢复机制。

### II. Test-Driven Development (NON-NEGOTIABLE) - 金融数据验证核心
所有新功能必须采用TDD：编写测试 → 用户批准 → 测试失败 → 然后实现。核心模块测试覆盖率最低80%。所有数据管道必须包含金融数据一致性测试。外部API必须被模拟以确保测试可靠性。数据库操作必须有事务回滚测试。

### III. Consistent User Experience - 配置与错误处理统一性
所有模块暴露一致的CLI接口，具有标准化参数和错误报告。配置文件必须集中管理并验证。错误消息必须可操作并适当记录。Web界面遵循RESTful原则，具有清晰的API文档。金融数据更新状态必须有明确的反馈机制。

### IV. Performance & Scalability - 批量数据处理优化
数据处理必须高效处理批量操作，包含内存使用监控。数据库查询必须优化并建立适当索引。并发操作必须是线程安全的。关键路径需要性能基准测试。AKShare/Tushare API调用必须有速率限制和重试机制。

### V. Data Integrity & Security - 金融数据完整性优先
金融数据完整性至关重要，每个处理阶段都必须验证。敏感配置（数据库凭据）必须加密或基于环境变量。所有外部数据源必须有输入验证和清理。历史数据必须保持不可变性和可追溯性。

## Development Standards

### Technology Stack (基于现有技术栈)
- **主要语言**: Python 3.7+ (兼容AKShare/Tushare)
- **数据库**: MySQL 5.7+，使用utf8mb4编码
- **Web框架**: Flask用于内部应用（现有finance_calendar_app）
- **数据源**: AKShare/Tushare API，包含错误处理和重试机制
- **测试**: pytest + coverage报告 + 金融数据验证测试
- **文档**: Sphinx或MkDocs用于API文档 + 数据字典

### Code Organization (针对当前项目结构)
- **数据采集层**: 统一AKShare/Tushare接口，统一错误处理
- **数据存储层**: 标准化MySQL操作，连接池管理
- **数据分析层**: 模块化分析函数，参数化配置
- **可视化层**: 统一图表生成接口，支持多种输出格式
- **Web应用层**: Flask应用标准化，模板统一管理
- **配置管理**: 统一的.ini配置文件架构，环境敏感配置分离

### Quality Gates (金融数据特殊要求)
1. **预提交检查**: 代码风格检查、类型检查、SQL语法验证
2. **CI管道**: 单元测试、集成测试、金融数据验证测试
3. **预部署**: 性能测试、安全扫描、数据一致性检查
4. **部署后**: 监控、错误跟踪、数据完整性验证

## Governance
本宪法优先于所有其他开发实践。修订需要记录理由、项目维护者批准以及现有代码的迁移计划。所有拉取请求必须验证是否符合这些原则。复杂性必须通过性能或可维护性收益来证明。
