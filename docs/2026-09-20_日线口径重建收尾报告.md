## 2. 口径改造的验收判据

新体系下三条等式构成闭环，任一处写错都会显形：

```
实际价      = close                       （源原始价，不再加工）
后复权价    = close × adj_factor
前复权价    = close × adj_factor / latest(adj_factor)
收益率      = (c2·f2)/(c1·f1) − 1
VWAP 自洽   = amount / volume ∈ [low, high]（±25% 容差）
因子自洽    = pre_close(t) ≈ close(t−1) × f(t−1) / f(t)
```

## 3. 本轮发现并修复的缺陷（7 项）

### 3.1 🔴 单行越界连坐整批 300 只（严重）

- **现象**：批次 13（600600~600899，300 只）整批丢失，主重建完成标记只有 94.8%。
- **根因**：`executemany` 遇一行 `turnover_ratio` 越界（MySQL 1264）使**整批 30 万行回滚**；
  执行器对该批 `continue` 且**故意不落完成标记**，于是一次坏行扩大成 300 只票的永久缺口。
- **修法**：`_flush` 改**逐行降级**——坏行记入 `_bad_rows` 并跳过，其余行照常写入；
  关键点是 **MySQL 的 DataError 是语句级错误，事务仍可用，绝不能 `rollback()`**
  （初版误加 rollback，又一次杀掉了同事务已执行的 334 行好数据）。
- **验收**：残留重建的 `errors` 里只留下那一行
  `600654@1992-05-08 DataError(1264, turnover_ratio)`，其余行全部落库 ✅

### 3.2 🔴 退市股被误判「失败」并白跑重试

- **根因**：akshare 自带 `akshare.utils.demjson.JSONDecodeError` **不是 stdlib 的子类**，
  `except json.JSONDecodeError` 永不命中 → 退市股整只无返回被当成网络失败，白跑一整轮重试。
- **修法**：新增 `is_source_missing(e)`，按**类名 + 消息**判定「源确无此票」；`call_with_retry`
  增加 `no_retry_exc`。
- **验收**：残留重建「源无数据」正确计数，「失败」为 0 ✅

### 3.3 🟠 编排器闸门把合法状态判成「中途中断」

- **现象**：首版编排器因「完成标记 94.8% < 99%」判定主重建疑似中断，**直接退出**，
  白白错过后续全部步骤。
- **根因**：拿 done 标记数当硬闸门 —— 但执行器对失败批次**故意不落标记**是设计行为。
- **修法**：闸门只认日志结束标记 `REBUILD_RUNNER_DONE`；标记缺口只**告警**，
  并把缺口清单当作「本次未覆盖的票」交给残留重建。

### 3.4 🟠 复核判据把「已修复的票」重复计入（307 ≠ 真实）

- **现象**：编排器复核输出「仍未能重建 **307 只 / 1,442,014 行**」。
- **根因**：`inventory()` 的判据 `if code in miss or with_fac/total < 0.10`——
  把「主重建标记缺口」无条件当作整只未重建，而残留重建补完后又**没有更新 `miss` 集合**。
- **实测推翻**：按数据层事实重算（因子空 >90% 才算未重建）：

  | 判定 | 只数 | 行数 |
  |---|---|---|
  | ✅ 因子齐备 | **5,366** | — |
  | 🔴 真·未重建 | **8** | **16,241** |
  | 🟡 零星缺失 | 413 | 64,197 |

  真·未重建的 8 只：`600565 / 600591 / 600849`（退市股）+ `832317 / 833874 / 833994 / 835305 / 839680`（北交所老码）。
  抽查印证：600600 因子空仅 **1** 行、600601 仅 29 行、600654 为 0 行 —— 它们其实都已重建成功。

### 3.5 🟠 689009（CDR）腾讯源 volume 是真实股数的 100 倍

- **现象**：DQ 规则 `daily_price_vwap` 报最新日 1 行越界。
- **根因**：`689009` 该日 `volume=726,059,900`、`amount=272,668,500` → `vwap=0.376 元`，
  而 `close=38.00` 元，VWAP 落在 `[low, high]` 之外**差 100 倍**。
- **交叉印证**：同源 `turnover=1.29%`；若真实成交 726 万股，隐含流通股本 ≈ 5.63 亿股，
  与九号公司流通盘吻合；若按库内 7.26 亿股则隐含流通盘 563 亿股，量级荒谬。
- **影响面实测**（决定性证据）：

  | code | 行数 | vwap≈close | vwap≈close/100 |
  |---|---|---|---|
  | 000003 | 2,465 | 2,465 ✅ | 0 |
  | 000005 | 7,222 | 7,222 ✅ | 0 |
  | 000013 | 2,908 | 2,908 ✅ | 0 |
  | 600565 | 5,044 | 5,044 ✅ | 0 |
  | 600899 | 2,096 | 2,096 ✅ | 0 |
  | **689009** | **1,432** | **0** | **1,432** |

  → 单位偏差是**按票**而非按源的，故 `canon()` 改为三假设多数决（新增 `÷100` 分支）。
- **修法**：① 落库修正 1,432 行（`volume ÷100`）；② `canon()` 增第三单位假设防复发。
- **验收**：修正后 **1,432/1,432** 行 `vwap≈close`；黄金样本 23,469 行逐值比对仍 0 差异 ✅

### 3.6 🔴 `ytd_change_pct` 漏掉分红 —— 排行榜被系统性带偏（**回归，最严重**）

- **现象**：`stock_market_current.ytd_change_pct`（「年初至今涨幅」）的算法是
  `close(最新) / close(年初) − 1`，改造后两端都成了**不复权实际价** → 年内除权的票
  **漏掉整段分红**，系统性低估收益。
- **为什么改造前是对的**：改造前两端都是**同一基准的前复权价**，比值本身就等于
  「含分红再投的真实收益」；改成实际价后这个隐含前提消失，
  **代码没动，语义却变了** —— 这是最典型的口径改造副作用。
- **实测（10/10 只全部低估，1.95~5.54pp，方向一致为少算）**：

  | code | 名称 | 现算法 | 正确（×因子） | 偏差 |
  |---|---|---|---|---|
  | 600036 | 招商银行 | **−4.16%** | **+1.03%** | 5.18pp ← **符号反了** |
  | 601857 | 中国石油 | 4.87% | 10.41% | 5.54pp |
  | 600900 | 长江电力 | 3.63% | 7.46% | 3.83pp |
  | 601318 | 中国平安 | −26.24% | −22.42% | 3.82pp |
  | 000001 | 平安银行 | 1.74% | 5.09% | 3.35pp |
  | 601088 | 中国神华 | 14.83% | 17.71% | 2.88pp |
  | 601398 | 工商银行 | 3.20% | 5.58% | 2.38pp |
  | 601988 | 中国银行 | 15.34% | 17.71% | 2.36pp |
  | 600519 | 贵州茅台 | −11.84% | −9.76% | 2.09pp |
  | 600028 | 中国石化 | −15.27% | −13.32% | 1.95pp |

- **影响面（不只是展示）**：`app/analysis/ytd.py` 的「年初至今涨幅」**排行榜**
  直接按该列排序 → 前端 `AnalysisView` 的「YTD 涨幅/跌幅 TOP」页签与柱状图；
  `/api/market/current?sort=ytd_change_pct` 也吃它。
  即**高分红股被系统性排到榜尾或错判进跌幅榜** —— 这正是本项目「年初至今涨幅」这一玩法的核心用途。
- **修法**：改 `(今收×今因子) / (年初收×年初因子) − 1`（后复权比值，除权日连续、历史永不变）；
  因子缺失则退化为 ×1（回到旧行为，不引入新错误）。已在 `market_current_sync.py` 的
  模块头与 SQL 处各写一段 🔴 回归警告。
- **验收**：重跑 `market_current_sync` 后逐票对比 —— 变动只数、方向、与独立重算的误差见 §6 证据文件。

### 3.7 🟠 K 线头部涨跌幅「现算」与十字光标「接口值」自相矛盾

- **现象**：`KLineChart.vue` 的 `toKLineData()` 用接口的 `change_pct`（正确，含除权调整）
  渲染十字光标，而 `setLatest()` 却**用相邻两根 close 现算**头部那个涨跌幅。
- **后果**：同一天在同一个组件里出现两个不同数字；除权日尤甚（现算的是跳空跌幅）。
- **修法**：`setLatest()` 优先用接口 `change_pct`，取不到才回退现算。
  **这与「K 线用不复权还是复权序列」的决策无关** —— 接口的 `change_pct` 在两种口径下都正确，
  故不等决策、直接修。

## 4. 1990~1992 段量额修正

- **问题**：新浪 1990-01-01~1992-12-31 的 `volume` 与 `amount/close` 偏差 >5 倍者占 **33%~68%**

### 5.8 🔴 `daily_change_link` 的 72,614 行是**误报**（2026-09-21 定案并修复）

前一版报告把它当成「旧口径残留的投影」接受掉了（§5.1）。**这是错的**，且是**判据本身写错**。

#### 决定性证据（四步排除法）

| # | 检验 | 结果 | 推论 |
|---|---|---|---|
| 1 | 加 / 去掉 `adj_factor IS NOT NULL` 各跑一次 72,614 的那条 where | **都是 72,614** | 违规行**本来就有因子** → 「旧口径残留」归因不成立 |
| 2 | 看代码：`derived_rows` 里 `pre = close/(1+ret)`、`pct = ret*100` | 三者**同源于 ret** | 恒等式 `(close−pre)/pre×100 ≡ pct` **构造上必然成立**，残差**只可能**来自存储舍入 |
| 3 | 违规行的价格分布 | `<1元 10.56% / 1~2元 67.07% / 2~3元 22.34%`，合计 **99.97% 在 <3 元** | 而**全表 <3 元仅占 4.13%** → 阈值与价格强相关＝量纲错的指纹 |
| 4 | 推导：pre_close 存 3 位小数（±0.0005 元），相对误差 ≈ `0.05/pre_close` pp | 价格 < 约 **3 元** 必然顶穿 **0.02pp** | 阈值 `0.02pp` 与价格量级无关 ＝ 根因 |

#### 修法（元口径 + 完整存储精度上界）

```sql
adj_factor IS NOT NULL AND pre_close>0 AND close>0 AND change_pct IS NOT NULL
AND ABS(close - pre_close*(1+change_pct/100))
    > 0.001 + 0.0005*ABS(change_pct)/100 + pre_close*0.000001
```

上界＝ `pre_close(3位小数) ±0.0005×毛收益` ＋ `close(3位小数) ±0.0005` ＋ `change_pct(4位小数) ±pre_close×5e-7`。

#### 验收

| 项 | 结果 |
|---|---|
| 直接跑 SQL | **0 行** |
| 走生产实现 `CHECKERS['where_count']` | **pass，metric=0**（54s） |
| `dq_report` 落账 | `run_at=2026-09-21 18:51:42` **>** 规则 `update_time=18:49:24` ✅ |

#### 附带更正

- **`adj_factor` 过滤的真实作用**：它确实滤掉 22 行，但**全部是 `600018` 的 AUSAHRE 段**——
  原因是**那批行的 `change_pct` 只存 2 位小数**、精度更差，**不是**「前复权老值」。
- `legacy_scale_rows` 实测值 **75,394 → 75,173**（分源明细见 §5.1 新表）。

#### 同源隐患未处置（**列为决策项**）

`daily_factor_link` 现报 **1000 行**，症状同族（阈值偏紧：违规行 `abs_dev ≤0.005 元` 占 53/1000、
`0.005~0.05 元` 591 行）。但**不能照搬本修法**：该规则里因子 `f` 存 **8 位小数**，
其舍入被 `×prev_close` 放大，粗略绝对上界（`0.001+prev_close×1e-8`）实测会放过 **603 万行**
⇒ 该上界**不是**有效判据，需另行推导。真实异常候选是 `600870`（2018-10-26
`pre_close=124.83` vs `prev_close=2.09`）等 TENCENT 低价段（**896/1000 来自 TENCENT**）。

### 5.7 本轮新发现（未擅自处置）

#### 🔴 K 线改存实际价 → 除权日跳空（**口径取舍，等拍板**）

- **事实**：`/api/market/kline` 直接 `SELECT ... close ...` 返回，**不含 `adj_factor`、不做复权重建**；
  前端 `KLineChart.vue` 也没有复权开关（全项目搜 `复权`/`adj_factor` 无命中）。
- **变化**：改造前库内存的是**前复权价**，K 线天然连续；现在存实际价 → **除权日在图上出现跳空**。
  而 `change_pct` 是按 hfq 派生的**真实收益**，所以在除权日会出现「图上一根大阴线、涨跌幅却显示 −0.2%」的观感冲突。
- **派生影响**：前端在该序列上算的 MA / BOLL / MACD 会在每个除权日产生**假拐点**。
- **补充证据**：`stock_market_daily_ex`（名义上是「除权」表）是**冻结快照**，
  最后数据 2025-09-19、最后更新 2025-09-20，**不承担实时除权视图**。
- **不作为缺陷直接修的理由**：改 K 线默认口径是产品语义决策（券商终端两种做法都有），
  且「实际价」本身是本次改造的**目标**而非缺陷；按约定列为决策项。
  选项：① 后端按 `close×adj_factor`（后复权，历史永不变）重建序列返回；
  ② 前端加「不复权 / 前复权 / 后复权」开关；③ 接受跳空并在图上标注口径。

#### 🟠 数据中心预览走无索引列，全表 filesort

实测观察到一个 `SELECT * FROM stock_market_daily ORDER BY update_time ASC LIMIT 51 OFFSET n` ——
`update_time` **无索引**，18.5M 行全表扫描 + filesort。它是数据中心页的表预览分页查询，
与全史 DQ 周组并发时会互相拖垮（实测把同表的 `SUM()` 从 ~40s 拖到 **390s+**）。
属独立性能议题，未擅动。
