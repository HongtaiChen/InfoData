# 可移植性开发标准 v1.0

> 生效日期：2026-10-17 · 状态：**强制标准**（与 `AGENTS.md` 互为表里：AGENTS 是提交前清单，本文是判据与设计依据）
> 适用对象：InfoData / InvestBuddy 全部后端采集、派生计算、元数据与配置文件
> 恢复操作手册：`scripts/git-only-restore.md`（本文讲「为什么这么设计」，手册讲「具体怎么跑」）

---

## 1. 为什么把它定为一等标准

这个项目的资产**不是代码**，是 `adata` 库里那 3700 万行数据。代码随时可重写，但**源站滑走的数据不可重生**：

| 已发生的损失 | 规模 | 原因 |
|---|---|---|
| `stock_capital_flow` 2025-09-19 之前的行 | 约 74.8 万行 | 东财硬限最近 120 个交易日，停跑即滑走 |
| `stock_market_daily_ex` 退市股段 | 123.3 万行 | 新浪对已退市代码任何区间都返回空 |
| `news` 存量 | 17,827 行 | 源不回溯历史，只能从当下开始积累 |

**结论**：可移植性不是「部署便利性」问题，是**资产保全**问题。因此它不是某个任务，而是所有任务的前置约束。

## 2. 判据（唯一，不接受替代解释）

> 仓库 clone 到干净机器 + 空 MySQL，只跑 `scripts/restore.py`，
> 不需要原作者在场、不需要人工传参、不需要翻聊天记录，
> 就能得到「服务可启动 + 数据接近完整 + 且能清楚说出剩下缺什么」。

由这一句拆出三条支线，**任何改动不得让其中任意一条变差**：

### 2.1 可重建
每张表都有明确重建路径。路径只有四类，且必须**实测**过：

| 路径 | 判据 | 不算数的情况 |
|---|---|---|
| 采集器 | **空库 + 默认参数**能否拿回全史 | 「有采集器」本身不算证明（水位线续跑型空库会落到短窗口） |
| 派生 | 重跑上游任务能否再生 | 依赖人工筛选/拍脑袋参数的「派生」不算 |
| 脚本 | 台账登记的迁移/回填脚本可重放 | 只在 navicat 里跑过的一次性 SQL 不算 |
| 不可重建 | 源侧已消失 → 必须显式标注 + 考虑冷备 | 不标注就等于静默缺失 |

### 2.2 可验证
恢复完成后必须有**客观**判据，不能靠人眼扫一遍说「看起来有数据」。

- 每条恢复阶段的产出行数要与基线同量级（不是相等，源侧会变）
- 每张表的日期区间要与基线一致（这是判断「有没有只补了最近一段」的唯一手段）
- 校验方式：`restore.py` 的 S4 核对 + `restore_baseline.json` 逐表比对（**待建，见 §7**）

### 2.3 可告知
不可重建的部分必须**在界面上可见**，而不是藏在文档里。

已落地：`table_meta.rebuild` 六档 + 数据中心「仅看换机会丢的表」筛选（当前 6 张）+ 详情卡悬停说明缺口规模。

## 3. `rebuild` 六档的定义与判定口径

| 档 | 定义 | 当前张数 |
|---|---|---|
| `full` | 有采集器，换机跑恢复脚本能自动补全史 | 42 |
| `partial` | 能补大部分，源侧不再提供某类标的 | 1（`stock_market_daily_ex`，92.52%） |
| `window` | 源侧只留最近 N 天，停跑超期即永久缺口 | 3 |
| `derived` | 由其它表派生，重跑任务可再生 | 8 |
| `none` | 无采集器 / 源无历史 / 纯运营态数据 | 2 |
| `archive` | 备份留档快照，本就不需要重建 | 3 |
| ~~`param`~~ | **缺陷标记，正常必须为 0** | **0** |

### 3.1 口径要点（2026-10-17 修正，教训）

**按「恢复脚本实际传入的参数」判定，不按「任务的裸默认参数」判定。**

原口径量错了对象：它看的是「空库跑默认参数能补多少」，但使用者换机跑的是 `restore.py`，
而 `restore.py` 的 `TASK_OVERRIDES` 会给特定任务传参。于是把一张在恢复路径上**本来就能全补**
的表（`ths_concept_market`）误标成 `param`，白白制造了一个「风险项」。

### 3.2 `param` 的语义是「缺陷标记」而非「使用者须知」

出现 `param` ⇒ `restore.py` 漏了 `TASK_OVERRIDES`。正确处置：

1. 实测源侧**真实起点**（不要照抄上一次的日期）
2. 把参数固化进 `TASK_OVERRIDES`
3. 标签升 `full`

> 实测教训：`ths_concept_market` 原标注写「源侧提供 2018 年以来数据」，实际
> `物联网` 传 `start_date=20050101` 返回最早 **2010-01-04**（3,591 行）。
> 「2018 那一年返回了 243 行」被误读成「从 2018 年开始才有」。

## 4. 新增或改造数据表：七步（与 AGENTS.md 第 1 条对应）

```
① 改 schema.sql ──► python scripts/dump_schema.py && python scripts/dump_schema.py --check
② 写/改采集器  ──► 必须能回答「空库默认参数能否全史」
③ 若不能        ──► 参数进 restore.py 的 TASK_OVERRIDES
④ 登记 table_meta ──► seed_table_meta.py 里加 _REBUILD 条目（rebuild + note 都必填）
⑤ 若属二次开发   ──► 见 §5（脚本化 + 幂等 + 台账）
⑥ 更新文档      ──► git-only-restore.md（阶段、耗时、缺口）
⑦ 自检          ──► restore.py --dry-run，确认计划里出现该任务
```

**为什么 ③ 不能省**：采集器普遍是「水位线续跑」型 —— 库里有历史就 `last_date+1`，
只有库里**完全没有**该标的时才用 `start_date` 兜底。空库恢复时这个兜底值决定你拿到 1 年还是 15 年。

## 5. 二次开发数据：必须可重放

### 5.1 什么算「二次开发数据」

不是采集器正常产出的，而是人为加工出来的：

- 手工 `UPDATE` / `DELETE` 修数（口径订正、剔除脏数据）
- 批量回填（`backfill_*.py`、缺口定向补历史）
- 派生列 / 物化表的口径变更（如 `market_style_daily` 新增派生列）
- 索引、DQ 规则、元数据、排期配置的改动
- **任何「我在数据库里跑了一段 SQL」的行为**（这一条最容易被忽略）

### 5.2 四条硬要求

| 要求 | 判据 | 反例（本项目真实踩过） |
|---|---|---|
| 脚本化 | 有 `backend/scripts/*.py`，可重复执行 | 只在客户端跑过一次的 SQL |
| 幂等 | 跑两遍结果相同 | 无 `WHERE` 限定的 `INSERT`、无唯一键的 `REPLACE` |
| 可追溯 | 头部注释写清为什么、影响行数实测值、口径来源、回滚办法 | 「修了一下数据」 |
| 可逆 | 改存量前先 `_bak_YYYYMMDD` 或导出 CSV | `conn.autocommit=True` 就以为事务安全 |

> **最贵的教训**：`pymysql` 下 `autocommit=True` 实测不生效 —— `UPDATE` 返回 `rowcount=1`、
> **同连接内**读得到新值，换新连接却是旧值，`close()` 时静默回滚。
> 一次丢掉 4 条规则参数 + 11 处元数据订正 + 344 行状态回填，而同连接自检「全部通过」。
> ⇒ 任何 DML 后**显式 `commit()`**，复核**必须另起进程/新连接**。

### 5.3 台账

新增脚本登记到 `scripts/MIGRATIONS.md`（**待建，见 §7**）：

| 字段 | 为什么需要 |
|---|---|
| 编号 | 保证执行顺序可复现 |
| 目的 | 换机的人要知道「跑它是为了什么」 |
| 幂等性 | 决定「重跑是否安全」 |
| 是否必须重跑 | 区分「一次性历史修复」与「每次换机都要跑」 |
| 依赖顺序 | 有些回填依赖采集器已跑完 |

## 6. 配置的唯一事实来源

`task_config` / `dq_rules` / `table_meta` / 索引的**权威定义在 seed 脚本**。
前端热改、命令行直改 DB 一律只算应急，**必须回写脚本**，否则换机时被 seed 静默覆盖。

**现状取证（2026-10-17 实测）**：库内 `capital_flow_sync.cron = '15 22 * * *'`，
而 `seed_task_config.py` 写的是 `手动` —— **已经漂移 1 处**。方向无害（该任务 `enabled=0`），
但它证明了「没有机制时，漂移会长期存在且无人发现」。

**已建立检测**：`python backend/scripts/config_drift.py`（只读，有漂移退出码 1，支持 `--json`）。
正负对照实测：原始 1 处 → 对齐后 0 处 → 故意改错 1 处。
**尚未建立**：`--export`（把库内值回写到 seed 脚本），目前仍需手工改脚本。
⇒ 每次改完配置，**跑一次 `config_drift.py` 确认零漂移再提交**。

## 9. 附：本文数字的取数方式（可复核）

| 结论 | 取数方式 |
|---|---|
| 六档分布 42/1/3/8/2/3、`param`=0 | `SELECT rebuild, COUNT(*) FROM table_meta GROUP BY rebuild`（59 张全覆盖） |
| 筛选命中 6 张 | 前端 DOM 量测：标签数 6、徽标「6 张」、备份表不出现、0 pageerror |
| 退市股 1,233,599 行 | `SELECT COUNT(*) FROM stock_market_daily_ex WHERE stock_code IN (SELECT stock_code FROM stock_info WHERE list_status='退市')` |
| 表体量 MB | `information_schema.tables` 的 `data_length + index_length`（**含索引**，口径已注明） |
| 配置漂移 1 处 | `importlib` 载入 `seed_task_config.TASKS` 与库内 `task_config` 逐字段比对 |
| 源侧真起点 2010-01-04 | `akshare.stock_board_concept_index_ths("物联网", start_date="20050101")` + 负对照 `20260101` |

> 纪律：本文所有数字都必须能由上面任一方式复现。**写不出取数方式的数字，不许写进文档。**
