### 0.2 为什么不能加在 `dc_index_market`

你要的"行情表"是 `dc_index_market`，它**不是一只指数一行，是日频 K 线表**：

| 事实 | 实测值 |
|---|---|
| 行数 / 指数数 | **100,078 行 / 21 只**（每只 1,084 ~ 8,746 行） |
| 你点名的 14 只占 | **64,622 行**，平均每只 **4,616 行** |
| 表体积 | 数据 21.5 MB + 索引 12.4 MB |
| 两列的字符串载荷（若加进本表） | **14.9 MB**（每行一份副本） |
| 同样两列的载荷（加进 `index_profile`） | **3.3 KB** |

**证据 1：同一段话要在库里存几千份。**
上证 8,746 行，「最早最权威的指数、最深入人心的指数……」就会存 8,746 次；14 只平均 4,616 份副本。改一个错字要 `UPDATE` 8,746 行，而这 8,746 份之间没有任何约束保证一致。

**证据 2：采集器每轮把这些行 DELETE 掉再重建。**
`backend/app/collectors/index_market_sync.py:534`：

```python
"DELETE FROM dc_index_market WHERE index_code=%s AND trade_date>=%s "
"AND data_source IN ('AKSHARE','TENCENT','CSINDEX','CNINDEX+TENCENT','EM','SINA')"
```

窗口起点是 `max_d - overlap_days`（第 165 行，`overlap_days=7`）。紧接着第 547 行 `INSERT INTO dc_index_market (index_code, index_name, trade_date, open, high, low, close, volume, amount, change_amount, change_pct, turnover_ratio, index_group, group_desc, update_time, data_source)` —— **列清单写死 15 列**。新加的两列不在这个清单里，被 DELETE 后重建的行一律 = NULL。实测最近 10 天内，14 只共有 **98 行**会被这样的循环反复重建。

**证据 3：`index_group` / `group_desc` 能活到今天，是因为采集器专门回填它们。**
第 558 行每次运行把这三列重写一遍**全历史**。想让字段在日频表上活下来，唯一办法就是让采集器每轮重写 10 万行——这正是 `可移植性开发标准` 最反对的做法：把人工判断的存储权交给采集器。后果很具体：一次 `backfill`（全量回补，第 427 行同样的 DELETE）会把这 64,622 行删掉重写，**你的判断全部消失，且没有任何报错**。

> 字段从 5 个收到 2 个，**这个问题一点没变**：它跟字段数量无关，只跟"这张表会被采集器整批重建"有关。

### 0.4 你仍然可以"从行情角度直查"

```sql
SELECT i.index_code, i.index_name, i.trade_date, i.close, i.change_pct,
       p.core_note, p.limit_note
FROM dc_index_market i
JOIN (SELECT index_code, MAX(trade_date) md FROM dc_index_market GROUP BY index_code) t
```

| 参数固化 | 21 行 × 2 列全写进脚本常量，换机不需要传任何参数 |
| 幂等 | `INSERT … ON DUPLICATE KEY UPDATE`（现有 seed 就是这个写法），连跑两遍行数不变 |
| 可追溯 | 脚本头写清：原话来源、影响行数（21）、回滚办法 |
| 可逆 | 纯 `ADD COLUMN`，回滚 2 条 `DROP COLUMN`；改前先 `CREATE TABLE index_profile_bak_20261018 AS SELECT * FROM index_profile` |

**但有一个前置缺陷必须先修**：

`index_profile` 在全仓库**只有一个写入方** —— `backend/app/setup_index_tables.py`（第 128 行）。而这个脚本：

- 不在 `backend/scripts/`（恢复脚本目录）
- 不在 `restore.py` 的 `SEEDS` 列表
- 不在 `MIGRATIONS.md`（该台账至今不存在）

后果：干净机器跑完 `restore.py`，`index_profile` 是**空表**，这两列的新判断一起消失，而 `table_meta` 里它标着 `full`（= 可重建）。这正是 `AGENTS.md` 第 5 条点名禁止的"用有采集器证明可重建"——这里连采集器都没有。

施工顺序不能颠倒：

```
P0-a  把 seed 迁成 backend/scripts/seed_index_profile.py，进 restore.py 的 SEEDS
      （脚本带 --apply 预览风格，与 seed_task_config.py 一致）
P0-b  加 2 列 + 写入 14 行
P0-c  空库单跑一次，验证不是空表
```

只做 P0-b 不做 P0-a，等于给一张"换机即失"的表加字段。

> 补充：**顺序不参与这个风险**。它在后端常量里（2.2），随 git 走，空库也照样排得对。

### 1.7 三条纪律

1. **不改 `description`**。它是一段百科释义，和你的判断是两种东西；混在一起会两头都不好用。
2. **不建字典表，也不要再往下拆字段**。这两列存的就是整段原话。以后想按"避险/亢奋"筛选，用 `LIKE` 或另立分析视图，**不要回头把这列拆成 5 类**——拆一次就要重新判一遍"这句属于哪类"，那是把成本转嫁给未来的你。
3. **空值有语义，UI 不许显示 `--`**。两列全空 = "这只指数你没给判断"，不是"数据缺失"。显示 `--` 会让人误以为没填。
