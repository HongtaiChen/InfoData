## 0. 这份文档解决什么

现在 `dc_index_market` 里躺着 21 只指数、10 万行、最长回溯到 1990 年，数据是够的。
但**「哪只指数该被怎么看」这层知识，一条都没进系统**：

- 它只存在于人的脑子里，或者最多存在 `index_profile.description` 那种 50~90 字的百科式释义里；
- 而「上证是情绪锚、红利是避险腿、券商是亢奋信号、房地产领涨反而是坏事」这类判断，恰恰是**能直接驱动界面排序、分组、告警方向**的东西。

本文要落的就是这一层：把它做成**结构化、可查询、可重建**的元数据，并规定前台怎么呈现。

三句话概括设计取向：

1. **不新增认知负担** —— 不新建页面，只重构现有行情条的组织方式。
2. **不把定性判断当文案** —— 每条判断都要么绑一个可算的代理指标，要么明确标注「只能叙述、不可计算」。
3. **不留不可重建的数据** —— 这批元数据是人工加工产物，属于二次开发数据，必须脚本化、幂等、进恢复流程（见 §8）。

## 1. 使用者视角：这 14 只指数要替我回答什么

### 1.1 使用者与时间预算

| 项 | 内容 |
|---|---|
| 使用者 | 项目拥有者本人（A 股个人投资者 + 数据系统建设者） |
| 场景 | 每个交易日收盘后（约 19:30 指数行情入库后）打开行情看板，**5 分钟内**要判断「今天这个市场是什么性质」 |
| 时间预算 | 打开页面 → 出结论 ≤5 分钟；不允许为了得出一个判断去翻 3 个页面、点 8 次下钻 |
| 现有替代方案 | 记住「上证能代表大家情绪、科创50 看风偏、红利银行看避险」这一套经验，靠脑子在 21 张卡里自己找 |

### 1.2 ⭐ 要答出的 5 个判断句（全文锚点，后续每个需求项都对应其中一句）

> **J1.** 今天整体是涨是跌，而且这个涨跌「算不算数」—— 有多少人真的在看、真的在交易？
> **J2.** 钱是在往进攻端躲（科技成长、小盘），还是往防守端躲（高股息、银行、白酒）？
> **J3.** 散户和小资金今天在不在场？
> **J4.** 是「有人在卖」，还是「根本没人买卖」？
> **J5.** 大盘股是不是在托指数（国家队/权重股动作）？

### 1.3 为什么这 5 句必须一起看

单看 J1 会误判：指数涨 0.3% 可能只是银行拉了一下，全市场 3000 家下跌。
单看 J2 会误判：进攻端跌可能是「获利了结」，也可能是「避险启动」，要靠 J4 的资金冷清度区分。
单看 J3 会误判：微盘活跃既可能是散户进场，也可能是最后的接力。
**这 5 句的相互关系，正是那 14 只指数彼此不可替代的原因** —— 它们不是 14 个可选项，是 5 个判断句的 14 条腿。

### 1.4 现状按场景化失败叙述

| 场景 | 现在会发生什么 | 代价 |
|---|---|---|
| 打开行情看板找「避险腿」 | 21 张卡平铺，按代码排序。红利/银行/白酒/券商被排到最后几格 | 要滚动 + 自己认名字，5 分钟预算被消耗在「找」而不是「判断」 |
| 想知道「今天钱往哪躲」 | 卡片只有价格和涨跌幅，没有任何「这是避险腿」的标记 | 必须切到「市场风向」页看六组，两页信息对不上 |
| 想知道「上证这个涨幅算不算数」 | 只有上证自己的涨幅，没有「相对全市场」的口径 | J1 的「算不算数」无法回答 |
| 想确认「房地产是不是在领涨（冷清信号）」 | 房地产卡片和别的卡长得一样，涨了是红色，看起来是好事 | **信号方向会被读反** |
| 换台机器重新部署后 | 这些说明还在（因为它们现在压根不存在） | 一旦开始补，就会变成「只在主库有」的欠债 |

`index_group` / `group_desc` 已经在库里躺了一个多月，但 `/market/index-list` 的 SELECT 里**没有取这两列**（`api/market.py` 第 85~99 行）。前端因此只能靠一句 description 做 ⓘ 浮窗，分组等于白做。

### 2.3 缺口二：排序与使用者的价值判断直接冲突

`api/market.py` 第 75~79 行的 `INDEX_ORDER` 是硬编码 13 个：

000698, 399330, 399673, 899050, 931775

与用户 14 只清单对比（清单本身见附录 A）：

| 关系 | 数量 | 明细 |
|---|---|---|

同时这是一份**第三处硬编码清单**（另两处：采集器 `INDEX_META`、`INDEX_ORDER`），`index_meta.py` 文件头已记录「写死的清单 vs 动态行情表已漂移两次」。本文的设计目标之一就是**彻底消灭 `INDEX_ORDER`**，改为数据驱动排序。

### 2.4 缺口三：隐喻性判断无处安放

用户写的 28 段判断里，能直接对应到现有字段的只有「沪深300 反映大票」等少数几条（可映射到周期六分类）。其余如「最能影响大众情绪」「最能反映国家队动作」「领涨反而是资金冷清」**在库里没有任何落点**，也无法参与任何计算。

### 2.5 🔴 缺口四（可移植性）：`index_profile` 的 rebuild 标注失实

这是本次调研顺带查出来的真实缺陷，必须在动这批数据之前修掉。

| 事实 | 证据 |
|---|---|
| `table_meta` 把 `index_profile` 标为 `full`，依据写「指数档案快照，一次全量」 | `seed_table_meta.py:1378` |
| `table_meta` 的 writers 声明说它由 `index_cons_sync` 写入（source=中证指数官网，13 只） | `seed_table_meta.py:787` |
| **`index_cons_sync.py` 实际只写 `index_constituents`**，对 `index_profile` 只做 `SELECT ... FROM index_profile p`（第 312 行，用于成分覆盖率巡检） | grep 实证 |

## 3. 元数据模型：三层

### 3.1 为什么分三层

| 层 | 回答的问题 | 现有的？ | 稳定性 | 谁维护 |
|---|---|---|---|---|
| L1 分类 `index_group` | 它属于哪一类（统计属性） | ✅ 已有，21/21 | 高（跟采集器走） | 采集器 `INDEX_META` |
| L2 **角色标签** | 它能替我判断什么（功能属性） | ❌ 本次新增 | 中（会随认知更新） | 人工 seed |
| L3 **口径边界** | 它不能替我判断什么（局限） | ❌ 本次新增 | 中 | 人工 seed |

分层的必要性：L1 是「客观事实」，L2/L3 是「**使用者的判断**」。混在一起会导致下次有人改分类时顺手改掉了判断，或者反过来。分开存，改分类不会动判断，改判断也不会动分类。

### 3.2 `index_profile` 扩列（标量属性，可排序可过滤）

```sql
ALTER TABLE index_profile
  ADD COLUMN mindshare_rank   TINYINT      NULL COMMENT '大众认知度名次：1=最深入人心；并列同号；NULL=不在大众情绪链上',
  ADD COLUMN display_section  VARCHAR(16)  NULL COMMENT '行情条分区：base/mindshare/risk/structure/compare/other',
  ADD COLUMN section_rank     TINYINT      NULL COMMENT '分区内排序（升序）',
  ADD COLUMN scope_key        VARCHAR(24)  NULL COMMENT '覆盖范围：all_market/cross_market/single_exchange/single_board/single_industry',
  ADD COLUMN cap_tier         TINYINT      NULL COMMENT '规模档 1=超大盘 5=微盘；行业/策略类为 NULL',
  ADD COLUMN core_note        VARCHAR(500) NULL COMMENT '核心之处（使用者原话精炼）',
  ADD COLUMN limit_note       VARCHAR(500) NULL COMMENT '不足之处（口径边界）';
```

列宽依据：`core_note` 最长一条是房地产（**实测 81 字**，`len()` 计数、含标点），次长是银行（59 字）；`limit_note` 最长是北证50（**37 字**）。取 500 留 6 倍余量，同时远离 `pymysql DataError 1406` 的历史坑（本项目曾因 `varchar(255)` 写超长描述导致整批回滚）。

**为什么 `mindshare_rank` 要独立成列，而不是塞进标签表**：它要作为排序主键直接进 `ORDER BY`，放标签表就得 JOIN + 聚合，且名次本身是唯一值（一个指数一个名次），不符合多对多语义。

**为什么 `scope_key` 独立成列**：它是**互斥枚举**，并且直接驱动一条展示规则 —— 「只有全市场指数能当超额收益的分母」（§7.5）。

### 3.3 `index_role_tag` 新表（多对多能力标签）

```sql
CREATE TABLE index_role_tag (
  id          INT AUTO_INCREMENT PRIMARY KEY,
  index_code  VARCHAR(20)  NOT NULL COMMENT '指数代码',
  role_key    VARCHAR(32)  NOT NULL COMMENT '角色词表，见 §3.4',
  strength    ENUM('strong','medium') NOT NULL DEFAULT 'strong' COMMENT '强度：最能=strong；第二能/较能=medium',
  polarity    ENUM('normal','conditional_inverse') NOT NULL DEFAULT 'normal' COMMENT 'normal=正向；conditional_inverse=仅在特定条件下反向',
  note        VARCHAR(255) NULL COMMENT '该指数在该角色上的具体说明（含强弱序，如"第二避险腿"）',
  verify_key  VARCHAR(64) NULL COMMENT '绑定的量化代理指标键，对应 §5 词表',
  source      VARCHAR(20)  NOT NULL DEFAULT 'seed',
  update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_index_role (index_code, role_key),
  KEY idx_role_key (role_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='指数角色标签（人工判断，seed 维护）';
```

`UNIQUE (index_code, role_key)` 是幂等的基础：seed 用 `ON DUPLICATE KEY UPDATE`，跑两遍结果相同。

## 5. 定性判断 → 量化代理（诚实度分级）

**核心原则：能算的必须算，不能算的必须明说不能算，不许用假指标凑。**

### 7.2 卡片与徽章

卡片在现有结构上加两处，**不加高**：

┌──────────────────────────────┐

└──────────────────────────────┘

- 徽章文字取该指数**最强的一枚**角色（`strength='strong'` 优先），最多显示 2 枚，其余进 ⓘ

- `conditional_inverse` 角色的卡片（房地产）加一枚琥珀色小点（`#B45309`），鼠标悬停显示「该指数领涨时需反读」

### 8.4 seed 脚本的三个硬要求

### 8.7 新增指数的同步义务：从 3 处变 4 处（但少了一处隐性坑）

`index_cons_sync.py` 文件头记着一条教训：**「写死的清单 vs 动态的行情表」已经漂移两次**，并因此定下「新增指数上市场页必须同步三处」。本次改造改变了这个清单，必须同步更新那段注释，否则第四次漂移从这里开始：

| | 改造前 | 改造后 |
|---|---|---|
| ① 成分来源 | `CSINDEX_CONS` / `CNINDEX_CONS` / `CNI_ONLY` | 不变 |
| ② 释义档案 | `setup_index_tables.py` 的 `SEED` | 改为 `seed_index_profile.py` 的 `SEED`，**且必须同表填写 `display_section` / `section_rank` / `scope_key` / `cap_tier`** |
| ③ 口径不适用 | `NON_EQUITY_INDEXES`（债券等） | 不变 |
| ④ **角色标签**（新增） | — | `index_role_tag` 的 seed（不填 = 卡片无徽章、ⓘ 无「能判断什么」段） |
| ~~⑤ 行情条排序~~ | `api/market.py` 的 `INDEX_ORDER`（隐性义务，已漂移两次的源头之一） | **删除**，改由 ② 的 `display_section`/`section_rank` 驱动 |

**净效果：显性义务 3 → 4，但消灭了 1 处最易漏的隐性义务。** 因为「新指数忘了加进 `INDEX_ORDER`」不会报错、只会静默排到末尾（现状正是如此：6 只被挤到末尾没人发现）；而「新指数忘了填 `display_section`」会落到 `other` 区，是个**看得见**的兜底，不是静默错误。

降级行为必须写进脚本注释：`display_section IS NULL` → 落 `other`；`role_tags` 为空 → 卡片无徽章但其余正常。**不允许因为元数据缺失而让指数从界面上消失**（§6.1 的 `COALESCE` 兜底同理）。
