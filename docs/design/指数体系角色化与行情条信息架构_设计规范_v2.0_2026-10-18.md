| v1.0 的说法 | 实测结论 | 证据 |

## 导读（不属三部分正文，5 分钟可读完）

### 0.1 这份文档解决什么

`dc_index_market` 里躺着 21 只指数、100,078 行、最长回溯到 1990 年，行情数据是够的。
但**「哪只指数该被怎么看」这层知识，一条都没进系统**：

- 它只存在于人的脑子里，或最多存在 `index_profile.description` 那种 45~96 字的百科式释义里；
- 而「上证是情绪锚、红利是避险腿、券商是亢奋旗手、房地产领涨反而是坏事」这类判断，恰恰是**能直接驱动排序、分组、告警方向**的东西。

三句话概括设计取向：

1. **不新增认知负担** —— 不新建页面，只重构现有行情条的组织方式。
2. **不把定性判断当文案** —— 每条判断要么绑一个可算的代理指标，要么明确标注「只能叙述、不可计算」。
3. **不留不可重建的数据** —— 这批元数据是人工加工产物，必须脚本化、幂等、进恢复流程。

### 0.2 ⭐ 五个判断句（全文锚点）

> **J1.** 今天整体是涨是跌，而且这个涨跌「算不算数」—— 有多少人真的在看、真的在交易？
> **J2.** 钱是在往进攻端躲（科技成长、小盘），还是往防守端躲（高股息、银行、白酒）？
> **J3.** 散户和小资金今天在不在场？
> **J4.** 是「有人在卖」，还是「根本没人买卖」？
> **J5.** 大盘股是不是在托指数（国家队/权重股动作）？

使用者：项目拥有者本人。场景：每交易日收盘后（约 19:30 指数行情入库后）打开看板，**5 分钟内**判断「今天这个市场是什么性质」。

**这 5 句必须一起看**：单看 J1 会误判（指数涨 0.3% 可能只是银行拉了一下）；单看 J2 会误判（进攻端跌可能是获利了结，也可能是避险启动，要靠 J4 区分）。这 14 只指数不是 14 个可选项，是这 5 句判断的 14 条腿。

### 0.3 三部分的分工与边界（**本文的组织原则**）

| | 第一部分 **数据落地** | 第二部分 **后端服务** | 第三部分 **前端展示** |
|---|---|---|---|
| 回答 | 存什么、存在哪、每行长什么样、换台机器能不能重建 | 怎么读出来、按什么顺序给、缺字段时怎么办 | 怎么摆在屏幕上、徽章写什么、点开看到什么 |
| 交付物 | DDL + seed 脚本 + 全量数据内容 + 恢复流程 + 台账 | 接口契约 + 排序降级逻辑 | 分区结构 + 卡片规范 + 交互 |
| 唯一真相 | **数据库** | **接口响应** | **DOM** |
| 改动落在 | `backend/scripts/seed_index_profile.py`、`schema.sql`、`seed_table_meta.py` | `backend/app/api/market.py` | `frontend/src/views/MarketView.vue`、`components/*` |
| 验收方式 | `SELECT` 结果逐行核对 + 空库重跑 | `curl` 响应的字段与顺序 | 截图 + DOM 量测 |
| 本部分**不**涉及 | 任何 HTTP、任何 CSS | 任何建表、任何像素 | 任何 SQL、任何 seed |

**为什么必须切开**：三部分的失败模式完全不同。数据落地的失败是「换机就没了，且没人知道」；后端的失败是「字段没下发，前端做了也白做」；前端的失败是「信号方向被读反」。混在一份文档里写，评审时无法定位责任层。

## 1. 本部分的边界

### 1.1 进库的（结构化，可查询）

| 内容 | 存在哪 | 性质 |
|---|---|---|
| 认知度名次、分区、规模档、覆盖范围 | `index_profile` 新增的 5 个标量列 | 枚举/整数，可排序可筛选 |
| 「核心之处」精炼文字 | `index_profile.core_note` | 人工判断 |
| 「不足之处」精炼文字 | `index_profile.limit_note` | 人工判断 |
| 能力标签（情绪锚/避险腿/人气基石…） | `index_role_tag` 新表，多对多 | 人工判断 + 强度 + 极性 |
| 标签绑定的量化代理键 | `index_role_tag.verify_key` | 字符串键，指向 §6 词表 |

### 1.2 不进库的（每次实时算，或永远不入库）

| 内容 | 为什么 |
|---|---|
| 标签的**当前读数**（如「避险腿 · 相对全指 +1.2%」） | 是行情派生值，每天变；入库存历史无意义，且会与 `market_style_daily` 重复。由后端实时算（第二部分 §13） |
| 标签订单的**展示顺序** | 由 `strength` + 词表固定顺序推导，不入库 |
| 用户原话全文 | 只入精炼后的 `core_note`/`limit_note`；原话留在本文附录 A 备查（`varchar(500)` 放得下但不该拿来当 UI 文案） |
| 「国家队真实持仓」 | 无合规公开源，永不入库，只做代理 |

### 1.3 一条硬规则

**任何一列都不允许「只有主库有、换机就丢」。** 本部分产出的全部数据必须由仓库内脚本产生（§8）。这正是本部分要优先评审的原因。

### 2.3 `index_group` 的价值与局限

`dc_index_market.index_group` / `group_desc` 两列 **21/21 已填充**，六分类由采集器 `index_market_sync.py` 的 `INDEX_META` 定义：

| 六分类 | 成员数 | 回答的问题 |
|---|---|---|
| 市场基准 | 5 | 它是不是宽基 |
| 市值风格 | 5 | 它对应哪个规模档 |
| 科技成长 | 5 | 它是不是成长赛道 |
| 情绪温度 | 1 | 它是不是情绪指标 |
| 股息防守 | 4 | 它是不是防守资产 |
| 政策周期 | 1 | 它是不是周期行业 |

**局限（本设计存在的理由）**：六分类回答「它是什么」（统计属性），不回答「它能替你判断什么」（功能属性）。同一类里可以有完全不同的用途——「股息防守」4 只里，红利是避险腿、银行同时是压舱石与国家队窗口、白酒是价值派情绪、转债根本是债券（口径不纯）。六分类无法承载这种差异。

## 3. 目标数据模型

### 3.1 三层，各管一段

| 层 | 回答 | 载体 | 稳定性 | 谁维护 |
|---|---|---|---|---|
| L1 分类 | 它**属于**哪一类（统计属性） | `dc_index_market.index_group`（**已存在，不动**） | 高 | 采集器 `INDEX_META` |
| L2 **角色** | 它能替你**判断**什么（功能属性） | `index_role_tag` 新表 + `index_profile` 几个标量列 | 中 | 人工 seed |
| L3 **边界** | 它**不能**替你判断什么（局限） | `index_profile.limit_note` | 中 | 人工 seed |

**为什么 L1 不动**：`index_group` 归采集器管，改它要动 `INDEX_META` 并影响「市场风向」页的六组计算。本次只读它、不写它。L2/L3 是纯人工判断，独立成表，改判断不会碰分类。

### 3.2 `index_profile` 扩列（7 个新列）

```sql
ALTER TABLE index_profile
  ADD COLUMN mindshare_rank   TINYINT      NULL COMMENT '大众认知度名次：1=最深入人心；并列同号；NULL=不在大众情绪链上',
  ADD COLUMN display_section  VARCHAR(16)  NULL COMMENT '行情条分区：base/mindshare/risk/structure/compare/other',
  ADD COLUMN section_rank     TINYINT      NULL COMMENT '分区内排序（升序）',
  ADD COLUMN scope_key        VARCHAR(24)  NULL COMMENT '覆盖范围：all_market/cross_market/single_exchange/single_board/single_industry/non_equity',
  ADD COLUMN cap_tier         TINYINT      NULL COMMENT '规模档 1=超大盘 2=大盘 3=中盘 4=小盘 5=微盘；不适用为 NULL',
  ADD COLUMN core_note        VARCHAR(500) NULL COMMENT '核心之处（使用者原话精炼）',
  ADD COLUMN limit_note       VARCHAR(500) NULL COMMENT '不足之处（口径边界）';
```

**列宽依据（实测，非估计）**：改造后 `core_note` 最长是房地产 **51 字**，`limit_note` 最长是中证2000 **35 字**（Python `len()` 对 §4.3 逐条计数，含标点）。取 `varchar(500)` 留 9 倍以上余量，同时远离本项目踩过的 `pymysql DataError 1406`（曾因 `varchar(255)` 写超长描述导致**整批回滚**）。

**为什么 `mindshare_rank` 独立成列而不是塞进标签表**：它要作为排序主键直接进 `ORDER BY`。放标签表就得 JOIN + 聚合，且名次本身是唯一值（一只一个名次），不符合多对多语义。

**为什么 `scope_key` 独立成列**：它是**互斥枚举**，并直接驱动一条硬规则——「只有 `all_market` 能当超额收益分母」（见第三部分 §17）。

**`scope_key` 六个值域的含义**：

### 6.1 `signal_ballast` 与 `signal_mood_anchor` 的可区分性（D1 的数据侧证明）

拆成两个词表的**前提是它们能被区分**。两列口径确实不同：

| | `beta_x_weight`（银行） | `turnover_share`（券商） |
|---|---|---|
| 输入 | 收益率序列 + 权重 | 成交额/换手率 |
| 测什么 | 对**指数点位**的边际影响 | 对**人气/参与度**的边际影响 |
| 典型形态 | 低波动、高权重 → 值稳定 | 高弹性、成交额忽大忽小 → 值跳变 |
| 会不会同向 | **不会**：银行常在人少时托指数（ballast 高、turnover 低），券商在人多时放大成交（turnover 高） |

如果二者同向变动，说明拆分没意义；实测口径上它们输入不同（价格 vs 成交），**可以分开**。

### 8.5 seed 脚本的三个硬要求

1. **参数固化**：21 条档案 + 35 条角色标签全写在脚本常量里，不接受「要传参」。换机不需要知道任何参数。
2. **`ALTER TABLE` 必须幂等**：新增列前先查 `information_schema.columns` 再决定是否 `ADD`（与 `market_style_sync._ensure_columns` 一致）。MySQL 8 没有 `ADD COLUMN IF NOT EXISTS`，硬写 `ADD` 第二次执行报 1060。
3. **DML 后显式 `commit()`，复核另起连接**：本项目付过代价（`autocommit=True` 实测无效，曾一次丢 4 条规则参数 + 11 处元数据订正 + 344 行回填）。脚本最后一步必须**新开连接**重新 `SELECT` 并打印行数，不允许同连接自检就宣布成功。

### 8.6 新增指数的同步义务：3 处 → 4 处，但少了一个隐性坑

`index_cons_sync.py` 文件头记着教训：「写死的清单 vs 动态的行情表**已漂移两次**」，并定下「新增指数上市场页必须同步三处」。本次改造改变了这个清单：

| ② 释义档案 | `setup_index_tables.py` 的 `SEED` | 改为 `seed_index_profile.py`，**须同表填 `display_section`/`section_rank`/`scope_key`/`cap_tier`/`core_note`/`limit_note`** |

## 12. 接口契约

### 12.1 `GET /api/market/index-list`（改）

**现状**：`market.py:85-99` 的 SELECT 只取 `i.*` 与 `p.description/p.base_date/p.base_point`，**没有 `index_group`**，也没有任何新列。排序在 Python 里用 `INDEX_ORDER` 硬编码（`market.py:109-110`）。

**新增下发字段**：

| 字段 | 来源 | 缺省 |
|---|---|---|
| `index_group` / `group_desc` | `dc_index_market`（已存在，**白捡**） | NULL |
| `display_section` / `section_rank` | `index_profile` | 缺省 `'other'` / 99 |

| `core_note` / `limit_note` | `index_profile` | NULL |
| `role_tags[]` | `index_role_tag` 聚合 | `[]` |

**排序改为 SQL 内完成，删除 `INDEX_ORDER` 常量**：

```sql
ORDER BY FIELD(COALESCE(p.display_section,'other'),
               'base','mindshare','risk','structure','compare','other'),

```

`COALESCE(...,'other')` 是兜底：新纳入 `dc_index_market` 但还没登记档案的指数**不会消失**，只会落到末尾。

## 13. 排序、降级与读数计算

### 13.1 降级矩阵（缺什么会怎样）

| 缺什么 | 行为 | 会不会「消失」 |
|---|---|---|
| `index_profile` 整行没有 | 落 `other`，无徽章，ⓘ 只有 description（可能也为空） | ❌ 不消失 |
| `display_section` 为 NULL | 落 `other` | ❌ 不消失 |
| `role_tags` 为空 | 卡片正常，无徽章，ⓘ 缺「能判断什么」段 | ❌ 不消失 |
| `verify_key` 为 NULL | 该角色不显示数值，只显示文字 | ✅ 正常 |
| 读数算不出来（如 `risk_appetite_20` 当天 NULL） | 显示「今日不可用」+ 灰色，**不显示 0** | ✅ 正常 |

### 13.2 读数计算（`verify_key` → 数值）

`index-list` 只需要轻量读数（能显示在卡片/浮窗里的一个数），建议：

| `verify_key` | 计算方式 | 数据来源 |
|---|---|---|
| `amount_share` | `amount / market_amount`（当日，不复权） | `dc_index_market` + `market_style_daily` |
| `excess_vs_all` | 该指数 20 日收益 − 中证全指 20 日收益 | `dc_index_market` 两段查询 |
| `sentiment_20` / `scissors_20` / `risk_appetite_20` | 直接读当日列 | `market_style_daily` |
| `turnover_share` | `amount / market_amount` 的 20 日均值分位 | 同上两表 |
| `cap_tier_num` | 直接读列 | `index_profile` |
| `corr_60` / `beta_x_weight` / `state_proxy` / `cold_trigger` | **本期不在 `index-list` 算**（重） | 留给 P2 的 signal-board |
| `dividend_yield_pct` | NULL（无数据） | — |

**性能约束**：`index-list` 现在是一次主查询 + 一次子查询，加计算后**不得**变成 21 次往返。凡是需要逐指数历史序列的（`corr_60`、`beta_x_weight`），本期一律不在列表接口算。

### 13.3 缓存

不加新缓存机制。若响应超过 500ms，先查 §13.2 有没有引入往返，而不是加缓存层。

## 16. 卡片、徽章与浮窗

### 16.1 卡片结构（在现有结构上加两处，**不加高**）

```
┌──────────────────────────────┐
│ 上证指数 ①            000001 │   ← 名称 + 认知度角标；代码右对齐
│ 3,042.18  +0.42%  +12.7       │   ← 数字区不变（红涨绿跌）
├──────────────────────────────┤
│ 额 3,842亿  年 +12.3%   成分 │
└──────────────────────────────┘
   情绪锚                        ← 徽章：1~2 枚
```

- 徽章取 `strength='strong'` 优先，最多 2 枚，其余进 ⓘ
- 徽章配色沿用现有 `.tag-idx`（底 `#E6F1FB`、字 `#185FA5`），**不引入新颜色**
- 认知度角标：`mindshare_rank` 有值显示 ①②③④；**无值什么都不显示**（不是 `--`）
- `conditional_inverse`（房地产）加一枚琥珀小点 `#B45309`，hover 提示「该指数领涨时需反读」

### 16.2 券商与银行的徽章必须不同（D1 的前端落点）

| 指数 | 徽章（取最强） | 第二枚 |
|---|---|---|

| 证券公司 | **人气基石** | 亢奋 |

### 16.3 ⓘ 浮窗：从一段话升级为三段式

| 段 | 内容 | 来源 |
|---|---|---|
| 是什么 | 现有 45~96 字释义 | `description` |
| 能替我判断什么 | 角色 + 当前读数（如「避险腿 · 相对全指 +1.2%（20 日）」） | `role_tags` + 后端读数 |
| 边界 | 不足之处一句话 | `limit_note` |
| 落款 | 基日 / 基点（现有） | 不变 |

### 16.4 房地产的特殊处理（防读反）

不做常驻数值条。仅在 `cold_trigger` 触发时（当日涨幅进全指数前 3 且成交额处 1 年 30% 分位以下）在该卡位置显示一条琥珀提示：「房地产领涨 + 全市场缩量 → 资金极度冷清」。未触发时**什么都不显示**。

### 16.5 一条必须遵守的口径规则

**只有 `scope_key='all_market'` 的指数（中证全指）才能当超额收益的分母。** 用上证当分母会混入「沪 vs 深」结构偏差；用沪深300 会把「大小盘分化」误读成「个股分化」。所有「相对超额」必须标注分母是谁。
