## 导读（不属三部分正文）

### 0.1 这份文档解决什么

`dc_index_market` 里躺着 21 只指数、100,078 行、最长回溯到 1990 年，行情数据是够的。
但**「哪只指数该被怎么看」这层知识，一条都没进系统**：

- 它只存在于人的脑子里，或最多存在 `index_profile.description` 那种 45~96 字的百科式释义里；
- 而「上证是情绪锚、红利是避险腿、券商是攒人气的、房地产领涨反而是坏事」这类判断，恰恰是**能直接驱动排序、分组、告警方向**的东西。

三句话概括设计取向：

1. **不新增认知负担** —— 不新建页面，只重构现有行情条的组织方式。
2. **不把定性判断当文案** —— 每条判断要么绑一个可算的指标，要么明确标注「只能叙述、不可计算」。
3. **不留不可重建的数据** —— 这批元数据是人工加工产物，必须脚本化、幂等、进恢复流程。

### 0.2 ⭐ 五个判断句（全文锚点）

> **J1.** 今天整体是涨是跌，而且这个涨跌「算不算数」—— 有多少人真的在看、真的在交易？
> **J2.** 钱是在往进攻端躲（科技成长、小盘），还是往防守端躲（高股息、银行、白酒）？
> **J3.** 散户和小资金今天在不在场？
> **J4.** 是「有人在卖」，还是「根本没人买卖」？
> **J5.** 大盘股是不是在托指数（国家队/权重股动作）？

使用者：项目拥有者本人。场景：每交易日收盘后（约 19:30 指数行情入库后）打开看板，**5 分钟内**判断「今天这个市场是什么性质」。

**这 5 句必须一起看**：单看 J1 会误判（指数涨 0.3% 可能只是银行拉了一下）；单看 J2 会误判（进攻端跌可能是获利了结，也可能是避险启动，要靠 J4 区分）。这 14 只指数不是 14 个可选项，是这 5 句判断的 14 条腿。

### 0.3 三部分的分工与边界

| | 第一部分 **数据落地** | 第二部分 **后端服务** | 第三部分 **前端展示** |
|---|---|---|---|
| 回答 | 存什么、存在哪、每行长什么样、换台机器能不能重建 | 怎么读出来、按什么顺序给、缺字段时怎么办 | 怎么摆在屏幕上、徽章写什么、点开看到什么 |
| 交付物 | DDL + seed 脚本 + 全量数据内容 + 恢复流程 + 台账 | 接口契约 + 排序降级逻辑 | 分区结构 + 卡片规范 + 交互 |
| 唯一真相 | **数据库** | **接口响应** | **DOM** |
| 改动落在 | `backend/scripts/seed_index_profile.py`、`schema.sql`、`seed_table_meta.py` | `backend/app/api/market.py` | `frontend/src/views/MarketView.vue`、`components/*` |
| 验收方式 | `SELECT` 结果逐行核对 + 空库重跑 | `curl` 响应的字段与顺序 | 截图 + DOM 量测 |
| 本部分**不**涉及 | 任何 HTTP、任何 CSS | 任何建表、任何 seed | 任何 SQL、任何 seed |

**为什么必须切开**：三部分的失败模式完全不同。数据落地的失败是「换机就没了，且没人知道」；后端的失败是「字段没下发，前端做了也白做」；前端的失败是「信号方向被读反」。

## 1. 本部分的边界

### 1.1 进库的（结构化，可查询）

| 内容 | 存在哪 | 性质 |
|---|---|---|
| 认知度名次、分区、规模档、覆盖范围 | `index_profile` 新增的 5 个标量列 | 数字或中文枚举，可排序可筛选 |
| 「核心之处」精炼文字 | `index_profile.core_note` | 人工判断 |
| 「不足之处」精炼文字 | `index_profile.limit_note` | 人工判断 |
| 角色名（情绪锚/避险腿/人气基石…） | `index_role_tag.role_name`，**直接存中文** | 人工判断 |
| 强度、极性 | `index_role_tag.strength` / `polarity`，**直接存中文** | 人工判断 |
| 该角色用什么指标衡量 | `index_role_tag.indicator`，**直接存中文指标名** | 人读说明，不参与程序分支 |

### 1.2 不进库的（实时算，或永远不入库）

| 内容 | 为什么 |
|---|---|
| 指标的**当前读数**（如「避险腿 · 相对全指 +1.2%」） | 是行情派生值，每天变；入库存历史无意义，且会与 `market_style_daily` 重复。由后端实时算（第二部分 §13） |
| 角色**排序** | 由 `display_order`（已在库）决定，不需要额外存 |
| 用户原话全文 | 只入精炼后的 `core_note`/`limit_note`；原话留在本文附录 A 备查 |
| 「国家队真实持仓」 | 无合规公开源，永不入库，只做代理 |

### 1.3 一条硬规则

**任何一列都不允许「只有主库有、换机就丢」。** 本部分产出的全部数据必须由仓库内脚本产生（§8）。这正是本部分要优先评审的原因。

### 2.3 `index_group` 的价值与局限

`dc_index_market.index_group` / `group_desc` **21/21 已填充，且存的都是中文**（`市场基准`/`市值风格`/`科技成长`/`情绪温度`/`股息防守`/`政策周期`），由采集器 `index_market_sync.py` 的 `INDEX_META` 定义。

**这就是本次中文化的依据**：项目里「分类信息直接存中文」已经是既有约定，不是新发明。`index_role_tag` 存中文是**继承**这个约定。

**局限（本设计存在的理由）**：六分类回答「它是什么」（统计属性），不回答「它能替你判断什么」（功能属性）。同一类里可以有完全不同的用途——「股息防守」4 只里，红利是避险腿、银行同时是压舱石与国家队窗口、白酒是价值派情绪、转债根本是债券（口径不纯）。六分类无法承载这种差异。

## 3. 目标数据模型

### 3.0 为什么中文化，以及哪两处**不**中文化

#### 3.0.1 三个理由（不是审美偏好）

| 理由 | 说明 |
|---|---|
| **① 项目既有约定就是这样** | `dc_index_market.index_group` 存的是 `市场基准`/`科技成长`；`table_meta.category` 存的是 `债券`/`宏观`/`指数`。全库 **0 个 ENUM 列、大量中文 VARCHAR 值**。用英文键反而要新造一套风格 |
| **② 消灭一处前端硬编码** | 英文键方案下，前端必须维护 `{'signal_ballast':'压舱石', ...}` 这份映射；中文直存后，徽章文本 = `role_name`，前端**零映射**。少一处映射 = 少一处漂移 |
| **③ 验收与排障不再需要对表** | 验收 SQL 输出 `人气基石 / 最能 / 价格` 一眼能判对错；输出 `signal_mood_anchor / strong` 时必须回头查文档。**中文化的最大受益者是排障，不是界面**——界面本来就要显示中文，中文化只是让中间那一层也可读 |

#### 3.0.2 代价（诚实说）

| 代价 | 严重度 | 处置 |
|---|---|---|
| 改文案 = 改数据（不是改展示层） | 中 | 这批文案（14 个角色名）几乎终身不变；真要改，`UPDATE` + 同步 seed 常量，一次即可 |
| 中文写错字不会报错（`人气基石 ` 带空格 / `人气基右`），会静默多出一个值 | **高** | 用三条防线：① seed 脚本是**唯一写入方**，且脚本内断言 `role_name` ∈ 常量集合；② 验收加「无词表外的值」检查（§9.1 第 7 条）；③ `UNIQUE (index_code, role_name)` 保证同只指数不会重复 |
| 中文无法按字母序排出有意义顺序 | 中 | 排序**不依赖字符串**：改用 `display_order` 整数（§3.2） |

#### 3.0.3 两处坚持不中文化（请确认）


**幂等的支点**：`UNIQUE (index_code, role_name)`。seed 用 `INSERT ... ON DUPLICATE KEY UPDATE`，跑两遍行数不变。

**为什么不用 `ENUM`**：全库实测 **0 个 ENUM 列**，用 ENUM 会是本项目里第一例，且加一个角色就要 `ALTER TABLE`（会锁表、要写迁移）。改用 `VARCHAR` + 三条防线（§3.0.2）——与 `index_group` 完全同构，你一眼能看出它们是同一类东西。

**为什么 `indicator` 是「人读说明」而不参与程序**：如果程序按 `indicator` 的值分支（`if indicator == '成交额占比'`），那它就成了伪装的枚举，改一个字算法就静默失效。所以约定：**程序按 `role_name` 分派算法；`indicator` 只写给人看**。这也让 `indicator` 可以自由改写措辞而不破坏计算。

**为什么 `note` 是 `varchar(255)` 而实测最长只有 16 字**：它是**徽章旁短注**（「第二避险腿」「权重稳定器」）。留 255 是宽松余量，但要守住纪律——**不许把 51 字的 `core_note` 塞进 `note`**，长文本回 `index_profile.core_note`。

#### D1 定稿说明：为什么「权重压舱石」和「人气基石」是两个角色

你的原话里，银行和券商都叫「压舱石」。但它们是两种完全不同的东西：

| | 银行 399986 → **权重压舱石** | 券商 399975 → **人气基石** |
|---|---|---|
| 稳的是什么 | **指数**（权重 × 低波动，托住点位） | **人气**（券商不动，市场就没有做多情绪） |
| 失效表现 | 银行跌 → 指数失去支撑 | 券商不动 → 成交量萎缩、无人接力 |
| 量化指标 | `Beta×权重` 对全指波动的贡献度 | 成交额占全市场比重 + 换手率的分位 |
| 类比 | 船的**压舱石**（物理配重） | 船的**发动机预热**（人气点火） |

共用「压舱石」三个字也能跑，但徽章只能显示一枚文案，「压舱石」会让读者默认理解成银行那种含义，券商的「人气」属性就丢了。拆开后徽章各写各的，代价只是多一个角色名。

### 6.1 「权重压舱石」与「人气基石」的可区分性（D1 的数据侧证明）

拆成两个角色名的**前提是它们能被区分**。两列口径确实不同：

| | Beta×权重（银行） | 成交额占比分位（券商） |
|---|---|---|
| 输入 | 收益率序列 + 权重 | 成交额 / 换手率 |
| 测什么 | 对**指数点位**的边际影响 | 对**人气/参与度**的边际影响 |
| 典型形态 | 低波动、高权重 → 值稳定 | 高弹性、成交额忽大忽小 → 值跳变 |
| 会不会同向 | **不会**：银行常在人少时托指数（压舱值高、人气值低），券商在人多时放大成交（人气值高） |

若二者同向变动，说明拆分没意义；实测口径上输入不同（价格 vs 成交），**可以分开**。

## 7. 数据侧已知缺陷与处置

### 7.1 🔴 风偏分数当天会整条断掉

`market_style_daily.risk_appetite_20 = ret_tech_20 − ret_div_20`，而 `ret_div_20` 由股息防守组 4 只**全有才算**（`market_style_sync.py:553-557`：`len(cols) != len(GROUP_MEMBERS[group])` 即整组放弃）。

- 实测 2026-10-16：`000832` 中证转债最新日期停在 **10-15**，导致 `ret_div_20` / `ret_div_60` / `risk_appetite_20` 当日全 NULL
- 历史缺失面：`ret_div_20` 空值 **973 / 5,272 ≈ 18.5%**
- 这正是 J2（钱往哪躲）的**主指标**，断了就等于这条判断句当天答不出

**处置（两步）**：

| 步 | 动作 | 理由 |
|---|---|---|
| a | 把 `000832` 中证转债从 `GROUP_MEMBERS["div"]` 剥离 | 它是**债券指数**（`scope_name=非股票`），用债券当股票避险腿，口径本身不纯。剥离后该组 = 红利/银行/白酒三腿，**正好等于你的「避险三兄弟」** |
| b | 改为「缺腿则按剩余腿等权 + 记录 `missing_leg`」 | 整组丢弃让一个数据源的延迟毁掉整条判断句，代价过大 |

> 需 **D4 决策**：是否同意剥离 `000832`。

### 7.2 🔴 估值表几乎不覆盖这批指数

见 §2.5 实测。三个具体后果：

| 缺什么 | 打掉谁 | 补源方向 |
|---|---|---|
| 中证红利无任何估值行 → 无股息率 | 「高股息」从 🟢 掉到 🔴；「避险腿」只剩「超额」半条腿 | 中证指数官网 `000922` 的股息率；或从成分股加权反算 |
| 全表无 PB 列 | 银行的估值锚完全无法做 | **先 `ALTER` 加 `pb`/`pb_pct10y` 列，再补源** |
| 白酒/全指/2000/创业板指无估值行 | 白酒 PE 分位、全指整体估值水位 | 按需补，非 P0 |

**结论：「高股息」与「避险腿」的完整量化，取决于补源，不取决于前端。** 前端做了也读不到数。

### 7.3 🟠 成分快照没有时序

`index_constituents` 26,092 行，**每指数只有 2~4 个快照日**且不连续。指数调仓、权重漂移**无法回溯**。

处置：本期**不做**成分时序分析（做出来就是假图）。前端抽屉不得声称能看到「成分变化」。若要支持，需按调仓日（6 月/12 月）留档，属独立任务。

### 7.4 🟡 房地产的极性必须单独声明

你写的是反向指标（「突然涨了很多、在涨幅榜领先 → 资金极其冷清」），而系统里 `policy_excess_20` 按**正向**解读。直接复用它会把信号读反。

处置：`polarity='条件反向'` 是唯一技术手段（§4.4 #34），且**必须**在 seed 脚本注释里写明「此值不可批量改为 正常」。前端侧不做常驻数值条（第三部分 §16.4）。

### 8.5 seed 脚本的三个硬要求

1. **参数固化**：21 条档案 + 35 条角色标签全写在脚本常量里，不接受「要传参」。换机不需要知道任何参数。
2. **`ALTER TABLE` 必须幂等**：新增列前先查 `information_schema.columns` 再决定是否 `ADD`（与 `market_style_sync._ensure_columns` 一致）。MySQL 8 没有 `ADD COLUMN IF NOT EXISTS`，硬写 `ADD` 第二次执行报 1060。
3. **DML 后显式 `commit()`，复核另起连接**：本项目付过代价（`autocommit=True` 实测无效，曾一次丢 4 条规则参数 + 11 处元数据订正 + 344 行回填）。脚本最后一步必须**新开连接**重新 `SELECT` 并打印行数，不允许同连接自检就宣布成功。

### 8.6 新增指数的同步义务：3 处 → 4 处，但少了一个隐性坑

`index_cons_sync.py` 文件头记着教训：「写死的清单 vs 动态的行情表**已漂移两次**」，并定下「新增指数上市场页必须同步三处」。本次改造改变了这个清单：

| | 改造前 | 改造后 |
|---|---|---|
| ① 成分来源 | `CSINDEX_CONS` / `CNINDEX_CONS` / `CNI_ONLY` | 不变 |
| ② 释义档案 | `setup_index_tables.py` 的 `SEED` | 改为 `seed_index_profile.py`，**须同表填 `display_section`/`display_order`/`scope_name`/`cap_tier`/`core_note`/`limit_note`** |
| ③ 口径不适用 | `NON_EQUITY_INDEXES`（债券等） | 不变 |
| ④ **角色标签**（新增） | — | `index_role_tag` 的 seed（不填 = 无徽章、文末无「能判断什么」段） |
| ~~⑤ 行情条排序~~ | `api/market.py` 的 `INDEX_ORDER`（**隐性**义务，已漂移两次的源头） | **删除**，改由 ② 的 `display_order` 驱动 |

**净效果：显性义务 3 → 4，但消灭了 1 处最易漏的隐性义务。** 因为「忘了加进 `INDEX_ORDER`」不报错、只会静默排到末尾（现状正是：6 只被挤到末尾没人发现）；而「忘了填 `display_section`」会落到 `其他` 区，是**看得见**的兜底。

### 16.4 房地产的特殊处理（防读反）

不做常驻数值条。仅在触发时（当日涨幅进全指数前 3 且成交额处 1 年 30% 分位以下）在该卡位置显示一条琥珀提示：「房地产领涨 + 全市场缩量 → 资金极度冷清」。未触发时**什么都不显示**。

判断依据是 `polarity === '条件反向'` 这个**中文字符串**——因此前端必须把这个字面量集中定义在一个常量里，**不允许散落多处比较**（中文拼写漂移会静默失效）。

### 16.5 一条必须遵守的口径规则

**只有 `scope_name='全市场'` 的指数（中证全指）才能当超额收益的分母。** 用上证当分母会混入「沪 vs 深」结构偏差；用沪深300 会把「大小盘分化」误读成「个股分化」。所有「相对超额」必须标注分母是谁。
