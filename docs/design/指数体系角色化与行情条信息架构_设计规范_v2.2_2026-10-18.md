## 导读（不属三部分正文）

### 0.1 这份文档解决什么

`dc_index_market` 里躺着 21 只指数、100,078 行、最长回溯到 1990 年，行情数据是够的。
但**「哪只指数该被怎么看」这层知识，一条都没进系统**：

- 它只存在于人的脑子里，或最多存在 `index_profile.description` 那种 45~96 字的百科式释义里；
- 而「上证是情绪锚、红利是避险腿、券商是攒人气的、房地产领涨反而是坏事」这类判断，恰恰是**能直接驱动排序、分组、告警方向**的东西。

三句话概括设计取向：

1. **不新增认知负担** —— 不新建页面，只重构现有行情条的组织方式。
2. **不把定性判断当文案** —— 每条判断要么绑一个可算的指标，要么明确标注「只能叙述、不可计算」。
3. **不留不可重建的数据** —— 这批元数据是人工加工产物，必须脚本化、幂等、进恢复流程。

### 0.2 ⭐ 五个判断句（全文锚点）

> **J1.** 今天整体是涨是跌，而且这个涨跌「算不算数」—— 有多少人真的在看、真的在交易？
> **J2.** 钱是在往进攻端躲（科技成长、小盘），还是往防守端躲（高股息、银行、白酒）？
> **J3.** 散户和小资金今天在不在场？
> **J4.** 是「有人在卖」，还是「根本没人买卖」？
> **J5.** 大盘股是不是在托指数（国家队/权重股动作）？

使用者：项目拥有者本人。场景：每交易日收盘后（约 19:30 指数行情入库后）打开看板，**5 分钟内**判断「今天这个市场是什么性质」。

**这 5 句必须一起看**：单看 J1 会误判（指数涨 0.3% 可能只是银行拉了一下）；单看 J2 会误判（进攻端跌可能是获利了结，也可能是避险启动，要靠 J4 区分）。这 14 只指数不是 14 个可选项，是这 5 句判断的 14 条腿。

### 0.3 三部分的分工与边界

| | 第一部分 **数据落地** | 第二部分 **后端服务** | 第三部分 **前端展示** |
|---|---|---|---|
| 回答 | 存什么、存在哪、每行长什么样、换台机器能不能重建 | 怎么读出来、按什么顺序给、缺字段时怎么办 | 怎么摆在屏幕上、徽章写什么、点开看到什么 |
| 交付物 | DDL + seed 脚本 + 全量数据内容 + 恢复流程 + 台账 | 接口契约 + 排序降级逻辑 | 分区结构 + 卡片规范 + 交互 |
| 唯一真相 | **数据库** | **接口响应** | **DOM** |
| 改动落在 | `backend/scripts/seed_index_profile.py`、`schema.sql`、`seed_table_meta.py` | `backend/app/api/market.py` | `frontend/src/views/MarketView.vue`、`components/*` |
| 验收方式 | `SELECT` 结果逐行核对 + 空库重跑 | `curl` 响应的字段与顺序 | 截图 + DOM 量测 |
| 本部分**不**涉及 | 任何 HTTP、任何 CSS | 任何建表、任何 seed | 任何 SQL、任何 seed |

**为什么必须切开**：三部分的失败模式完全不同。数据落地的失败是「换机就没了，且没人知道」；后端的失败是「字段没下发，前端做了也白做」；前端的失败是「信号方向被读反」。

## 1. 本部分的边界

### 1.1 进库的（结构化，可查询）

| 内容 | 存在哪 | 性质 |
|---|---|---|
| 认知度名次、分区、规模档、覆盖范围 | `index_profile` 新增的 5 个标量列 | 数字或中文枚举，可排序可筛选 |
| 「核心之处」精炼文字 | `index_profile.core_note` | 人工判断 |
| 「不足之处」精炼文字 | `index_profile.limit_note` | 人工判断 |
| 角色名（情绪锚/避险腿/人气基石…） | `index_profile.roles` **JSON 数组内 `角色` 字段**，直接存中文 | 人工判断 |
| 强度、极性 | 同一 JSON 的 `强度` / `极性` 字段，直接存中文 | 人工判断 |
| 该角色用什么指标衡量 | 同一 JSON 的 `指标` 字段，直接存中文指标名 | 人读说明，不参与程序分支 |

### 1.2 不进库的（实时算，或永远不入库）

| 内容 | 为什么 |
|---|---|
| 指标的**当前读数**（如「避险腿 · 相对全指 +1.2%」） | 是行情派生值，每天变；入库存历史无意义，且会与 `market_style_daily` 重复。由后端实时算（第二部分 §13） |
| 角色**排序** | 顺序已固定在 JSON 数组里（按展示优先级），不需要额外列；指数的排序则由 `display_order` 决定 |
| 用户原话全文 | 只入精炼后的 `core_note`/`limit_note`；原话留在本文附录 A 备查 |
| 「国家队真实持仓」 | 无合规公开源，永不入库，只做代理 |

### 1.3 一条硬规则

**任何一列都不允许「只有主库有、换机就丢」。** 本部分产出的全部数据必须由仓库内脚本产生（§8）。这正是本部分要优先评审的原因。

### 2.3 `index_group` 的价值与局限

`dc_index_market.index_group` / `group_desc` **21/21 已填充，且存的都是中文**（`市场基准`/`市值风格`/`科技成长`/`情绪温度`/`股息防守`/`政策周期`），由采集器 `index_market_sync.py` 的 `INDEX_META` 定义。

**这就是本次中文化的依据**：项目里「分类信息直接存中文」已经是既有约定，不是新发明。`index_profile.roles` 存中文是**继承**这个约定。

**局限（本设计存在的理由）**：六分类回答「它是什么」（统计属性），不回答「它能替你判断什么」（功能属性）。同一类里可以有完全不同的用途——「股息防守」4 只里，红利是避险腿、银行同时是压舱石与国家队窗口、白酒是价值派情绪、转债根本是债券（口径不纯）。六分类无法承载这种差异。

## 3. 目标数据模型

### 3.0 为什么中文化，以及哪两处**不**中文化

#### 3.0.1 三个理由（不是审美偏好）

| 理由 | 说明 |
|---|---|
| **① 项目既有约定就是这样** | `dc_index_market.index_group` 存的是 `市场基准`/`科技成长`；`table_meta.category` 存的是 `债券`/`宏观`/`指数`。全库 **0 个 ENUM 列、大量中文 VARCHAR 值**。用英文键反而要新造一套风格 |
| **② 消灭一处前端硬编码** | 英文键方案下，前端必须维护 `{'signal_ballast':'压舱石', ...}` 这份映射；中文直存后，徽章文本 = `角色` 字段，前端**零映射**。少一处映射 = 少一处漂移 |
| **③ 验收与排障不再需要对表** | 验收 SQL 输出 `人气基石 / 最能 / 价格` 一眼能判对错；输出 `signal_mood_anchor / strong` 时必须回头查文档。**中文化的最大受益者是排障，不是界面**——界面本来就要显示中文，中文化只是让中间那一层也可读 |

#### 3.0.2 代价（诚实说）

| 代价 | 严重度 | 处置 |
|---|---|---|
| 改文案 = 改数据（不是改展示层） | 中 | 这批文案（14 个角色名）几乎终身不变；真要改，`UPDATE` + 同步 seed 常量，一次即可 |
| 中文写错字不会报错（`人气基石 ` 带空格 / `人气基右`），会静默多出一个值 | **高** | 用三条防线：① seed 脚本是**唯一写入方**，写入前**逐元素**断言 `角色` ∈ 常量集合；② 验收加「无词表外的值」检查（§9.1 第 7 条，`COUNT(DISTINCT 角色)` = 14）；③ 因单表化后失去了 `UNIQUE(index_code, 角色)`，再加一道「单只条数 > 5 即报警」（§4.5 查询 6） |
| 中文无法按字母序排出有意义顺序 | 中 | 排序**不依赖字符串**：改用 `display_order` 整数（§3.2） |

#### 3.0.3 两处坚持不中文化（请确认）

| 不中文的东西 | 为什么 |
|---|---|
| **列名**（`roles`、`display_order`…） | 列名是工程标识符，所有 SQL 都引用它；且 `index_group`（中文值）配的也是英文列名。**中文化的是「值」，不是「列名」**。`roles` 内的键也按同一原则处理——它们是 JSON 里的"列名"，所以用中文（`角色`/`强度`），因为那是数据的字段名而非工程标识 |
| **`cap_tier` 的值**（1/2/3/4/5） | 它是**档位序数**，`1 < 2 < 3` 有比较语义，且要与现有 `SizeGradient.vue` 的五档口径对齐。换成 `大盘`/`小盘` 就无法比较大小、也无法做渐变映射。若要中文，只能加一列冗余的 `cap_tier_name`，收益不抵 |

> 若你希望 `cap_tier` 也存中文（`超大盘`/`大盘`/`中盘`/`小盘`/`微盘`），我改，但需要同时把 `SizeGradient` 的数值映射改成字符串匹配——**这是一个独立决策项，编号 D5**（附录 D）。

### 3.1 三层，各管一段

| 层 | 回答 | 载体 | 稳定性 | 谁维护 |
|---|---|---|---|---|
| L1 分类 | 它**属于**哪一类 | `dc_index_market.index_group`（**已存在，不动**） | 高 | 采集器 `INDEX_META` |
| L2 **角色** | 它能替你**判断**什么 | `index_profile.roles`（1 列 JSON）+ 几个标量列 | 中 | 人工 seed |
| L3 **边界** | 它**不能**替你判断什么 | `index_profile.limit_note` | 中 | 人工 seed |

**为什么 L1 不动**：`index_group` 归采集器管，改它要动 `INDEX_META` 并影响「市场风向」页的六组计算。本次只读它、不写它。

### 3.2 `index_profile` 扩列（8 个新列，**0 张新表**）

```sql
ALTER TABLE index_profile
  ADD COLUMN mindshare_rank  TINYINT      NULL COMMENT '大众认知度名次：1=最深入人心，并列同号；NULL=不在大众情绪链上',
  ADD COLUMN display_section VARCHAR(16)  NULL COMMENT '行情条分区（中文）：分母/情绪锚/风偏与散户/结构腿/对照/其他',

  ADD COLUMN cap_tier        TINYINT      NULL COMMENT '规模档 1超大盘 2大盘 3中盘 4小盘 5微盘；不适用为 NULL',
  ADD COLUMN core_note       VARCHAR(500) NULL COMMENT '核心之处（使用者原话精炼）',
  ADD COLUMN limit_note      VARCHAR(500) NULL COMMENT '不足之处（口径边界）',
  ADD COLUMN roles           JSON         NULL COMMENT '角色标签栈（中文），按展示优先级定序；元素含 角色/强度/极性/说明/指标';
```

> `roles` 是 v2.2 相对 v2.1 的**唯一结构变化**：v2.1 那张 `index_role_tag` 新表被取消，内容搬进这一列。表数：**2 → 1**。

**列宽依据（实测，非估计）**：改造后 `core_note` 最长是房地产 **51 字**，`limit_note` 最长是中证2000 **35 字**（Python `len()` 对 §4.3 逐条计数，含标点）。取 `varchar(500)` 留 9 倍以上余量，同时远离本项目踩过的 `pymysql DataError 1406`（曾因 `varchar(255)` 写超长描述导致**整批回滚**）。

**`roles` 不需要定长**：MySQL 的 `JSON` 类型上限 1 GB，实测最长一只（399986 银行，5 条）序列化后 **367 字符**（附录 B）。这也正是不能用「5 组固定列」的原因——见 §3.3.1。

**为什么 `section_rank` 改成 `display_order`（全局序）**：中文化后不能再靠字母序排，原方案要用 `ORDER BY FIELD(display_section,'分母','情绪锚',...)` —— 那是把中文硬编码进 SQL，改一个分区名就要改 SQL，等于把字典表搬到了 SQL 里。改用单个整数后，排序只依赖 `ORDER BY display_order`，**SQL 里一个中文字符都不出现**。

**`display_order` 编号规则**：十位 = 分区序（1 分母 / 2 情绪锚 / 3 风偏 / 4 结构腿 / 5 对照 / 6 其他），个位 = 分区内位置。留 9 个空位便于插入。

**`scope_name` 六个值域**：

| 值 | 含义 | 本库成员 |
|---|---|---|
| `全市场` | 覆盖全市场 | 000985 中证全指 |
| `跨市场` | 沪深跨市场 | 000300、000905、000852、932000、000922 |
| `单交易所` | 单一交易所 | 000001（沪）、899050（京）、000016（沪）、399001（深）、399330（深） |
| `单板块` | 单板块 | 399006、000688、000698、399673 |
| `单行业` | 单行业/主题 | 399986、399975、399997、931775、980017 |
| `非股票` | **非股票资产** | 000832 中证转债（债券） |

`非股票` 是特意新增的值：它让「债券指数不该混进股票避险组」这个判断**在数据层面就能被查询到**，而不是只写在文档里。

### 3.3 `roles` 这一列的形状（**取代 v2.1 的新表**）

#### 3.3.1 为什么是「一列 JSON」而不是「5 组固定列」

先把事实摆出来：**每只指数的角色条数不是常数**，实测分布如下（附录 B 有取数脚本）：

| 条数 | 只数 | 谁 |
|---|---|---|
| 1 条 | 3 | 中证全指、中证500、北证50 |
| 2 条 | 3 | 上证、红利、房地产 |
| 3 条 | 7 | 沪深300、创业板、科创50、中证1000、中证2000、券商、白酒 |
| **5 条** | 1 | **中证银行** |

最多 5 条、最少 1 条。若用固定列，`role1_name/role1_strength/role1_说明/…` 摊到 5 组就是 **25 列**，而且第 6 条角色出现时还要 `ALTER TABLE`。所以：

| 方案 | 表数 | 新增列 | 角色数上限 | 判词 |
|---|---|---|---|---|
| 新建 `index_role_tag` 表（v2.1） | 2 | — | 无限 | 结构最正统，但**多一张表**（你要避免的） |
| 5 组固定列 | 1 | 25 | 5（硬顶） | 列太脏，且扩展要改表 |
| **一列 JSON（v2.2）** | **1** | **1** | **无限** | 表不变、列不脏、内容可整体替换 |
| 一列分号字符串 | 1 | 1 | 无限 | 少一层校验：MySQL 会替我们挡非法 JSON，但不会挡 `人气基右`（见 §3.3.5） |

**选 JSON 不是赶时髦**：本库已有 **6 个 JSON 列**（`dq_rules.params`、`table_meta.writers`、`table_meta.writer_cols`、`task_config.params`、`task_runs.run_detail`、`user_prefs.payload`），且 MySQL 版本 **8.2.0**（实测）。这是项目既有手法。

#### 3.3.2 形状契约（**唯一权威定义**）

```
roles = [
  { "角色": <中文角色名，14 种之一>,
    "强度": "最能" | "较能",
    "极性": "正常" | "条件反向",
    "说明": <短注，实测最长 16 字>,
    "指标": <量化指标中文名，仅人读>
  }, ...
]
```

四条不变量（验收时逐条查，§9.1）：

| # | 不变量 | 为什么 |
|---|---|---|
| I1 | 每个元素**恰好 5 个键**，键名逐字为 `角色/强度/极性/说明/指标` | 缺键会让前端读出 `undefined`；多键说明有人手改了结构 |
| I2 | 数组**已按展示优先级定序**，前端取前 2 条即徽章 | 前端不需要比「最能 > 较能」，零逻辑 |
| I3 | `角色` ∈ 14 个词表值（§3.4） | 中文化的代价：错别字不报错，只多一个值 |
| I4 | `极性 = 条件反向` 全库**恰好 1 条**（房地产） | 防止「它涨了」被读成好事 |

#### 3.3.3 幂等与写入：`UPDATE` 整列，不做元素级增删

seed 脚本对每只指数执行：

```sql
UPDATE index_profile SET roles = CAST(%s AS JSON) WHERE index_code = %s
```

**为什么整列覆盖而不是"追加一条角色"**：因为幂等的支点从 v2.1 的 `UNIQUE (index_code, role_name)` 变成了「**每只指数的 roles 由脚本一次性定义**」。整列覆盖跑两遍结果完全相同；而"追加式"写法跑两遍会变成 10 条（银行）。这一变化必须写进脚本注释——**v2.1 的 `ON DUPLICATE KEY UPDATE` 手法在这里不适用**。

**代价（诚实说）**：v2.1 里 `UNIQUE` 能在数据库层挡住「同一只指数重复标同一角色」；现在没有了，只能靠 seed 断言 + 验收（§9.1 第 5 条用 `JSON_LENGTH` 与 `COUNT(DISTINCT)` 比对）。**这是单表化付出的唯一实质代价**，我判断可接受：写入方只有一个脚本，不是多人并发写。

#### 3.3.4 数组顺序 = 展示优先级（**这一点请重点看**）

v2.1 里数组内的顺序是"seed 书写顺序"，徽章要靠前端比 `最能 > 较能`。v2.2 改成**入库即定序**，规则是 §3.4 的「展示优先级」列（1 最先）。

**为什么不按 `强度` 排**：因为「较能」的角色常常比「最能」的泛角色更有信息量。实例——券商若按强度排，两枚徽章会是「人气基石(最能) + 市场代表性(最能)」，而「市场代表性」14 只里 10 只都有，等于没说；按展示优先级排则是「**人气基石 + 亢奋情绪**」，后者才回答"它能替你判断什么"。

**为什么「市场代表性」被压到最后一位**：14 只里 **10 只**都有它（附录 B 实算），它在卡片上几乎恒亮，且「覆盖范围」这件事已经由 `scope_name` 列单独承载。它保留在 JSON 里是为了让抽屉与浮窗能完整叙述，但不该抢徽章位。

#### 3.3.5 一个必须实测才发现的坑（🔴 施工必读）

我在本机 MySQL 8.2.0 上把验收 SQL 真跑了一遍，发现：

```sql
-- ❌ 报错 (3143, 'Invalid JSON path expression...')
JSON_TABLE(t.roles, '$[*]' COLUMNS (
   角色 VARCHAR(32) PATH '$.角色',    -- 裸中文路径，多列时失败
   强度 VARCHAR(8)  PATH '$.强度'
)) jt

-- ✅ 通过：中文键路径必须加双引号
JSON_TABLE(t.roles, '$[*]' COLUMNS (
   角色 VARCHAR(32) PATH '$."角色"',
   强度 VARCHAR(8)  PATH '$."强度"'
)) jt
```

实测矩阵（附录 B）：**单列**时裸路径能过；**≥2 列**时必报 `3143`。所以定死一条规矩：**凡在 SQL 里写 JSON 路径，中文键一律写 `$."键"`，不要依赖"单列能过"这个假象。**

> 如果嫌这个坑烦，可以改用英文键（`role/strength/...`）躲避——但那就回到了 v2.0 的"要回头查文档才知道 `polarity` 是什么"。我选择留中文键 + 加引号，因为**只有验收 SQL 需要写路径**，业务代码只做 `json.loads` 后整体透传，压根不碰路径。

#### 3.3.6 为什么 `指标` 是「人读说明」而不参与程序

若程序按 `指标` 的值分支（`if 指标 == '成交额占比'`），它就变成了伪装的枚举：改一个字算法静默失效。约定：**程序按 `角色` 分派算法；`指标` 只写给人看**。这也让 `指标` 可自由改措辞而不破坏计算。

**已知冗余（不遮掩）**：14 个角色名与 14 个指标名是 **1:1**（§3.4 表），所以同一句话在 35 条里重复了 N 次。仍然逐条存，是为了让**单独一条 JSON 脱离文档也能读懂**；如果将来指标名要统一改，seed 里有常量，改一处即可。

#### D1 定稿说明：为什么「权重压舱石」和「人气基石」是两个角色

你的原话里，银行和券商都叫「压舱石」。但它们是两种完全不同的东西：

| | 银行 399986 → **权重压舱石** | 券商 399975 → **人气基石** |
|---|---|---|
| 稳的是什么 | **指数**（权重 × 低波动，托住点位） | **人气**（券商不动，市场就没有做多情绪） |
| 失效表现 | 银行跌 → 指数失去支撑 | 券商不动 → 成交量萎缩、无人接力 |
| 量化指标 | `Beta×权重` 对全指波动的贡献度 | 成交额占全市场比重 + 换手率的分位 |
| 类比 | 船的**压舱石**（物理配重） | 船的**发动机预热**（人气点火） |

共用「压舱石」三个字也能跑，但徽章只能显示一枚文案，「压舱石」会让读者默认理解成银行那种含义，券商的「人气」属性就丢了。拆开后徽章各写各的，代价只是多一个角色名。

## 6. 定性判断 → 量化指标（诚实度分级）

**核心纪律：能算的必须算，不能算的必须明说，不许用假指标凑。**

| `角色` | `指标`（中文名） | 算式/口径 | 数据现状 | 诚实度 |
|---|---|---|---|---|
| 大众认知度 | 成交额占比 | 该指数 `amount` ÷ `market_style_daily.market_amount`，取 20 日均值与 1 年分位 | 数据齐，**未计算** | 🟢 |
| 市场代表性 | 成分股占比 | `index_constituents` 支数 ÷ 全市场 A 股数 | 齐（但仅 2~4 快照日） | 🟢 |
| 规模档身份 | 规模档 | 直接读 `index_profile.cap_tier` | 齐 | 🟢 |
| 风险偏好 | 风偏分 | 已有 `risk_appetite_20`（科技成长组 − 股息防守组 20 日收益差） | 有列，**当天可能 NULL**（§7.1） | 🟠 |
| 避险腿 | 相对全指超额 | 该指数 20 日收益 − 中证全指 20 日收益 | 可算 | 🟠（完整需股息率） |
| 亢奋情绪 | 券商超额 | 已有 `sentiment_20`（券商 − 全指 20 日超额） | 已有值 | 🟢 |
| 散户情绪 | 大小盘剪刀差 | 已有 `scissors_20` | 齐 | 🟢 |
| 资金冷清度 | 冷清触发 | 房地产当日涨幅排名进全指数前 3 **且** 涨幅 > 2%，**且** 全市场成交额处 1 年 30% 分位以下 | 需新增一次排名查询 | 🟡 阈值待定（D2） |
| 国家队动作 | 国家队代理 | 银行 + 上证50 相对全指的 20 日超额合成 | 可算 | 🟡 **只是代理，非真持仓** |
| 权重压舱石 | Beta×权重 | 银行对中证全指 60 日 Beta × 其在全指中的权重 → 对指数波动的贡献度 | 可算 | 🟡 近似 |
| **人气基石** | 成交额占比分位 | 券商 `amount` 占全市场比重 20 日均值分位 + 换手率分位 | 可算 | 🟡 近似 |
| 高股息 | 股息率分位 | 股息率及其 5 年历史分位 | 🔴 **红利无估值行** | 🔴 不可算 |
| 老派价值 | 相对全指超额 | 白酒相对全指 20 日超额（唯一可用代理） | 可算 | 🟡 **代理，非真值** |
| 定位重叠 | 相关系数 | 两指数 60 日收益相关系数 | 可算 | 🟢 |

**统计：🟢 6 / 🟠 2 / 🟡 5 / 🔴 1 = 14。**

### 6.1 「权重压舱石」与「人气基石」的可区分性（D1 的数据侧证明）

拆成两个角色名的**前提是它们能被区分**。两列口径确实不同：

| | Beta×权重（银行） | 成交额占比分位（券商） |
|---|---|---|
| 输入 | 收益率序列 + 权重 | 成交额 / 换手率 |
| 测什么 | 对**指数点位**的边际影响 | 对**人气/参与度**的边际影响 |
| 典型形态 | 低波动、高权重 → 值稳定 | 高弹性、成交额忽大忽小 → 值跳变 |
| 会不会同向 | **不会**：银行常在人少时托指数（压舱值高、人气值低），券商在人多时放大成交（人气值高） |

若二者同向变动，说明拆分没意义；实测口径上输入不同（价格 vs 成交），**可以分开**。

### 7.1 🔴 风偏分数当天会整条断掉

### 7.2 🔴 估值表几乎不覆盖这批指数

| 缺什么 | 打掉谁 | 补源方向 |

### 8.5 seed 脚本的三个硬要求

1. **参数固化**：21 条档案 + 35 条角色标签（写成 14 只各一段 JSON 常量）全写在脚本里，不接受「要传参」。换机不需要知道任何参数。
2. **`ALTER TABLE` 必须幂等**：新增列前先查 `information_schema.columns` 再决定是否 `ADD`（与 `market_style_sync._ensure_columns` 一致）。MySQL 8 没有 `ADD COLUMN IF NOT EXISTS`，硬写 `ADD` 第二次执行报 1060。
3. **DML 后显式 `commit()`，复核另起连接**：本项目付过代价（`autocommit=True` 实测无效，曾一次丢 4 条规则参数 + 11 处元数据订正 + 344 行回填）。脚本最后一步必须**新开连接**重新 `SELECT` 并打印行数，不允许同连接自检就宣布成功。

### 8.6 新增指数的同步义务：3 处 → **还是 3 处**，且少了一个隐性坑

`index_cons_sync.py` 文件头记着教训：「写死的清单 vs 动态的行情表**已漂移两次**」，并定下「新增指数上市场页必须同步三处」。本次改造改变了这个清单：

| | 改造前 | 改造后（v2.2 单表） |
|---|---|---|
| ① 成分来源 | `CSINDEX_CONS` / `CNINDEX_CONS` / `CNI_ONLY` | 不变 |
| ② 释义档案 | `setup_index_tables.py` 的 `SEED` | 改为 `seed_index_profile.py`，**同一行里同时填** `display_section`/`display_order`/`scope_name`/`cap_tier`/`core_note`/`limit_note`/`roles` |
| ③ 口径不适用 | `NON_EQUITY_INDEXES`（债券等） | 不变 |
| ~~④ 角色标签~~ | — | **不再是一条独立义务**——v2.1 需要额外去 `index_role_tag` 插行，v2.2 只要在 ② 的同一个 dict 里加 `"roles": [...]` |
| ~~⑤ 行情条排序~~ | `api/market.py` 的 `INDEX_ORDER`（**隐性**义务，已漂移两次的源头） | **删除**，改由 ② 的 `display_order` 驱动 |

**净效果：显性义务仍是 3 处，但消灭了 1 处最易漏的隐性义务，且新数据的"落点"从 2 个表收敛到 1 个表。** 因为「忘了加进 `INDEX_ORDER`」不报错、只会静默排到末尾（现状正是：6 只被挤到末尾没人发现）；而「忘了填 `display_section`」会落到 `其他` 区，是**看得见**的兜底。

> 这一条是单表化在可移植性上的真实收益：**新增一只指数，只改一处 dict，且只有一张表要恢复**。多一张表就多一个"忘了 seed 它"的机会。

降级规则写进脚本注释：`display_section IS NULL` → 落 `其他`；`display_order IS NULL` → 排最后；`roles` 为 NULL 或空数组 → 无徽章但其余正常。**不允许因元数据缺失让指数从界面消失。**

## 12. 接口契约

### 12.1 `GET /api/market/index-list`（改）

**现状**：`market.py:85-99` 的 SELECT 只取 `i.*` 与 `p.description/p.base_date/p.base_point`，**没有 `index_group`**，也没有任何新列。排序在 Python 里用 `INDEX_ORDER` 硬编码（`market.py:109-110`）。

**新增下发字段**（值全部是中文，**接口层不做任何映射**）：

| 字段 | 来源 | 缺省 |
|---|---|---|
| `index_group` / `group_desc` | `dc_index_market`（已存在，**白捡**） | NULL |
| `display_section` | `index_profile` | 缺省 `'其他'` |
| `display_order` | `index_profile` | 缺省 999 |
| `mindshare_rank` | `index_profile` | NULL |
| `scope_name` / `cap_tier` | `index_profile` | NULL |
| `core_note` / `limit_note` | `index_profile` | NULL |
| `roles[]` | `index_profile.roles` **整列透传**（`json.loads` 后原样下发），元素键为 `角色`/`强度`/`极性`/`说明`/`指标` | `[]` |

**排序改为 SQL 内完成，删除 `INDEX_ORDER` 常量**：

```sql
ORDER BY COALESCE(p.display_order, 999), i.index_code
```

**注意：这里没有 `FIELD()`，没有一个中文字面量。** 这是 `display_order` 取代 `section_rank` 的直接收益——排序逻辑与中文文案完全解耦，改分区名不影响排序。

**`roles[]` 没有 N+1 问题**（v2.1 有）：它就在 `index_profile` 的同一行上，与其它列一次查询取回。v2.1 需要"再查一次 `index_role_tag` 再按 code 分组"，v2.2 删掉了这段代码。

**接口字段叫 `roles` 而不是 `role_tags`**：与 DB 列同名，后端 `row["roles"]` 直接就是响应字段，**中间没有改名这一步**。

**pymysql 读 JSON 列返回的是 `str`**（已实测，不是 dict），所以后端必须 `json.loads()` 一次再下发；漏了这一步，前端拿到的是字符串、`.length` 会得到字符数而不是条数——这类 bug 很难第一眼看出。若某只 `roles IS NULL`，`json.loads(None)` 会抛 `TypeError`，必须先判空再解析（降级为 `[]`）。

## 13. 排序、降级与读数计算

### 13.1 降级矩阵

| 缺什么 | 行为 | 会不会「消失」 |
|---|---|---|

### 13.2 读数计算（`角色` → 数值，程序按角色名分派）

> **注意**：程序按 `角色` 分派算法，**不按 `指标`**（见 §3.3.6）。`指标` 只是给人看的说明。

| `角色` | 计算方式 | 数据来源 |
|---|---|---|
| 大众认知度 | `amount / market_amount`（当日）+ 20 日均值分位 | `dc_index_market` + `market_style_daily` |
| 市场代表性 | `index_constituents` 支数 ÷ 全市场 A 股数 | `index_constituents` |
| 规模档身份 | 直接读 `cap_tier` | `index_profile` |
| 风险偏好 / 散户情绪 / 亢奋情绪 | 直接读当日 `risk_appetite_20` / `scissors_20` / `sentiment_20` | `market_style_daily` |
| 避险腿 / 老派价值 | 该指数 20 日收益 − 中证全指 20 日收益 | `dc_index_market` 两段查询 |
| 人气基石 | `amount / market_amount` 的 20 日均值分位 + 换手率分位 | 同上市值占比表 |
| 权重压舱石 / 国家队动作 / 资金冷清度 / 定位重叠 | **本期不在 `index-list` 算**（需要逐指数历史序列，太重） | 留给 P2 的 signal-board |
| 高股息 | NULL（无数据） | — |

**性能约束**：`index-list` 现在是一次主查询 + 一次子查询，加计算后**不得**变成 21 次往返。凡需要逐指数历史序列的，本期一律不在列表接口算。

### 16.1 卡片结构（在现有结构上加两处，**不加高**）
