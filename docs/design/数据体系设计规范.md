# InvestBuddy 数据体系设计规范 v1.0

> **文档定位**：本规范是 InvestBuddy 的两大设计资产之一（与 `颜色体系设计规范.md` 同级）。
> 它回答三个问题：**平台有哪些数据、数据从哪来、数据健康吗**，并为后续优化提供可勾选的路线图。
>
> **盘点基线**：2026-09-05（库表/行数/新鲜度为当日实测；作业配置取自 `task_config` 实时快照）
> **适用范围**：InvestBuddy 全栈（采集器 / 数据库 / 分析模块 / 前端栏目）；同时作为个人金融数据仓库的可复用方法论
> **维护约定**：每次「新增表 / 新增采集器 / 数据源变更 / 健康度重大变化」必须同步更新本文档对应章节；建议每季度做一次全量健康盘点并刷新 §5 快照。

## 1. 数据体系总览

### 1.1 使命

> **把 A 股市场的公开数据，沉淀为一份本地私有、可持续更新、可交叉分析、可 AI 增强的数据资产。**

与颜色体系的"品牌一致性"定位不同，数据体系是**平台价值的底座**：前端七个栏目的每一个画面，最终都来自这里某几张表。

### 1.2 分层架构

```
┌─────────────────────────────────────────────────────────────────┐
│  展示层  Frontend（七个栏目 + 数据浏览只读浏览器）                │
│  行情看板 · 概念 · 日历 · 资讯 · 分析 · 作业监控 · 系统设置 · 数据浏览 │
└───────────────▲──────────────────────────▲─────────────────────┘
                │ REST /api/*（9 模块）      │ 只读 SELECT
┌───────────────┴──────────────────────────┴─────────────────────┐
│  服务层  FastAPI backend/app                                    │
│  api/ 9 模块 · analysis/ 4 个分析模板 · tasks/run.py 统一入口      │
└───────────────▲────────────────────────────────────────────────┘
                │ 写表
┌───────────────┴────────────────────────────────────────────────┐
│  采集层  backend/app/collectors（6 个已实现 + 6 个遗留未实现）     │
│  APScheduler 调度器 ← task_config 热配置 → task_runs 全程记录     │
└───────────────▲────────────────────────────────────────────────┘
                │ 拉取
┌───────────────┴────────────────────────────────────────────────┐
│  数据源  东财(日线/快讯/快照) · 腾讯/新浪(日线降级) · 同花顺(概念/分红)  │
│         财联社(电报) · 豆包方舟 AI（概念×事件分析，待重新激活）        │
└────────────────────────────────────────────────────────────────┘
       存储层：本地 MySQL `adata` 库 —— 27 张表 · 约 5,300 万估算行 · ~7.5GB
```

### 1.3 关键数字速览

| 维度 | 数值 | 说明 |
|---|---|---|
| 业务库 | `adata`（utf8mb4） | 本地 MySQL，1990-12-19 起 36 年跨度 |
| 表数量 | 27 张 = 25 业务 + 2 系统 | `task_config` / `task_runs` 为调度系统表 |
| 数据规模 | 全库估算 **~5,250 万行 / ~7.5GB** | 含备份与复权衍生；剔除备份 ≈ 3,640 万行 |
| 股票覆盖 | 5,786 只（日线库） | 沪深京 A/B，1990-12-19 上交所首日至今 |
| 核心行情表 | `stock_market_daily` 17,833,101 行 / 2.1GB | 唯一键 (stock_code, trade_date) |
| 定时作业 | 12 个配置 = **6 已实现 + 6 未实现** | 未实现任务调度器跳过（见 §3.3） |
| 数据源 | 5 类外部源 + 1 本地聚合 + 1 AI | 降级链保证日线可用性（见 §4） |
| 分析资产 | 4 个 Python 分析模板 → 3 个公开 API | ytd / dividend / concept-rank + AI |
| 同步频率 | 30 分钟 ~ 每月 | news 最密、月频任务为低频快照 |

## 3. 采集作业体系

### 3.1 运行架构

```
task_config（12 行，enabled/cron/params 可在前端热改）
   │  APScheduler（Asia/Shanghai，coalesce+max_instances=1+misfire 1h 补跑）
   ▼
run_task(name) ── TaskRecorder 记录 task_runs（running → success/failed + 写入条数）
   │
   ▼
collectors/*.py（实现类）→ pymysql 写表
```

- **运行中保护**：同任务 2 小时内已有 `running` 记录则拒绝新触发，防并发双写
- **失败策略**：全失败 raise → 任务 failed；部分失败（有成功写入）→ warning 但任务记 success
- **幂等**：INSERT IGNORE / TRUNCATE 重建 / 最小行数护栏（快照 <1000 行拒绝覆盖）

### 3.2 已实现任务（6 个，TASKS 注册表）

| 任务 | cron | 源 | 写表 | 说明/容错 |
|---|---|---|---|---|
| `stock_daily_incr` | `0 19 * * 1-5` | 东财→腾讯→新浪→Tushare 四级降级 | stock_market_daily | 从每股本地最新日起增量补齐；退市/停牌股失败不阻断全量（有写入则记成功） |
| `market_current_sync` | `30 18 * * 1-5` | 无外部源 | stock_market_current | 纯本地聚合日线最新交易日；TRUNCATE+全量重建 ~5,400 行；<1000 行护栏 |
| `news_fetch` | `*/30 * * * *` | 东财快讯 API + 财联社(akshare) | news | 双源容错（cls 失败仅告警）；INSERT IGNORE 兜底 |
| `trade_calendar_sync` | `30 2 * * 0` | 新浪交易日历(akshare) | trade_calendar | 补齐当年+次年 |
| `concept_market_sync` | `0 20 * * 1-5` | 同花顺(akshare) | ths_concept_market / ths_concept_info | 398 概念日线增量；新概念自动注册 309xxx；失败单概念不阻断 |

## 4. 数据源与可靠性

### 4.1 数据源清单

| 数据源 | 用途 | 接入方式 | 风控特征 | 可靠性 |
|---|---|---|---|---|
| 东方财富 | 日线主源、快讯、股票列表 | akshare `stock_zh_a_hist` + 快讯 HTTP API | 高频易触发风控/限流 | ★★★★ 主源 |
| 腾讯行情 | 日线降级 2 | akshare `stock_zh_a_hist_tx` | 偶发返回空/畸形数据 | ★★★ |
| 新浪财经 | 日线降级 3、交易日历 | akshare `stock_zh_a_daily` / `tool_trade_date_hist_sina` | 稳定 | ★★★★ |
| Tushare | 日线降级 4 | akshare `stock_zh_a_daily`(tu 通道) | 需 token、积分门槛 | ★★★ 保底 |
| 同花顺 | 概念清单/K线/分红 | akshare `stock_board_concept_*` | 名称匹配依赖上游 | ★★★★ |
| 财联社 | 电报快讯 | akshare `stock_info_global_cls` | 内部签名，偶发不可用 | ★★★ 容错源 |
| 豆包方舟 AI | 事件×概念分析 | OpenAI 兼容 HTTP | 需 ARK_API_KEY | ⚠️ 当前未激活 |

### 4.2 降级链（已实现的关键韧性设计）

日线采集四级降级，单只股票某源失败自动尝试下一源：

```
东财 stock_zh_a_hist ──失败──► 腾讯 ──失败──► 新浪 ──失败──► Tushare ──全败──► 记录错误（不阻断全量）
```

配套防御：`NO_PROXY=*`（国内源不走代理）、socket 级 15s 超时（防退市股卡死）、随机延时（降风控）。

## 5. 数据质量与健康保障

### 5.1 已落地的质量机制

| 机制 | 位置 | 作用 |
|---|---|---|
| 自然键唯一索引 + INSERT IGNORE | 各写表 SQL | 幂等去重，防并发/重跑双写 |
| TRUNCATE + 最小行数护栏 | market_current_sync | 快照全量重建，<1000 行拒绝覆盖防清空 |
| 部分失败容忍 | run.py | 有写入即记成功；全失败才 raise |
| 运行中保护 + 2h 过期 | scheduler.py | 防同任务并发双写，防脏 running 卡死 |
| 任务级审计 | task_runs | 每次执行留痕（状态/耗时/写入条数/错误） |
| 调度热配置 | task_config + sync_from_db | 前端改 cron/启停即时生效 |
| 数据浏览只读闸门 | db_browser.py | 表名/列名白名单 + 参数化绑定，杜绝写面 |

### 5.2 盘点日已知问题（2026-09-05 实测，详见 §8）

1. **`stock_market_daily` 缺 09-02/03/04 三个交易日** —— 08-17~09-01 每交易日 ~5,127-5,131 行连续，之后断档；增量任务 09-04 19:00 仅写 37 行（异常）。已影响：行情快照与全部行情看板停留在 **09-01 收盘**。
2. **`news_fetch` 间歇 1062 重复键失败** —— 同一新闻跨天被反复拉取（如 em 9/3 一条从 21:00 到 23:30 连败 6 次）；`cls-` 空 url 记录撞唯一键。已有 INSERT IGNORE 但仍有漏网路径，需排查。
3. **`finance_calendar` 停更于 2026-01-06** —— 旧 JY 源失效，AI 概念分析（`finance_concept_analysis`）随之停摆 + 无 ARK_API_KEY 降级占位。
4. **18 张历史表无采集实现**（§2.2 🔴），数据价值仍在但不可保鲜。
5. **`stock_market_daily_ex` 注释缺失、与 daily 的关系口径未文档化**；备份表 `_bak_20250802` 占 1.9GB 待归档决策。
6. **news 保留策略未定义** —— 当前仅 648 条（约 2 天），需明确窗口（如 90 天）避免历史资讯不可查。

## 7. 治理原则（新增资产必须遵守）

1. **登记优先**：新增表/字段必须同步更新本文档 §2.2 清单（表注释写进 DDL）
2. **实现优先于配置**：`task_config` 只允许登记**已在 TASKS 注册**的任务；未实现任务一律 enabled=0，杜绝"看起来在跑"
3. **源必留痕**：每个采集器 docstring 必须写数据源接口与降级策略；每个数据域标注来源
4. **幂等是底线**：所有写表必须可重跑（INSERT IGNORE / 唯一键 / TRUNCATE 重建）
5. **读取不写**：网页层只读；任何写/改/删只允许发生在 MySQL 客户端或采集器内
6. **密钥不落库**：API Key 一律环境变量（当前 `ARK_API_KEY` 已规范，待重新申请激活）
7. **指标可复算**：分析 SQL 的每个数字要能追溯到源表（避免"死数字"）
