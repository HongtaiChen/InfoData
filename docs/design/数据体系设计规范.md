> v2.11（2026-09-24）：**落地 v2.10 遗留三项待决 + P0~P3 五项整改（新股日线空洞 / table_meta 漂移 / 排期权威前移 / 引用完整性规则 / B 股状态）**。方法上**先实测复核、再动手**，结果**推翻 v2.10 自己的三条结论**：
> - **❌ 勘误一（漂移行数）**：v2.10 记「11 行漂移」**不实**，实测 **10 行**；且方向单一——全部是「**库 = 事实、脚本过期**」（seed 脚本 `_META` 未回写）。裁决证据：8 行 `flow_desc` 内的时刻与 `task_config.cron` 逐条精确对上（21:40 / 19:05 / 21:30 / 19:10 / 22:15 / 21:30 / 21:45 / 21:00）。其中 `stock_info` / `stock_info_ex` 两行原判「脚本新、库旧」**也反了**（库内已含 v2.9 换源完整说明）。
> - **❌ 勘误二（`current_cap_notnull`）**：v2.10 记「已自愈、属 TRUNCATE 重建的瞬时形态」**判错**。实测是**排期竞态**：快照 `market_current_sync`（`40 21 * * 0-4`）从 `stock_shares` 取 `MAX(change_date)` 派生 `total_captital`，而股本 `stock_shares_sync`（`45 21 * * *`）**晚 5 分钟**；新股当日无股本行 ⇒ 快照 `total_captital` 为 NULL。09-23 fail 的 2 行正是当日新股 **920025 凯达重工 / 920229 世纪数码**。「自愈」的真相只是次日股本行到位后重建即恢复。

> **P0 · 新股首采起始日（治真因，非治表象）**：名册缺行（v2.9 已修）只是**暴露**，真正隐患在 `stock_daily_incr._process_one` —— 对「本地无数据」的股票一律用 `cutoff`（目标日近 15 个交易日窗口）作起始日，新股首次入库只能补最近 15 天，**上市初期历史永久空洞**（实测 688836 宇树科技缺 08-19~09-08、001399 惠科股份缺 06-26~09-08）。修法：`get_stock_list()` 返回元组由 3 元扩为 **4 元**（新增 `list_date`；**注意 SQL 列序必须排在子查询 `last_date` 之后**，否则位置解包错位——本次踩过一次，dry-run 筛出 0 只才发现），`_process_one` 改**三级起始日判定**：**有本地数据 → 最新日 +1；无本地数据 → `list_date`；连上市日也缺 → 才回退 15 交易日窗口**；`RUN_STEPS` 第 2 步文案同步。回补实测：候选池「本地零数据」**89 → 1**（唯一剩者 `920201 N百瑞吉`，2026-09-24 上市首日、源侧尚无行情）；2025-09 后上市新股 **169 只中 168 只有日线**，**「首行晚于上市日」的历史空洞 = 0**（修复前 60 只无日线）。

> **P1a · 漂移清零 + 排期时间「权威前移」**：① 漂移 **10 → 0** 行——用 **AST 行定位**（`ast.AnnAssign` + `elts[3].lineno/end_lineno`）整行替换 10 张表的 `flow_desc`，**刻意不用正则**（正则首版把 6 元组 `_META` 退化成 5 元组、吞掉 `source_desc`，靠备份回滚；第二版整行替换又吃掉元组分隔逗号 ⇒ 教训是「**语法正确 ≠ 结构正确**」，`ast.parse` 查不出，必须加元素数/字段数结构校验）；`dq_rules` 条数 131 → 132 一并同步。② **治本**：排期时刻长期被复述在 `table_meta.flow_desc`（静态文本）里，必然漂移。故把权威前移到**运行时**——后端 `/api/db/tables/flow` 的 job 块透传调度器早已产出却未暴露的 `cron_human`，前端数据流弹窗在「数据源」与「清洗口径」之间插入**「排期（实时读调度器 · 权威）」**区块（任务名 / cron 人话标签 / 原始 cron / `[已停用]` / 下次运行时间），并明确 **`flow_desc` 里的时刻一律降级为历史叙述**；前端类型检查 **`vue-tsc -b` 0 错误**。⚠️ **提交前复核发现：本仓库 `tsconfig.json` 是 solution 式引用文件，`vue-tsc --noEmit` 会「不检查任何文件、静默 exit 0」** —— 1 秒返回、零输出、连 `tsbuildinfo` 都不刷新，属**无效验收**（v2.8 / v2.9 条目里「vue-tsc 0」的同类表述据此同样不成立，勿再沿用该命令）。正确命令是 **`vue-tsc -b`**（即 `package.json` 的 `build` 脚本前置那一步），已用**负对照**验证其非死命令：植入 `const x: number = "abc"` 后 `EXIT=2` 并报 `error TS2322: Type 'string' is not assignable to type 'number'`，删除探针后复跑 `EXIT=0` / 零输出。

> **P1b · 股本候选池排序语义**：实测确认 `_common.load_refresh_targets` 的排序首键 `umax is not None` **= 新股优先**（`umax is None` 表示零记录，布尔 False 排最前）——该语义一直是**隐式**的，已就地写入注释固化，避免后人「顺手优化排序」而破坏新股优先。**残留（决策项，未擅动）**：候选池决定「谁先跑」，不决定「谁跑完」——快照 21:40 仍早于股本 21:45，新股当日 `total_captital` 仍为 NULL。

## 1. 数据体系总览

### 1.1 使命

> **把 A 股市场的公开数据，沉淀为一份本地私有、可持续更新、可交叉分析、可 AI 增强的数据资产。**

与颜色体系的"品牌一致性"定位不同，数据体系是**平台价值的底座**：前端七个栏目的每一个画面，最终都来自这里某几张表。

### 1.2 分层架构

                │ REST /api/*（9 模块）      │ 只读 SELECT

## 3. 采集作业体系

### 3.1 运行架构

```
task_config（12 行，enabled/cron/params 可在前端热改）
   │  APScheduler（Asia/Shanghai，coalesce+max_instances=1+misfire 1h 补跑）
   ▼
run_task(name) ── TaskRecorder 记录 task_runs（running → success/failed + 写入条数）
   │
   ▼
collectors/*.py（实现类）→ pymysql 写表
```

- **运行中保护**：同任务 2 小时内已有 `running` 记录则拒绝新触发，防并发双写
- **失败策略**：全失败 raise → 任务 failed；部分失败（有成功写入）→ warning 但任务记 success
- **幂等**：INSERT IGNORE / TRUNCATE 重建 / 最小行数护栏（快照 <1000 行拒绝覆盖）

## 7. 治理原则（新增资产必须遵守）

1. **登记优先**：新增表/字段必须同步更新本文档 §2.2 清单（表注释写进 DDL）
2. **实现优先于配置**：`task_config` 只允许登记**已在 TASKS 注册**的任务；未实现任务一律 enabled=0，杜绝"看起来在跑"
3. **源必留痕**：每个采集器 docstring 必须写数据源接口与降级策略；每个数据域标注来源
4. **幂等是底线**：所有写表必须可重跑（INSERT IGNORE / 唯一键 / TRUNCATE 重建）
5. **读取不写**：网页层只读；任何写/改/删只允许发生在 MySQL 客户端或采集器内
6. **密钥不落库**：API Key 一律环境变量（当前 `ARK_API_KEY` 已规范，待重新申请激活）
7. **指标可复算**：分析 SQL 的每个数字要能追溯到源表（避免"死数字"）
