## 一、为什么触发点必须是「启动」

### 1.1 实测的使用画像（全部设计的依据）

**方法**：以最高频任务 `news_fetch`（`*/30 * * * *`）为心跳探针 —— 服务在线 ⟺ 该小时必有它的执行记录。  
用 `task_runs` 回算近 38 天：

| 指标                    | 实测值                                               |
| --------------------- | ------------------------------------------------- |
| **在线率**               | **32.0%**（399 条 / 理想 1248 条）；在线小时 221/624 = 35.4% |
| **断线次数**              | **41 次 / 38 天** —— 几乎每天断一次                        |
| **典型形态**              | 22:00 关机 → 次日 18:00~19:00 开机，**每天离线约 20 小时**      |
| **01~06 时在位**         | **0 / 38 天**（仅 4 天的 00 时有记录）                      |
| **晚间窗口（19~23 时）完整覆盖** | **10 / 28 天 = 36%**；完全错过 2 天                      |
| **最长离线**              | **260 小时（10.8 天）**：09-27 23:30 → 10-08 19:30      |

### 1.2 由画像推出的结论

45 个任务的 cron **全部落在 19:00~23:00**（说明排期已被「晚上才开机」这个习惯塑形过一轮），  
但实测各时段在位率只有 **63% / 61% / 58% / 47% / 29%**：

> **排期假设了「你每天都开」，而实测有 1/3 的日子不成立。**

⇒ 任何「按墙上时钟触发」的机制（cron、每小时复检）都只在**在线的那几小时**里有效，  
而 90% 的问题发生在**离线期间**。**唯一真正对齐使用习惯的触发点是「进程启动」。**

⚠️ 这条结论**撤回了**上一轮讨论中的「方案 2（把 catchup 改为每小时复检）」——  
它在 32% 在线率下价值很低，且会带来重试洪峰与上游压力。

### 1.3 现有五条补偿通道，与它们的共同盲区

| # | 通道                    | 触发条件             | 依据                            |
| - | --------------------- | ---------------- | ----------------------------- |
| 1 | misfire 补跑            | 进程活着但错过触发点（≤6h）  | `MISFIRE_GRACE_SECONDS=21600` |
| 2 | 链式接力                  | 上游成功             | `CHAIN_NEXT`                  |
| 3 | 兜底班次                  | 固定时刻且当日无 success | `CHAIN_FALLBACK_TASKS`（3 个）   |
| 4 | 采集器水位回补               | 每次任务运行时          | 各源能力不同                        |
| 5 | 启动补偿 `catchup_missed` | **仅进程启动那一刻**     | `CATCHUP_LOOKBACK_DAYS=45`    |

**共同盲区**：五条全部住在**进程内部** ⇒ 「服务根本没启动」时集体静默（已实测 9 天：09-29~10-07）。

## 三、方案设计

### 3.1 启动流水线

```
uvicorn lifespan → SchedulerManager.start()
  ├─ reap_orphan_runs()         已有：回收僵尸 running
  ├─ sync_from_db()             已有：按 task_config 重建调度
  └─ _spawn_boot_pipeline()     ★新增（后台线程，不阻塞启动）
       └─ _execute("startup_converge")
            └─ run_startup_converge()  ── 六步闭环 ──
                 ① 跑一轮 daily 体检（复用 data_quality_check 任务）
                 ② latest_scan(groups=("daily",)) 读结果
                 ③ plan()：按白名单分诊 → 可自愈目标 / 需人工 / 定位不到
                 ④ _find_missed() 读时间维度遗漏 → merge_todo() 合并去重
                 ⑤ repair()：串行执行（预算只约束 DQ 来源的额外修复）
                 ⑥ 再跑一轮体检 + diff_rules() → 报告落 run_detail
```

⚠️ **兜底**：流水线自身异常时，`start()` 会回退调用原有的 `catchup_missed()` ——  
不让新增的自愈能力成为启动补偿的单点故障。

### 3.2 为什么要与 `catchup_missed` 合并成一条队列

两者目标高度重叠：**DQ 报 fail 的表，其 writers 往往正是 catchup 要补的任务**。

|    | `catchup_missed`               | 本收敛器                |
| -- | ------------------------------ | ------------------- |
| 依据 | **时间**：cron 最近触发点未被 success 覆盖 | **水位**：DQ 说哪张表、落后几天 |
| 擅长 | 覆盖 DQ 尚无规则的表；高频流（news）         | 精确到「哪张表真的缺」         |
| 短板 | 不知道「数据到底缺没缺」                   | 依赖 writers 映射质量     |

若各起一条后台队列 → 互相抢任务（`_execute` 的锁保证不双跑，但产生大量 skip 与日志噪音），  
且白跑一轮。**合并后按任务名去重**，重叠项标记 `source='missed+dq'`，  
便于事后判读「这次补跑到底是哪个依据救回来的」。

### 3.3 三条铁律（不可越界）

| # | 铁律            | 理由                                                                                                                  |
| - | ------------- | ------------------------------------------------------------------------------------------------------------------- |
| 1 | **只修「数据缺失型」** | 值域越界 / 唯一性冲突 / 格式不符 / 跨表引用缺失，**重跑修不好**，还可能用上游的间歇性异常值**覆盖真实数据**（本项目有过 `ths_concept_market.change_pct` 源侧空值率 99% 的先例） |
| 2 | **映射缺失不猜测**   | writers 为空或指向未注册/已禁用任务时，不做推断，直接转「待人工」。**猜测性重跑比不重跑更危险**                                                              |
| 3 | **不做无上限重试**   | 同一任务一次收敛内最多执行一次；修不好交人工，绝不进入「修→不过→再修」死循环                                                                             |

### 3.4 止损设计

| 机制    | 实现                                                       | 防的是什么                            |
| ----- | -------------------------------------------------------- | -------------------------------- |
| 单次上限  | `DEFAULT_MAX_REPAIRS=10`，超出的记 `deferred`                 | 重跑风暴（一张长期故障的表拖垮上游）               |
| 同任务一次 | `merge_todo` 按任务名去重                                      | 同一任务被两个依据重复触发                    |
| 不重试   | 复检仍 fail → 只**记录**，本轮不再动                                 | 无限修复循环                           |
| 并发安全  | 复用 `_execute` 的 `_task_lock`(进程内) ＋ `_running_count`(2h) | 与 cron / 手动触发双跑（09-19 真实事故的修复成果） |
| 防自递归  | `NEVER_REPAIR_TASKS` 排除 `startup_converge` 与两个体检任务       | 收敛器把自己当修复目标                      |

⚠️ **预算只约束 `source='dq'` 的项**：`missed` / `missed+dq` 属原有启动补偿语义（补齐关机期间错过的班次），不限额。

## 四、分诊白名单（21 类检查器全覆盖）

### ✅ 可自愈 7 类（语义统一为「数据缺失 / 停更 / 行数不足」，重跑 writers 是对症的）

| 检查器                  | 含义                |
| -------------------- | ----------------- |
| `freshness_daily`    | 表 MAX(日期) 落后交易日历  |
| `freshness_interval` | 距当前时长过久（高频流）      |
| `date_floor`         | 日期下限不足（停更）        |
| `date_floor_where`   | 某条腿停更（子集日期下限）     |
| `column_watermark`   | 有列无值：某列不再有新值      |
| `row_count_slice`    | 最新切片行数不足          |
| `row_count_total`    | 总行数不足（清空 / 大面积缺失） |

### ❌ 不可自愈 14 类（附可读原因，会出现在报告的「需人工处理」清单里）

| 检查器                 | 为什么不能自动修                                         |
| ------------------- | ------------------------------------------------ |
| `unique_index`      | 结构问题：需执行 DDL 补唯一索引，重跑无益                          |
| `regex_count`       | 格式不符：属解析逻辑问题，重跑只会把同样的错再写一遍                       |
| `null_rate_slice`   | 空值率高：可能是源侧间歇性不返回，重跑有覆盖真实数据的风险                    |
| `violation_count`   | 值域越界：需人工判断是脏数据还是口径变了                             |
| `where_count`       | 自洽约束不成立：需查复权因子或上游源                               |
| `ref_missing`       | 跨表引用缺失：属名册采集口径问题                                 |
| `pct_limit`         | 涨跌幅超板块上限：物理约束被违反，说明价格或因子写错                       |
| `factor_link`       | 复权因子不自洽：属因子体系问题                                  |
| `date_ceiling`      | 日期落到未来：日期解析/拼接写错，需改采集代码                          |
| `gap_scan`          | 全史缺口：应由 `daily_backfill` 定向回补（全史扫描耗时长，不宜在启动期自动跑） |
| `source_handoff`    | 跨源衔接偏差：属换源口径问题                                   |
| `per_key_coverage`  | 每票覆盖不足（均匀稀疏）：需查采集范围与源能力上限                        |
| `stale_running`     | 僵尸 running：已由启动时的 `reap_orphan_runs()` 自动回收      |
| `long_finished_run` | 超长运行：这是「机器待机冻结进程」的物理离线信号，不是任务故障                  |

## 八、勘误（推翻既往结论）

## 九、已知边界

- **收敛只在启动时发生**：服务连续运行多天不重启时，本机制不会触发（但 cron 与链式接力仍在工作）。
- **依赖 `table_meta.writers` 的质量**：映射错误会导致「重跑错任务」。当前 47 张 DQ 守护表中可自愈类的覆盖为 100%。
- **启动巡检只覆盖 daily 组**：weekly 组（8 条）仍由周一 21:30 的独立任务负责。
- **首次收敛耗时取决于缺口规模**：合并队列可能包含数十个待补任务（如 9 天停摆后的首次启动），此时修复会串行跑较久。
- **发布时刻门槛依赖 `task_config.cron` 的正确性**：cron 若写错（如把 22:00 的任务写成 09:00），门槛会跟着错判 —— 但这正是「跟着真源走」的代价，好过另立一张会漂移的「数据就绪时刻表」。
- **门槛只覆盖「日频级」任务**（当日触发 ≤ 6 次）：高频流（如 `*/30`）当日触发数十次，末次永远在未来，若也套门槛则等于**永不修复**，故显式豁免。
- **weekly 组的 8 条规则全部属不可自愈类**（见 §10.4）：进巡检的收益是「可见」，不是「可修」。

### 10.2 问题 A 的真根因（**推翻我上一轮的判断**）

上一轮我把问题 A 描述为「缺少发布时刻门槛」。真启动后取到的**数据侧证据**显示根因不同：

```
19:27:20  data_quality_check  success  199 条     ← 当天首次（19:27 那次启动）
20:47:59  data_quality_check  success  199 条     ← 每次 startup_converge 都会跑一轮
20:51:20  / 20:52:25 / 20:55:28 / 20:56:32 / 20:58:14 / 20:59:13   各 199 条
```

- `run_startup_converge` 的第 ① 步是 **`sm._execute("data_quality_check")`（真跑一轮体检）**；
- 而 `CHAIN_NOT_BEFORE = {"data_quality_check": "22:45"}` 这道 2026-09-22 专门设立的「数据就绪下限」**只在链式路径（`_chain_floor`）生效** —— `_execute` 与 `_run_scheduled` 都**没有**这道守卫；
- 于是启动收敛在 20:47（数据远未发全）跑体检 ⇒ 所有「21:30 后发布」的表必然 warning ⇒ 被判「可自愈」⇒ 白跑。

> **结论**：启动收敛**无意中绕开了既有的数据就绪保护**。修法不是再造一套时刻表，  
> 而是让**分诊环节**认识「这条规则的写入方今天还没到发数据的点」。

**判据**（`release_floor`）：从 `task_config.cron` 算「当日末次触发时刻」；  
`当日触发次数 ≤ 6`（日频级）且 `now < 末次触发` ⇒ 归 **`pending`（待发布）**。

**为什么用「末次触发」而不是「是否已有过 success」**：`concept_market_sync` 的  
`0 21,22 * * 0-4` 里，**21:00 那批 `status=success` 但只写 2~17 行**，当日主体在 22:00 才落库。  
按「有过 success」判会误认为数据已就绪、于是重跑（实测白烧 60~67s）。

**真库前置验证**（改码前先跑的对照，`_scratch/_probe_release_floor.py`）：

| 任务                             | cron                      | 当日次数 | 末次            | 判定                      |
| ------------------------------ | ------------------------- | ---- | ------------- | ----------------------- |
| `concept_market_sync`          | `0 21,22 * * 0-4`         | 2    | 22:00         | ✅ 待发布                   |
| `futures_sync` / `xcheck_sync` | `20 22` / `30 22 * * 0-4` | 1    | 22:20 / 22:30 | ✅ 待发布                   |
| `usd_index_sync`               | `10 21 * * *`             | 1    | 21:10         | ✅ **可修复**（21:10 已过，未误伤） |
| `news_fetch`                   | `*/30 * * * *`            | 48   | —             | ✅ 不适用（高频豁免）             |

### 10.3 兜底班次误报（问题 B）

`CHAIN_FALLBACK_TASKS`（`market_style_sync` / `market_current_sync` / `data_quality_check`）  
的固定班次在链式已跑成时，会被 `_run_scheduled` 打印「⏭ 兜底班次跳过」并**直接 return、不写 task_runs**。  
于是 `_find_missed` 的「该班次时刻之后没有 success」判据必然命中 ⇒ **每次重启都白补跑这三个**（约 90 秒，幂等、无数据影响）。

**修法**：在 `_find_missed` 里对这三个任务改用 **`_succeeded_today(name)`**（当日有 success 即算跑成）  
—— 与 `_run_scheduled` 第 409 行**同一判据**。这不是新特例，而是**把两处口径统一**。

### 10.4 weekly 进巡检：实测结论决定了「只读不重跑」

| 事实                             | 实测                                                                                                 |
| ------------------------------ | -------------------------------------------------------------------------------------------------- |
| weekly 8 条规则指向                 | **全部** `stock_market_daily`                                                                        |
| 它们的 `check_type`               | `where_count`×3 / `per_key_coverage` / `factor_link` / `gap_scan` / `pct_limit` / `source_handoff` |
| 是否属不可自愈类                       | **8/8 全部在 `MANUAL_ONLY_CHECKERS`**                                                                 |
| `data_quality_check_weekly` 耗时 | **808 / 1106 / 1477 / 2163 / 2318 秒**（13.5~38 分钟）                                                  |

⇒ 若「进巡检」＝**每次启动重跑**，代价是十几分钟，而**一条都修不了**。

**落地**：默认 `groups=["daily","weekly"]`，但 weekly **只读最近一轮结果**（`latest_scan` 本来就是读，  
所以这在成本上约等于零），把它的 manual 结论一并呈现在收敛报告里 —— 这才是「进巡检」真正有价值的部分。  
确需重跑时显式开 `rescan_weekly=true`，并配 `weekly_min_interval_days=6` 节流。

### 10.5 修复上限：从「个数」到「个数 + 时间」双维度

`max_repairs=10` 是**个数**维度，但单任务耗时实测跨度 **1s ~ 1722s**（`daily_recon_window` 全市场逐票拉取 28 分钟），  
「10 个任务」可能是 10 秒、也可能是 5 小时 —— 个数维度**防不住「一次启动占满整个晚间窗口」**。

**落地**：新增 `max_seconds=900`（时间维度），**两者任一触发即停**，余量原样转 `deferred`（报告里显示为「需人工/超限」）。  
两个预算**都只约束 `source='dq'` 的项** —— `missed` 是「补齐关机期间错过的班次」，属必需语义，跑得慢也该跑完。
