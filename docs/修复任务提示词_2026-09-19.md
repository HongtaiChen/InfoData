## 1. 环境与铁律（违反任何一条都会返工）

**体系**
- FastAPI 后端 `127.0.0.1:8000`（**无 --reload，改后端必须重启**）；Vue3 + Vite 前端 `127.0.0.1:5173`（HMR，改前端不用重启）
- 数据访问统一走 `app/db.py` 的 `query_all` / `query_one` / `execute_write`
- **种子脚本是唯一事实来源**：任务 `seed_task_config.py`、规则 `seed_dq_rules.py`、表元信息 `seed_table_meta.py`。直改 DB 后**必须回写种子脚本**，否则下次 seed 覆盖回去

**必须遵守的既有坑**
1. **先读 `information_schema.COLUMNS` 再拼 SQL**。2026-09-19 又踩一次：凭记忆写 `task_config.cron_expr` → `Unknown column`。真实列名是 `cron`（`task_config` 仅 `task_name / enabled / cron / params / update_time`）
2. `query_one` **自带 `LIMIT 1`**，SQL 里再写会拼成 `LIMIT 1 LIMIT 1`
3. `query_all` 传 `params=None` 时 pymysql 不做 `%` 转义 → SQL 里写 `%Y` 即可；**只有传 params 时才写 `%%`**（写反会静默返回空结果）
4. `information_schema.TABLE_ROWS` 是**估算值**（会把 36 读成 35、107 读成 104）→ 判一致性必须 `SELECT COUNT(*)`
5. 改采集器后必须**真实 import 验证**（`py_compile` 查不出导入期 NameError）
6. 同一文件**严格串行 Edit**（并发写会互相覆盖，工具却报成功）→ 改完 grep 复核落盘
7. 新增/改动主链任务必须**同步 `scheduler.CHAIN_NEXT`**；cron 时刻须落 **19:00–23:00** 窗口；`day_of_week` **0 = 周一**（与 Unix 反向）
8. 若目标表被 `DELETE+INSERT` **整表重建**，外来列会被清空 → 不能挂列，必须独立建表
9. 沙箱 Bash 会丢 coreutils PATH（`ls/tail/head` 报 command not found）→ 文件操作改用 python 绝对路径 `C:\Users\cht\.workbuddy\binaries\python\versions\3.13.12\python.exe`；涉及网络的脚本必须先 pop 掉全部代理变量
10. 启停服务用技能 `investbuddy-backend-restart`（后台 + 沙箱外 + 无代理），**停完复查端口**
11. ⚠️ **后台任务报 `failed` ≠ 服务挂了**（2026-09-19 实测：端口由另一 PID 正常服务、调度器健康、代码是最新的）——常见原因是**另一个会话按流程重启了后端**。收到失败通知先核 PID 与代码版本，别急着重启
12. ⚠️ **同一仓库可能被多个会话并发操作**（2026-09-19 当天就发生了：提示词写完时，另一个会话已交付批次 A 的 `96f8dcf`）→ 动手前先 `git log --oneline -3`；**只 `git add` 自己改的路径，别用 `git add -A`**（会卷进对方未完成的改动）；读代码做归因时必须确认读的是**出问题那一刻的版本**（`git show <commit>:<file>`）——当天踩过：拿**修复后**的代码推断**修复前**行为，得出错误根因
