### ✅ P1-① `current_turnover_dirty` 换手率判据量纲错 100 倍 → 4177 条假阳（**规则缺陷，非数据脏**）

- **现象**：09-22 `fail`，4177 行满足 `turnover_ratio > 1`，阈值 `max_count=60`。
- **根因（原定性已推翻）**：规则描述断言「本表 `turnover_ratio` 是比率量纲（0~1 正常）」。实测**前提不成立**：
  - `stock_market_current` 的该列由 `stock_market_daily` **直拷**（`market_current_sync.py:148` 取 `d.turnover_ratio`）；
  - 实测两表同交易日**逐行完全相等（5465 / 5465，不等 0）**——同一列、均为**百分比**量纲；
  - ⇒ 判据阈值比真实量纲小 100 倍，把正常换手率全判成越界。「0~1 比率」是 09-20 快照改为「从日线聚合」**之前**的旧口径。
- **时间线（关键证据）**：该规则 09-19 与 09-20 08:02 均 `pass(25)`，**09-20 16:06 突变为 `fail(3945)` → 09-21 4230 → 09-22 4177**，与快照表切换为「从日线取数」同一时刻。
- **修法（已落地）**：判据 `turnover_ratio > 1` → **`> 100`**（单日换手 >100% = 成交量超过全部流通股，物理不可能），`max_count` 60 → 0。
- **验收**：`turnover_ratio > 100` 实测 **0 行** → 规则回 **`pass(0)`** ✅（seed + 库内双改，防 re-seed 回流）

### ✅ P1-② 北交所 920 段 `total_captital` 全空（313 行）——真根因是**整个股本采集链路空转**

### ✅ P1-③ `ths_concept_market.change_pct` / `change_amount` 大面积 NULL

- **现象**：两列**同行同时为 NULL**，而 `close / open / high / low / volume / amount` **完好无缺**。null 率演化：

  | 日期 | 09-02 | 09-03 | 09-04~09-10 | 09-11 | 09-14~09-18 | 09-21 |
  |---|---|---|---|---|---|---|
  | null/总数 | 0/375 | 367/375 | 355~374 | 119 | 349~375 | **360/360** |

- **根因（代码级）**：`concept_market_sync.py` 的 `prev_close = None` **按概念重置**，涨跌额/涨跌幅**只能**由「同一次抓取返回的前一行」推出。增量窗口使**源每天只回一行**后，**首行恒 `prev_close=None` → 两列恒 NULL**。叠加写入用 `INSERT IGNORE`，**历史行永不回补**，故劣化不可自愈、只累积。
- **影响面（已核实）**：概念排行榜未受影响（`concept_rank.py` 已 COALESCE 兜底）；裸用点是 `api/concept.py`（K 线接口）与 `concept_rank._period_rank` 的 `day_change_pct` → 前端「涨跌幅/涨跌额」列出现空值。
- **修法（已落地）**：采集端新增 `_last_close_before()`——昨收取自**库内上一交易日 close**（`WHERE index_code=? AND trade_date<? ORDER BY trade_date DESC LIMIT 1`），不再依赖本次返回行；K 线接口改为子查询 + `LAG(close) OVER (PARTITION BY index_code ORDER BY trade_date)` + `COALESCE` 兜底；`concept_rank` 的 `day_change_pct` 同步兜底。
- **历史回补（已落地）**：`change_pct` **6281 行**、`change_amount` **5025 行**；全表仅剩 **398 行** = 每个概念的**首行**（无前收可依，不可消除）。
- **验收**：最新交易日 null 率 **0.000%** → `concept_change_pct_gap` 回 **`pass(0.000%)`** ✅

- **现象**：09-20 新增规则，指标恒为整数 1000（5 次执行全 1000），疑似截断。
- **实测结论（用独立脚本按年份/代码段/数据源三重分布，共 4 次全史窗口查询，耗时 399+386+393+388s）**：

  - 按代码段：`60*`(沪主板) 573 + `00*`(深主板) 342 + `20*` 55 + `30*`(创业板) 29 + `68*`(科创) 1；
  - 按数据源：**TENCENT 896 / SINA 104**。
- **勘误·第二次（v3，2026-09-22 已查清，见 `docs/昨收与涨跌幅列失真取证_2026-09-22.md`）**：
  - ❌ **v2 的「缩股/重整造成价格量级跳变而因子未跟随」定性已被推翻**——`adj_factor == 前日因子`

    124.830 vs 2.090 这个值**任何因子解释都推不出来**。

    用**后复权(hfq)序列的逐日比值 `ret`** 反算：`change_pct = ret×100`、`pre_close = close/(1+ret)`。

  - ✅ **决定性指纹**：代码护栏 `ret > -1` 会在 `change_pct ≤ -100%` 时把 `pre_close` 写 NULL 但照写 `change_pct`
    → 全库实测 `change_pct ≤ -100` 共 **307 行，其中 307 行 `pre_close IS NULL`，反例 0**。
  - ✅ **`close` / OHLC 不受影响**（`daily_ohlc_consistent` pass，样本中 `close` 全程平滑）→ **日线价格本身可信**。
  - ⚠️ **本规则（`factor_link`）的 1,000 行与「`pre_close` 列失真」是同一批东西**：其 `max_count=1000` 基线
    属**上账，不是豁免**；**是否重算该列 = 口径取舍，列为决策项**（取证报告 §八 给了可不回源的重算公式与风险）。
- **移交结论修正**：v2 建议的「因子未随除权跳变」立项**已完成并结案**，但**结论不是因子问题**——
  是 `pre_close`/`change_pct` 两列失真（受影响行占比 0.026%）。**不要再按「因子问题」方向排查。**

## 四、机制缺口

### 1. ✅【v3 已处置并勘误】DQ 执行时刻不是固定值，且「登记班次是否触发」曾被误判

> ❌ **v1/v2 的错误结论**：「`50 21 * * *` 班次**可能从未触发**」。
> ✅ **v3 实测推翻**：该班次**照常触发**，只是 `_run_scheduled` 见当日链式（约 20:02）已 `success`，
> 就走 `_succeeded_today` 的**「⏭ 兜底班次跳过」分支直接 return，不写 `task_runs`**
> ——所以「按 `started_at` 查不到 21:50 的记录」只证明它每次都走了跳过分支，**不能推出「没触发」**。
> 验证方式（不必等整点）：给 `infodata.scheduler` logger 挂内存 handler、把 `_succeeded_today`
> 打桩为 True 后调 `_run_scheduled("data_quality_check", force=False)`，断言日志含「兜底班次跳过」
> 且 `_execute` 未被调用（2026-09-22 实测 PASS，见 `tmp/test_chain.py` T4）。

- 关键事实（未变）：实际 DQ 时刻由**链式触发**决定（`stock_daily_incr` → `market_style_sync` →
  `market_current_sync` → `data_quality_check`，常态 **20:00–20:02**）；`task_config` 内时刻只是兜底。
- 三条纪律：① 判「任务跑没跑」查 `task_runs`；② 判「班次有没有触发」看日志或 `next_run`；
  ③ `_succeeded_today` 会**静默吞掉兜底班次**，故「兜底时刻」永不等于「实际执行时刻」。

**v3 处置（治本，已落地）**：把 DQ 推到所有采集之后——`scheduler.CHAIN_NOT_BEFORE =
{"data_quality_check": "22:45"}`。链式**保留**（保证不早于上游 success），只在早于下限时改挂
`defer__data_quality_check` 一次性 job 到点触发；`task_config` 的 cron 由 `50 21` 改为
**`0 23 * * *`**，降级为**纯兜底**（当日链式跑成即被跳过；若 22:45 失败或进程重启丢了延迟 job，
23:00 仍是当日补救窗口）。`sync_from_db()` 对 `defer__*` 前缀的 job **跳过不删**（否则每次热同步都误删）。

- 时刻依据（实测常态完成时刻）：`concept_market_sync` 补班 **22:01** / `jgdy_sync` **22:00** /
  `financial_abstract_sync` **22:15** / `futures_sync` **22:20** / `xcheck_sync` **22:30**
  → 22:45 = 最晚者之后 15 分钟余量。
- **验收 = 与排期等价的自然实验**（2026-09-22 22:43 实测，当时上述采集均已落库）：
  `concept_market_rows` **pass(375)**、`concept_market_freshness` / `futures_freshness` /
  `xcheck_freshness` 三条在**没有任何 `grace_days`** 的情况下**全部 pass**；
  daily 组 **120 pass / 1 warn / 0 fail / 0 error**。
- **实盘旁证（2026-09-22 23:00–23:01 观测）**：新调度器进程 22:40:51 起活。当晚 23:00 兜底时刻
  **到点但未执行**——`task_runs` 无 23:00 的 `data_quality_check` 记录（当日最后一条仍是 22:15:41 那班链式），
  `dq_report` 最新仍停在 22:43:04，而 `GET /api/jobs/tasks` 的 `next_run` 已推进到
  **2026-09-23 23:00:00**，证明该 due job 已被调度器正常消费并走了 `_succeeded_today` 的
  「⏭ 兜底班次跳过」分支（当日已有 success）；任务列表内**无 `defer__*` 残留**（延迟 job 不是常驻排期）。
- ⏳ **待 09-23 实盘确认**：`CHAIN_NOT_BEFORE` 的**延迟分支**今晚无机会触发（当晚链式在 22:15 已于
  重启前的旧代码下跑完）。明日链式若在 22:45 前跑成，观察点＝`defer__data_quality_check` 是否被挂出、
  22:45 是否自动执行、23:00 是否被跳过。

> （见 §五 #10 / #11 状态更新）——时点改对后它们天然 pass，留着只会把「当日数据根本没落库」一起放过，
> 等于把这三条监控废掉。**这是「治本」相对「治标」的实质差别，不是风格偏好。**

### 3. ✅【v3 已根治】`concept_market_rows`（critical）在 **21:00–22:00 窗口**内运行会假失败

- 该规则语义是「**最新交易日**行数 ≥ 150」。而 `concept_market_sync` 在 **21:00 与 22:00 各跑一次**，21:00 那次是残批（实测 09-22 只写入 2 行 / 09-21 是 4 行 / 09-18 是 132 行），**22:00 补班才是主体**（358 / 361 / 375 行）。

- **v3 处置**：DQ 整体后移至 **22:45**（早于下限则延迟，见 §四-1），残批窗口不再重叠。
  **验收**：22:43 自然实验 → `concept_market_rows = pass(375)` ✅（详见 §四-1）。

### 4. 🔴 采集器卡死在外部 HTTP 会让**整个后端**失去响应（2026-09-22 22:10 实测事故）

- **现象**：`/api/health` 在内的**全部接口**挂满 45s 无响应（非慢，是卡死）；前端取不到数据。同一时刻 `stock_shares_sync`(21:45 起) / `concept_market_sync`(22:00 起) / `jgdy_sync`(22:00 起) 三个任务状态均为 `running` 且远超正常耗时（正常 27s~155s / 50s）。

- **处置（已按 `investbuddy-backend-restart` 技能执行）**：停服 → 重启 → 启动自愈**回收僵尸 running 3 条**（`stock_shares_sync#656` / `concept_market_sync#657` / `jgdy_sync#658`）→ `catchup_missed()` **补跑 5 个遗漏班次** → 手动触发 `concept_market_sync` 补齐当日概念数据。
- **验收**：`/api/health` 200、`/api/jobs/tasks` 200（`scheduler_running=True`、`scheduled_count=34`、无重复任务名）、前端代理链路 `/api/analysis/market-wind` 200 ✅；补跑后概念 09-22 = **375 行** ✅

## 七、v3 起持续续写：检查器的「切片 vs 全史」口径必须显式确认

> 本节由 v3 开篇（7.1~7.3），v4 续写根因实锤（7.4），v5 续写出第二类缺陷（7.5）。

### 7.1 🔴 `daily_value_bounds` 名义全表、实际**只查最新一个交易日**（全史盲区）

- 规则描述写的是「脏值拦截：close≤0 / 量为负 / **|涨跌幅|>31%**」，读起来是全表约束。
- 但 `_violation_count` 的 SQL 带切片谓词：

  ```sql
  WHERE `trade_date` = (SELECT MAX(`trade_date`) FROM `表`) AND (close<=0 OR ... OR ABS(change_pct)>31)
  ```

  ⇒ **1,850 万行的历史部分从未被它覆盖**。此设计对 daily 组（「最新切片类、秒级」）本身**合理**，
  问题是**规则描述没有标注这一点**，导致审计时误以为「已覆盖」。

**检查器口径速查（本次补录，避免再误信）：**

| 检查器 | 口径 |
|---|---|
| `violation_count` / `null_rate_slice` / `row_count_slice` / `freshness_daily` / `row_count_total` | **最新切片**（`= MAX(date_col)`）或整表计数 |
| `where_count` / `gap_scan` / `factor_link` / `pct_limit` / `source_handoff` / `per_key_coverage` | **全史** |

### 7.2 🧭 由 7.1 盲区出发，查清了 `pre_close` / `change_pct` 列失真的**真因**

（完整取证另见 **`docs/昨收与涨跌幅列失真取证_2026-09-22.md`**；此处只放结论）

| # | 结论 |
|---|---|
| 1 | ❌ 推翻 v2 的「缩股/重整致因子未跟随」与更早的「低价股舍入」两种定性 |
| 2 | ✅ 真因：`pre_close`/`change_pct` **不是源字段**，而是 `stock_daily_core.py` L311–326 用**后复权(hfq)序列的逐日比值 `ret`** 反算（`pct=ret×100`、`pre=close/(1+ret)`）⇒ **一次失真、两列同错** |
| 3 | ✅ **决定性指纹**：护栏 `ret > -1` 使 `change_pct ≤ -100%` 的行 `pre_close` 恒写 NULL —— 全库实测 **307/307 命中、0 反例** |
| 4 | ✅ `close`/OHLC **不受影响**（`daily_ohlc_consistent` pass，样本 `close` 全程平滑）→ **日线价格本身可信** |
| 5 | ⚠️ 影响面 **4,721 行 / 842 只票（占全库 0.026%）**，且**必须分域**：718 行在 **1996-12-16 涨跌停制度实施前**、3,160 行在 **4/8/92 段（新三板协议转让本无涨跌停）**→ **不能一律判脏**；**可确证错 = 63 行**（v4 实测；原记「202~333」中的 **202 已勘误作废**，见 7.4） |
| 6 | ✅ **v4 已处置**：回源实锤腾讯 `hfq` **含负价** → **全量重算被否决**（会以错换错）；改为「代码护栏 + 修正 63 行 + 清单落库」，见 7.4 |

### 7.3 三条纪律（写进技能）

1. **读一条 DQ 规则，先确认检查器是「切片」还是「全史」**——描述里的阈值不代表覆盖范围。
2. **「恒等式类规则 pass」不等于「数据正常」**：若两列同源派生，恒等式 pass 是**构造必然**
   （`daily_change_link` pass 却同时有 4,721 行荒谬值，就是实例）。判「数据正常」要找**独立**判据。
3. **大波动不能一刀切判脏**：先按「该标的在该时期是否受涨跌停约束」分域
   （1996-12-16 前无涨跌停；4/8/92 段协议转让无涨跌停）。

### 7.4 🔴 v4 根因实锤：数据源的 `hfq` 根本不是后复权价（决定性地改变了处置方案）

**回源复核（取证报告 §八 建议 3 的明文前置条件）结果：三个源都不能用**

| 源 | 接口 | 实测 |
|---|---|---|
| 新浪 | `stock_zh_a_daily(adjust='hfq')` | **挂死**（60s 硬超时 × 5 个 case 全部 TIMEOUT） |
| 腾讯 | `stock_zh_a_hist_tx(adjust='hfq')` | **返回含负价的序列**（见下） |
| 东财 | `stock_zh_a_hist(adjust='hfq')` | `ConnectionError: RemoteDisconnected`（被风控） |

**决定性证据（600811，akshare 1.18.94）**：

| date | raw(`adjust=''`) | hfq(`adjust='hfq'`) | qfq(`adjust='qfq'`) |
|---|---|---|---|
| 2025-04-01 | 0.52 | **2.31** | 0.52 |
| 2025-04-08 | 0.43 | 0.42 | 0.43 |
| 2025-04-09 | 0.41 | **-0.01** | 0.41 |
| 2025-04-14 | 0.36 | **-1.06** | 0.36 |

- `hfq` 递减到**负** → 价格不可能为负 ⇒ **不是合法后复权价**
- `qfq` 与 `raw` **逐值完全相同** ⇒ 该接口的复权参数**未生效**，`hfq` 走的是另一条有缺陷的路径

⇒ 这**推翻**了 `stock_daily_rebuild.py` 的「整只票单源 ⇒ 因子序列内部自洽」假设，也是 **TENCENT 源 587 行**的根因。
⇒ 更重要的是：取证报告 §八 建议 3 的风险①（「用因子反推 pct 只是把一个错换成另一个错」）**成立**
→ **全量重算被否决**。

**因此 v4 的实际处置是「防未来 + 修可确证」，而不是「全量重算」**：

| 动作 | 内容 | 验收 |
|---|---|---|
| 代码护栏 | hfq 含负价 → **整只票弃用**（判据用 `< 0` 而非 `<= 0`，避免误伤「有停牌日（hfq=0）」的正常票）；`ret` 加 `pair_ok` 掩码，坏点相邻对落 NULL | 合成单测 **3/3 PASS**：正常票不误伤 / 负价票降级 / 单点停牌只污染相邻两行 |
| 数据修正 | 只修**物理不可能且因子未变**的行 = **207 行**（**63** + **144**，见取证报告 §10.3 / §10.3b） | `+4900% → -9.68%`、`-4100% → -9.09%`；三列残留 **0 行**；全库 `\|pct\|>31` 4,721 → **4,635**；备份 `dq_pct_fix_backup_20260922`（207 行） |
| 清单落库 | `dq_pct_anomaly_detail` 4,721 行 + CSV | 三档判定 `confirmed_dirty` 92 / `possible_dirty` 241 / `possible_legal` 4,388 |

> 📌 **7.4 的一条方法论**：**偏差分档能自证「真错 vs 噪声」的分界**。实测 **1%~5% 档完全空白**
> （>5% 有 63 行、≤1% 有 270 行），双峰分布天然给出阈值，比「拍一个阈值」可靠得多。

### 7.5 🔴 v5 新发现：`close ≤ 0` 的全史 4,152 行——同一个切片盲区，藏了第二类缺陷

**发现路径**：T+1 复核 v4 的 207 行修正时，发现其中 121 行仍 `|pct|>31`。
先排除「被覆盖」（`update_time` 与备份时刻同刻，见 §五 #25），再按 `close` 分层，
于是暴露出**与 `pct` 完全无关的一整类缺陷**。

**规模（全库实测）**：

| 缺陷 | 行数 | 说明 |
|---|---|---|
| `close < 0` | **3,947** | 值域 −13.750 ~ −0.010；`pre_close` **全部为 NULL**；AKSHARE 3,851 / TENCENT 96；前缀 001(2,606) 920(610) 601(405) 000(184) 600(142)；年份 **1991 ~ 2021** |
| `close = 0` | **184** | **全部** `920xxx` + **SINA** + 2018~2020；`O=H=L=C=0` 而 `volume`/`amount` 有效 |
| `close` 为空 | **21** | 920(16) / 主板(5) |
| **合计** | **4,152** | 清单表 `dq_close_nonpositive_detail` + CSV `docs/close_nonpositive_detail_2026-09-23.csv` |

**为什么规则没抓到（两层原因，都必须记住）**：

1. `daily_value_bounds` 的 where **字面确实有** `close<=0` —— 但它带切片谓词，
   只判最新一个交易日（§7.1 同一个病灶）⇒ 全史 4,152 行**从未被扫**。
2. 唯一的全史同类规则 `daily_pct_limit_rows`（按板块上限 10/20/30% 判）**抓不到** `close<0` 那 3,947 行 ——
   它们的 `change_pct` 都在 ±5% 量级，离板块上限很远。
   ⇒ **「有一条全史规则在守价格」是错觉**。

**`close = 0` 的一手指纹（SINA 解析丢弃价格字段）**：

```
920925 2020-11-16  O=0 H=0 L=0 C=0  pre=19.400  vol=333,334   amt=5,000,010.00
920077 2020-10-29  O=0 H=0 L=0 C=0  pre=6.660   vol=7,237,762 amt=38,939,160.00
```

**OHLC 全 0 但量额有效** ⇒ 不是「无成交」，是解析把价格丢成了 0。
且 `amount ÷ volume` 都能得到合理正价（上面第一条 = **15.0000** 整）⇒ 这 184 行**可修**。

**⚠️ 该缺陷与 v4 的修正有交叉，必须声明**：v4「批次2」144 行里有 **115 行正是这批 `close=0` 行**。
当时的判据（`pre_close IS NULL AND change_pct ≤ -100 AND same_factor = 1`）只填上了 `pre_close`，
`change_pct` 由 `(0 − pre_close)/pre_close` 重算后**仍是 −100%**。
⇒ **v4 的 `-100%` 不是新错，但也不是修好**：它是「列间自洽的源缺陷」。此结论已回写取证报告 §十一。

**v5 独立判据（与 `pct` 正交，可直接复用）**：

```sql
-- 全史 close 非正 / 为空（4,152 行）
SELECT COUNT(*) FROM stock_market_daily WHERE close IS NULL OR close <= 0;
-- 拆两类（互不重叠）
SELECT SUM(close < 0), SUM(close = 0), SUM(close IS NULL) FROM stock_market_daily;
```

> 📌 **7.5 的一条方法论**：**复核「修复效果」时必须按「被修字段的上游取值」分层，不能只看「修复后是否还有异常值」**。
> 本次若只跑「207 行里 |pct| 是否归零」，会得出「还剩 121 行没修好 → 修复失败」；
> 若只跑「恒等式是否成立」，会得出「0 违反 → 全修好」。
> **两个结论都错** —— 真相要靠 `close` 这一层才看得见。
> 同类陷阱：复核 SQL 里 `ON d.trade_date = d.trade_date` 是**自比较、恒真**，
> 会静默产生笛卡尔积（实测把 63 行放大成 264,506 行），必须写 `d.trade_date = b.trade_date`。
