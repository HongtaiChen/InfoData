## 二、问题起源：`daily_factor_link` 的 1,000 行

该规则断言（数学恒等）：

```
pre_close(t) = close(t-1) × adj_factor(t-1) / adj_factor(t)
```

实测 `偏差 > 0.5%` 的行数**恒为 1,000**，自规则建立起从未 pass 过。历史定性两次：

| 版本 | 定性 | 实测检验 |
|---|---|---|
| 09-20 | 「口径未知的空因子区被误报」→ 已修（LAG 窗口不再过滤） | 修正后仍 1,000 行，**否定** |
| 09-20/21 | 「低价股 + 2 位小数源的舍入退化」 | 见 §三，**不足** |
| 09-22 早前 | 「缩股/重整造成价格跳变而因子未跟随」 | 见 §三，**否定** |

## 三、对旧定性的两次推翻（实测）

### 3.1 不是舍入：偏差是**量级级**

偏差最大的 15 行（全史窗口查询实测）：

```
600870 2018-10-26 dev=5872.7%  pre=124.830  prev_close=2.090  f=0.34070796  prev_f=0.34070796  src=TENCENT
600870 2009-03-04 dev= 907.8%  pre= 20.962  prev_close=2.080  f=0.38766520  prev_f=0.38766520  src=TENCENT
600870 2009-03-10 dev= 623.2%  pre= 15.260  prev_close=2.110  f=0.14414414  prev_f=0.14414414  src=TENCENT
000606 2023-06-30 dev= 187.0%  pre=  0.660  prev_close=0.230  f=0.12000000  prev_f=0.12000000  src=TENCENT
...
```

两处关键事实：
1. **`f == prev_f`（相邻两行因子完全相同）** ⇒ 期间**无除权事件**，则 `pre_close(t)` **在数学上必须等于** `close(t-1)`。
   而 `600870 2018-10-26`：`pre_close=124.830` vs `close(t-1)=2.090` —— 差 59.7 倍。
2. 分布为**弥散型**（95 只票各只 1 行），排除了「某段因子切错」。

⇒ 无论怎么解释因子，都推不出这个值。**「舍入」与「缩股/重整」两种定性都不成立。**

### 3.2 是**两列同时**错，且互相自洽

关键反直觉点：**`daily_change_link`（全史、`max_count=0`）是 pass 的**。它的判据是

```
|close − pre_close × (1 + change_pct/100)| ≤ 存储精度上界
```

pass 意味着 `change_pct` 与 `pre_close` **严丝合缝地互相印证**。
**这曾被误读为「说明数据没问题」——恰恰相反：它说明这两列同源，错也一起错。**

实测佐证（`600811`，2025 年数据、非老数据）：

```
2025-04-09  close=0.410  pre_close=NULL    chg= -102.38%   f=0.97674419
2025-04-10  close=0.390  pre_close=0.009   chg=+4200.00%   f=0.97674419
```

`0.390 / (1 + 42.0) = 0.00907 ≈ 0.009` ✅ 恒等式成立。
`close` 从 0.410 平滑到 0.390（-4.9%），**而 `chg` 写着 +4200%**。

## 四、真因：派生逻辑（含决定性指纹）

`app/collectors/stock_daily_core.py`（L311–L326）：

```python
ret[1:] = hc[1:] / hc[:-1] - 1        # hc = 源「后复权(hfq)」序列的 close
...
with np.errstate(divide="ignore", invalid="ignore"):
    pre = np.where(np.isfinite(ret) & (ret > -1), c / (1.0 + ret), np.nan)   # c = 不复权实际价
    chg = c - pre
    pct = np.where(np.isfinite(ret), ret * 100.0, np.nan)
...
num(pre[i], 3), num(chg[i], 3), num(pct[i], 4)
```

即三列的关系被**构造性绑定**：

```
change_pct = ret × 100
pre_close  = close / (1 + ret)          （且 ret ≤ −1 时强制写 NULL）
change_amount = close − pre_close
```

### 4.1 决定性指纹：307 / 307

代码里 `ret > -1` 这个护栏会在 `ret ≤ −1`（即 `change_pct ≤ −100%`）时把 `pre_close` 写成 `NULL`，
**但 `change_pct` 照写**。全库实测：

| 查询 | 结果 |
|---|---|
| `change_pct <= -100` 的行数 | **307** |
| └ 其中 `pre_close IS NULL` | **307** |
| └ 其中 `pre_close IS NOT NULL`（反例） | **0** |

**307/307 命中、零反例。** 没有任何自然数据分布能造出这个模式 —— 它只能是该行代码路径的产物。
这是本报告的**核心证据**：同时证明了「`pre_close`/`change_pct` 由 `ret` 派生」与「`ret` 的值在这些行上失真」。

### 4.2 失真呈固定三日形态

4 只票各自窗口全部呈现同一形态（**「巨负（pre 置 NULL）→ 巨正 → 回落」**）：

```
600811  2025-04-09  chg= -102.38%  pre=NULL      ← 塌陷
        2025-04-10  chg=+4200.00%  pre=0.009     ← 暴涨（比值分母被压小）
        2025-04-11  chg=  +97.67%  pre=0.187     ← 逐日衰减回归

600747  2019-11-05  chg= -102.08%  pre=NULL
        2019-11-06  chg=+4900.00%  pre=0.006
        2019-11-07  chg= +100.00%  pre=0.125

600634  2021-06-10  chg=-4100.00%  pre=NULL
        2021-06-11  chg= +102.50%  pre=0.178
        （前一日 06-09 还有 chg=-98.08% / pre=22.880）

600870  2018-10-26  chg= -98.25%   pre=124.830
        2018-10-30  chg=-1700.00%  pre=NULL
```

⇒ 这是**源的后复权（hfq）序列在个别日期出现阶跃**的典型特征：
一次阶跃会在「逐日比值」上同时产生**前一日塌陷**与**后一日暴涨**两端，随后逐日衰减回归。
而 `close` 全程平滑 —— 因为 `close` 取自**不复权序列**，是另一条源序列。

> ⚠️ 未做的一步（诚实标注）：**未回源复核** `hfq` 原始响应。600811 的 2025-04 数据理论上仍可复抓，
> 但 akshare 的 hfq 接口在本机有挂死史（需多进程 + 30s 硬超时）。**「hfq 阶跃」是从库内三列关系推出的，
> 已具唯一性（307/307 + 三日形态），但「源侧哪一步产生阶跃」尚未直接观测到。**

## 六、为什么长期没被发现：`daily_value_bounds` 的全史盲区

`dq_rules` 里 `daily_value_bounds` 的描述是：
> 「脏值拦截：close≤0 / 量为负 / **|涨跌幅|>31%**」

听起来是全表约束。但检查器 `_violation_count` 的 SQL 是：

```sql
SELECT COUNT(*) FROM `表`
WHERE `trade_date` = (SELECT MAX(`trade_date`) FROM `表`) AND (close<=0 OR ... OR ABS(change_pct)>31)
```

**只判定「最新一个交易日」的切片**（这是 daily 组「最新切片类、秒级」的设计使然，本身合理），
所以全史 1,850 万行的这类脏值**从未被它覆盖**。真正的全史判据在 weekly 组
（`daily_pct_limit_rows` / `daily_factor_link` / `daily_ohlc_consistent`），
而前者按「板块上限」计数（16,491 行）、把成因写成「低价舍入」，后者的 1,000 行被疑为「因子问题」——
**两处都在，却都没指向 `pre_close` 列本身。**

⇒ 结论：**「规则存在」不等于「口径覆盖」，读规则必须先确认检查器是切片还是全史。**
（`violation_count` / `null_rate_slice` / `row_count_slice` / `freshness_daily` 都是**最新切片**；
`where_count` / `gap_scan` / `factor_link` / `pct_limit` 是**全史**。见 `investbuddy-dq-audit` 技能。）

## 八、处置建议（🧭 涉及口径取舍，**未擅自动手**）

### 建议 1（低风险，推荐先做）：修 `daily_value_bounds` 的描述，标注实际口径
把它的 `description` 从「脏值拦截…」改为明确写「**最新日切片**」，
并注明「全史同类判据见 `daily_pct_limit_rows` / `daily_factor_link`，见取证报告」。
**成本极低，收益是让后续审计不再误信这条规则的覆盖面。**

### 建议 2（可选）：补一条**全史**「无除权却跳变」规则
判据：`adj_factor == LAG(adj_factor)` 且 `|pre_close − LAG(close)| / LAG(close) > 50%`，
当前实测 **333 行**（受涨跌停约束域 202 行），按项目**上账**策略设 `max_count=333`。
**注意**：它与 `daily_factor_link`（`>0.5%` 阈值、1,000 行）**高度重叠**，
价值仅在于「去掉舍入噪声、只留下可确证错」——**故我倾向不新增，而是订正 `factor_link` 的定性**（本次已做）。

### 建议 3（🧭 数据手术，需明确授权）：重算 `pre_close` / `change_pct` / `change_amount`
**关键技术事实：可以不回源重算。** 因为三列的正确值可由库内列唯一确定：

```
ret_true(t)     = close(t) × adj_factor(t-1) / (close(t-1) × adj_factor(t)) − 1
pre_close_true  = close(t) / (1 + ret_true)
change_pct_true = ret_true × 100
```

- **优点**：无需外部源（避免 akshare 挂死风险）；可精确限定在受影响行（`|pct|>31%` 的 4,721 行或其子集），不动其余 1,850 万行。
- **风险**：① 这等于用**因子体系**去覆盖 `pct` 列，而因子本身也源自同一条有阶跃的 hfq 序列
  → **可能只是把一个错换成另一个错**，需先抽样人工核对；② 会让 `daily_change_link` 恒成立（**失去独立性**，
  该规则从此不再能发现 pct 问题）；③ 改动 1,850 万行大表需事务 + 备份。
- **前置条件（建议）**：先回源复核 3–5 只票的 hfq 原始响应，确认阶跃出在源侧哪一步；
  若确认是源侧坏点，则**更稳的做法是重抓那几只票的 hfq 并重建其因子**，而不是用因子反推 pct。

### 建议 4：把 4,721 行按「可确证错 / 可能合法」落成一份**行级清单**
（`dq_gap_detail` 同款形态的新表或 CSV），供人工抽查与后续修复对账。当前仅做了**分域计数**。

### 10.2 代码护栏（防未来污染，已落地）

`app/collectors/stock_daily_core.py` 的 `derive_rows`：

1. **hfq 口径体检**：hfq 序列中只要出现**负价**，即**整只票弃用 hfq**（`hfq_has_negative`）→
