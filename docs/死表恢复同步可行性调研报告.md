# 死表恢复同步可行性调研报告

> 调研日期：2026-09-13 ｜ 范围：v2.0 普查确认的 10 张「无采集器」历史导入表
> 实测环境：akshare 1.18.94 / pandas 3.0.5 / MySQL adata ｜ 方法：真实接口调用 + 字段级映射比对（不写库）

---

## 一、为什么这 10 张表没有定期同步

三条原因叠加，**不是"配了任务但跑失败"，而是"从来没有任务"**：

### 1. 结构性：导入脚本从未纳入采集器体系
`app/collectors/` 下 17 个采集器对这批表的引用数为 **0**（代码扫描仅命中 `docs/` 与 `seed_dq_rules.py` 的规则文本）。
`task_runs` 表 251 条运行记录里，**不存在任何一个写这些表的任务**。

### 2. 数据源已从环境中消失
本地 `data_source` 标记为 `ADATA` / `AUDATA`（**不是** AKSHARE），而 `adata` 库**当前未安装**。
项目后续把采集统一收口到 akshare，但只补齐了新体系（行情/概念/指数/资讯/日历），这批更早"从外部一次性导入"的业务表被遗漏。

### 3. 缺口被"冻结监护"掩盖
09-13 的 DQ 补规则只给了"防清空"级保护（`row_count_*` 阈值），**没有配 freshness 规则**——因此表停更一年也不会在体检里报警，长期静默。

### 直接后果（可见的）
- `ths_stock_dividend` → 被 `app/analysis/dividend.py` 消费 → 前端 `AnalysisView` 的**「股息率排行」Tab 展示的是一年前的数据**
  - 实证：600519 本地最新只到「2024年报」，源已有「2025三季报 / 2025年报 / 2026中报」三期
- `stock_jgdy_detail` → 本地停在 2025-09-19，源已到 2026-09-11

## 三、关键实证细节

### 3.1 `ths_stock_dividend` ← `stock_fhps_detail_ths`（11/11 完全对齐）

映射关系（源 → 本地）：

| 源列 | 本地列 |
|---|---|
| 报告期 | `report_period` |
| 董事会日期 | `board_date` |
| 股东大会预案公告日期 | `shareholders_meeting_date` |
| 实施公告日 | `implementation_date` |
| 分红方案说明 | `dividend_plan_desc` |
| A股股权登记日 | `ashare_record_date` |
| A股除权除息日 | `ashare_ex_date` |
| 分红总额 | `dividend_amount_total` |
| 方案进度 | `plan_progress` |
| 股利支付率 | `dividend_payout_ratio` |
| 税前分红率 | `pre_tax_dividend_ratio` |

同源验证（600519 / 2024年报）：本地 `ashare_ex_date=2025-06-26, pre_tax_dividend_ratio=1.93%`，源完全一致 → **确认为同花顺同一数据源，可直接增量补齐**。

> 坑：源数据含 `'--'` 与 `NaT`（如"不分配不转增"），入库前须清洗为空值。

### 3.2 `securities_margin` — 单位不一致

| 源 | 单位 | 处理 |
|---|---|---|
| `stock_margin_sse` | **元** | 直接使用 |
| `stock_margin_szse` | **亿元** | **× 1e8** |

且本地是沪深**合计**口径（`rzye`=2.38e12），需按 `trade_date` 两市求和。
`rzrqyecz` 字段含义待业务确认（本地值与 `rzrqye` 存在固定差额）。

> 另：`stock_margin_szse` 当日数据 T+1 才发布，直查当日返回空表，需按交易日回溯。

### 3.3 `stock_market_daily_ex` — 冗余副本（重要）

同日同股比对，`open/high/low/close/volume/amount` **逐字段完全相同**：

| 表 | 000001@2025-09-19 | 600519@2025-09-19 |
|---|---|---|
| `stock_market_daily` | O11.410 H11.510 L11.370 C11.450 V834651 | O1467.990 C1467.970 V32637 |
| `stock_market_daily_ex` | 完全相同 | 完全相同 |

行数 1625 万 / **3197MB**。`data_source` 同为 AKSHARE，仅导入时间不同。
→ **建议核对差集后归档**，释放约 3.2GB；无需为其开发采集器。

### 3.4 akshare 已知坑

- `stock_report_fund_hold` **列名与实际数据错位**（`股票代码` 列返回的是市值数字，`股票简称` 列返回的是代码）→ 必须按位置解析，不能按列名取值
- `futures_symbol_mark()` 返回的是「中文名 → 拼音」，**无法**用于 `futures_spot_price_daily` 的字母代码（C/A/M）→ 品种中文名映射需自建（约 54 个品种，一次性）
- `futures_spot_price_daily` 不提供 `main_basis_high/low/avg_180d`（本地表的 3 个派生列）→ 需本地按 180 日窗口自行计算
- 重跑采集前注意：8 张表缺唯一索引（`stock_capital_flow` / `securities_margin` 等可安全补 DDL；`ths_stock_dividend` 有 9.5 万重复行，需先定业务粒度）

## 四、环境限制说明（重要）

东财行情域名 `push2*.eastmoney.com` 在**当前调研环境**不可达：

- 裸 TCP 可连、TLS 握手成功，但服务端**主动断开并返回空响应**（非纯网络不通，是出口 IP 风控）
- 对照组正常：东财 `datacenter-web` / 深交所 / 上交所 / 同花顺 / 中证指数 / 巨潮 / 新浪 均 HTTP 200
- 生产侧佐证：`stock_daily_incr` 最近成功于 2026-09-11 20:44，且 historical errors 中已出现 `tencent` 降级记录 → 说明项目已具备双源容错，但东财本身在生产也存在间歇性失败

**结论**：表格中 4/8 号表的「东财依赖」判断需要在真实部署环境复测；其余接口结论不受影响。

## 五、建议落地路径

### 第 1 批（P0 · 修复可见功能）
`ths_stock_dividend` 增量采集器 —— 修复前端「股息率排行」一年未更新的问题。
建议策略：按 `stock_info` 在册名单逐股拉取（`stock_fhps_detail_ths`），只写 `report_period` 未入库的新期；月度 cron。

### 第 2 批（P1 · 性价比最高）
`securities_margin` + `stock_jgdy_detail` —— 两者均为日频全市场接口，单轮调用 1~2 次，成本极低。
可复用现有采集器模式（`RUN_STEPS` + `with_steps` + `task_config` cron + `TaskRecorder`）。

### 第 3 批（P2 · 中等成本）
`futures_spot_price`（需自建品种名映射 + 派生列计算）、`stock_industry_sw`（162 次月更）

### 第 4 批（P3 · 按需，逐股型成本高）
`stock_financial_abstract_ths` / `stock_capital_flow` / `stock_shares`（各约 5134 次/轮）
建议先做限流与断点续传，或只覆盖重点股票池。

### 独立事项
`stock_market_daily_ex` 归档（核对与 daily 差集 → 无独有数据则删除/转冷备）。

### 收口建议
1. 每张表恢复后**同步补 DQ freshness 规则**，避免再次静默停更
2. 更新 `docs/design/数据体系设计规范.md`（v2.0 → v2.1）的「G5 历史死表」风险条目
3. 新建采集器统一走 `seed_table_meta.py` 登记 writers，保证前端「数据流卡」能看到归属
