# 调度可靠性优化方案

> 2026-09-17 · 面向「家用电脑频繁待机」场景的采集调度加固方案
> 状态：**待评审，未落地**（本文档不含任何已执行的代码/配置改动）

---

## 0. 摘要

当前调度失效的根因不是调度器写错了，而是**三层缺陷叠加**：

1. 电源策略让机器每天有 18~19 小时处于 S3 待机（进程冻结）；
2. 调度器缺少「从睡眠恢复」的感知，补偿逻辑只在进程重启时触发一次；
3. `misfire_grace_time=3600` 会把睡眠超过 1 小时的过期班次**静默丢弃**。

实测后果：`news_fetch` 漏跑 26.9%，17:00 档任务命中率仅 21%，凌晨 3 点档与上午 8~10 点档命中率 **0%**。
但**核心日线数据未丢失**（9/01–9/16 每交易日 5119~5128 只，完整）。

**推荐路径**：不追求 7×24 常开，而是把「必须在线的时段」压缩进用户本就在用的 18:00–23:00 窗口，
再用唤醒补偿兜底。即 **L1（电源）+ L2（看门狗）+ L4（排期收敛）**，零成本，无需上云。

## 2. 根因分析

### 2.1 物理层：S3 待机冻结进程

当前电源方案为「平衡」：

| 设置 | 交流（插电） | 直流（电池） |
|---|---|---|
| 在此时间后睡眠 `STANDBYIDLE` | **1800 秒（30 分钟）** | 600 秒（10 分钟） |
| 在此时间后休眠 `HIBERNATEIDLE` | 1800 秒（休眠未启用） | 0 |
| 允许使用唤醒定时器 `RTCWAKE` | **启用** | 禁用 |

本机支持的是 **S3 传统待机**（`powercfg /a` 确认，无 S0 低电量待机、无休眠）。
S3 下 CPU 完全停摆、内存维持供电、网络断开——**进程被冻结，定时器不可能触发**。

好消息：**插电状态下唤醒定时器已启用**，这意味着可以配置 RTC 定时唤醒（见 §3.1 方案 B）。

### 2.2 感知层：唤醒后不触发补偿

`backend/app/scheduler.py` 中，`catchup_missed()`（启动补偿）**只在 `start()` 里被调用一次**：

```python
def start(self):
    ...
    self.reap_orphan_runs()   # 启动自愈
    self.sync_from_db()
    self.catchup_missed()     # ← 仅此处调用
```

而睡眠唤醒时进程并未重启，`start()` 不会再次执行——**补偿逻辑在「睡眠」这条路径上完全失效**。
目前只有「关机后重新开机 / 手动重启服务」能触发补偿。

### 2.3 容错层：过期班次被静默丢弃

`sync_from_db()` 注册 job 时的参数（`scheduler.py:274-277`）：

```python
coalesce=True,            # 错过多次只补跑一次
max_instances=1,          # 同任务不并发
misfire_grace_time=3600,  # 错过 1 小时内仍补跑
```

APScheduler 的处理逻辑：唤醒后 `_process_jobs` 以**墙钟**计算 `now`，此时 job 的所有触发点都落在过去；
`coalesce=True` 保留最后一个触发点；随后判断 `now - run_times[0] > misfire_grace_time` ——
**超时即丢弃，连日志都不留**。

因此实际命运矩阵为：

| 情形 | 现状行为 |
|---|---|
| 睡眠 < 1 小时 | APScheduler 补跑一次 ✅ |
| **睡眠 1 ~ 18 小时** | **静默丢弃** ❌（这是主要缺口） |
| 进程重启 / 关机再开机 | `catchup_missed()` 补最近一个未覆盖班次 ✅ |
| 连续多天不在线 | 只补最近一班，不逐天堆积（设计如此，可接受） |

### 2.4 结构性错配

见 §1.3：排期跨度 20 小时 vs 实际在线 5~6 小时。

## 3. 优化方案

### L1 · 电源策略

#### 方案 A：取消自动睡眠（最简单）

```bash
powercfg /change standby-timeout-ac 0      # 插电永不自动睡眠
powercfg /change hibernate-timeout-ac 0    # 插电永不休眠
powercfg /change monitor-timeout-ac 10     # 显示器照常 10 分钟关闭（省电大头，不影响任务）
```

优点：零代码、彻底。缺点：机器长期空转（电费、噪音、硬件磨损），不符合家用电脑使用习惯。

#### 方案 B：保留睡眠 + RTC 定时唤醒（推荐用于家用电脑）

唤醒定时器已启用，只需注册一个「唤醒型计划任务」：

```powershell
$action  = New-ScheduledTaskAction -Execute "cmd.exe" -Argument "/c exit"
$trigger = New-ScheduledTaskTrigger -Weekly -DaysOfWeek Monday,Tuesday,Wednesday,Thursday,Friday -At 16:50
$settings = New-ScheduledTaskSettingsSet -WakeToRun -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries
Register-ScheduledTask -TaskName "InvestBuddy-Wake" -Action $action -Trigger $trigger -Settings $settings
```

关键参数是 `-WakeToRun`，对应任务计划程序里的「唤醒计算机运行此任务」。
（`schtasks /create` 命令行不直接支持该参数，需用 PowerShell 或导入 XML 模板。）

若要在电池模式下也能唤醒，还需显式开启：

```bash
powercfg /setdcvalueindex SCHEME_CURRENT SUB_SLEEP RTCWAKE 1
powercfg /setactive SCHEME_CURRENT
```

#### 方案 C：唤醒 → 跑批 → 自动回睡（可选增强）

在上述基础上，增加一个「收尾任务」：当日批次全部完成后主动睡眠，避免跑完空转到超时。

```bash
rundll32.exe powrprof.dll,SetSuspendState 0,1,0
```

⚠️ 该命令需确认已关闭休眠（`powercfg /h off`），否则会变成休眠而非睡眠。

### L2 · 唤醒检测看门狗（**最关键**）

#### 设计思路

不依赖 APScheduler 自身的 misfire 处理，而是加一个高频心跳 job，通过**检测墙钟跳跃**判定「刚从挂起恢复」：

```
心跳每 2 分钟一次 → 记录 _last_tick 墙钟
若 (now - _last_tick) > 300 秒 → 说明期间进程被冻结（睡眠）→ 触发 sync_from_db() + catchup_missed()
```

该判定对 APScheduler 内部实现不敏感，鲁棒且幂等（`catchup_missed` 本身有防重逻辑，且执行走 `_execute` 的 running 保护）。

#### 代码草案（仅供参考，未实施）

```python
class SchedulerManager:
    SLEEP_DETECT_SECONDS = 300        # 心跳间隔 120s，超过 300s 视为挂起恢复
    WATCHDOG_JOB_ID = "_watchdog"

    def start(self):
        ...
        self._last_tick = datetime.now(TZ)
        self._scheduler.add_job(
            self._watchdog_tick,
            CronTrigger.from_crontab("*/2 * * * *"),
            id=self.WATCHDOG_JOB_ID,
            coalesce=True, max_instances=1,
            misfire_grace_time=None,      # 看门狗自身永不丢弃
            replace_existing=True,
        )
        self.sync_from_db()
        ...

    def _watchdog_tick(self):
        now = datetime.now(TZ)
        gap = (now - self._last_tick).total_seconds()
        self._last_tick = now
        if gap <= self.SLEEP_DETECT_SECONDS:
            return
        logger.warning(f"⏰ 检测到系统挂起 {gap / 3600:.1f} 小时，触发唤醒补偿")
        try:
            self.sync_from_db()
            self.catchup_missed()
        except Exception:
            logger.exception("唤醒补偿异常")
```

#### ⚠️ 落地陷阱（必须处理）

`sync_from_db()` 末尾的清理循环会**删除所有不在 `task_config` 中的 job**：

```python
for job_id in [j.id for j in self._scheduler.get_jobs()]:
    if job_id not in want:
        self._scheduler.remove_job(job_id)     # ← _watchdog 会被误删
```

而 `sync_from_db()` 正是唤醒补偿的第一步，会导致**看门狗自杀**。必须加白名单：

```python
if job_id not in want and not job_id.startswith("_"):
    self._scheduler.remove_job(job_id)
```

#### 为什么不用「直接放开 misfire_grace_time」

把 `misfire_grace_time` 改大或设为 `None` 看似更简单，但唤醒瞬间所有累积 job 会同时到期，
一起提交给 APScheduler 的 `ThreadPoolExecutor`（默认 10 线程）→ **并发风暴**：
多个 akshare 采集器同时抢数据库连接、同时打数据源接口，反而更容易触发限流与失败。

「看门狗 + 串行 catchup」优于「放开 grace time」，因为补偿时机和并发度都可控。

---

### L3 · `misfire_grace_time` 调整

若采纳 L2，本项可作为辅助：

| 现值 | 建议 | 理由 |
|---|---|---|
| `3600` | `21600`（6 小时） | 让晚间未开机时段的班次在次日开机后仍可被 APScheduler 补一次 |

不建议设为 `None`（理由见 §3.2）。真正的补偿交给 L2 的串行 catchup。

| `daily_recon_sample` | 10:00 周六 | 15:00 周六 | 同上 |

| `stock_company_sync` | 17:30 每日 | 19:25 每日 | 无下游依赖 |
| `finance_calendar_sync` | 17:45 每日 | 19:35 每日 | 无下游依赖 |

#### ⚠️ 存在依赖约束的任务

**`stock_info_sync`（17:00）不能被简单后移**。实测确认：

```
backend/app/collectors/stock_daily_incr.py:46
RUN_STEPS = [
    {"no": 1, "name": "读候选名单", "params": "stock_info 在市 A 股，可含北交所"},
    ...
```

日线采集的**候选股票池直接取自 `stock_info` 表**（`stock_daily_incr.py:191`）。
因此 `stock_info_sync` 必须早于 `stock_daily_incr`(19:00)。但它偏偏排在 17:00，
而用户 17:00 在线的天数不到一半（实测命中率 3/14）。

**建议改法（不是挪时刻，而是改机制）**：在 `stock_daily_incr` 开跑前强制刷新一次 `stock_info`，
即把「定时前置」改为「运行时前置」。这样无论几点开机，顺序都能保证。
代价是日线任务耗时增加（`stock_info_sync` 常态 1~2 分钟），可接受。

替代的轻量做法：把 `stock_info_sync` 挪到 18:00，并在 L2 看门狗里额外加一条
「日线开跑前若 stock_info 当日未更新则先刷新」的保护。

#### `margin_sync`（09:00，命中率 0）

两融为 T+1 数据（`freshness_daily` 规则已有 `grace_days` 兜底），不存在「必须 9 点采」的硬约束。
建议挪到 **20:00 之后**，但**需先实测确认当日两融数据的发布时间点**——若交易所当晚才发布，
挪到 20:00 会采到空数据，反而更差。**落地前必须先验证**。

### L5 · 采集器回看补采能力

`news_fetch` 的实现是**分页翻取最新快讯**（`max_pages=3 × page_size=50` ≈ 最新 150 条），
**不支持按时间窗回看**：

```python
# backend/app/collectors/news_fetch.py
EM_API = "https://np-listapi.eastmoney.com/comm/web/getFastNewsList"
RUN_STEPS = [
    {"no": 1, "name": "抓取东财快讯", "params": "np-listapi 分页翻取（sortEnd 游标，每源上限 max_pages 页）"},
    ...
]
```

因为每次抓的是「最新 150 条」滚动窗口，**单次漏跑 30 分钟通常能被下一次覆盖**；
但离线 18 小时后，中间时段的新闻就永久丢失了。

改进方向（中长期）：记录 `MAX(published_at)`，每次采集时若发现与当前时间存在缺口，
增大 `max_pages` 直到覆盖缺口（东财接口支持 `sortEnd` 游标翻页，具备可行性）。

## 4. 家用电脑场景：推荐组合

家用电脑不宜为采集任务 7×24 空转（电费、噪音、硬件磨损）。推荐：

| 层级 | 是否采纳 | 说明 |
|---|---|---|
| **L1 方案 B**（保留睡眠 + RTC 定时唤醒） | ✅ 采纳 | 16:50 自动唤醒，覆盖晚间批次 |
| **L2 看门狗** | ✅ **必须** | 兜底所有意外离线（含忘记开机、临时休眠） |
| **L3 grace_time → 6h** | ✅ 采纳 | 辅助兜底 |
| **L4 排期收敛** | ✅ 采纳 | 把 17 点档与凌晨档挪进 18:00–23:00 |
| **L5 回看补采** | ⏳ 择期 | 中长期改进 |

**预期效果**：机器日常照常睡眠，仅在需要时被唤醒；即使某天完全没开机，
次日开机也会自动补齐最近班次。相比现在的「每天漏 27% 新闻 + 17 点档命中率 21%」应有显著改善。

**保留的已知缺口**（属可接受范围）：

- 连续多天不开机时，只补最近一班，不逐天回溯；
- 23:00 之后的 `financial_abstract_sync` 若机器已睡，需靠唤醒定时器或次日补偿；
- 时效性数据（新闻、当日快照）在长离线后无法恢复。

## 5. 上云评估

### 5.1 成本对比

| 维度 | 本地优化后 | 云主机（轻量 2核4G/6M/70G SSD） |
|---|---|---|
| 年成本 | 电费约 250~350 元（若 24h 常开，按 50W × 0.6 元/度估） | **199 元/年**；3 年套餐 528 元 |
| 可靠性 | 仍受电源、网络、误操作影响 | 7×24 稳定 |
| 迁移成本 | 无 | 需重建环境 + 迁数据 |
| 外网访问 | 需内网穿透 | 自带公网 IP（80/443 需备案，用非标端口可绕过） |
| 主要风险 | 无 | **akshare 从数据中心 IP 采集可能被限流（未经实测验证）** |

值得注意：**若为了让电脑常开而放弃睡眠，本地电费反而可能高于云主机租金**。

### 5.2 数据迁移量

全库 **38 张表 / 8914 MB**：

| 表 | 行数 | 大小 |
|---|---|---|
| `stock_market_daily_ex` | 1625 万 | 3197 MB |
| `stock_market_daily` | 1622 万 | 3163 MB |
| `stock_market_daily_bak_20250802` | 1605 万 | 1905 MB |
| 其余 35 张表 | — | 约 650 MB |

瘦身后核心库约 **3.5~4 GB**，迁移成本不高。

### 5.3 上云前必须先验证的事

1. **数据源可达性**：在云主机上实测 `akshare` 各接口（东财 `push2his` 本机已不可达，
   依赖 `datacenter-web` 域；新浪/腾讯/中证的可用性），确认数据中心 IP 未被限流；
2. 采集并发是否会触发风控（云 IP 多为共享出口）；
3. MySQL 版本与字符集一致性；
4. 定时任务的时区设置（云主机默认 UTC，需显式设为 `Asia/Shanghai`）。

**结论**：上云能根治「机器不在线」，但引入「数据源可达性」这个新的未知数。
在第 1 项验证通过前，不建议直接迁。

## 6. 验证清单

落地后按以下顺序验证：

| # | 验证项 | 方法 | 通过标准 |
|---|---|---|---|
