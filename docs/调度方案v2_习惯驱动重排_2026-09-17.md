## 0. 一句话结论

你的在线窗口是**工作日 19:00–23:00（4 小时）+ 周末 08:00–23:00（15 小时）**，节假日可能连续数天离线。
经代码级核查：**这种作息不会造成核心数据丢失**——日线、物化表、快照都能在开机后一次性补齐缺口。

所以不需要上云，也不需要为跑任务让电脑常开。真正要做的只有两件事：

1. **把排期收进你的窗口**（当前排期跨度 3:00–23:00，是最主要的错配）；
2. **把「固定时刻驱动」换成「依赖完成驱动」**，让下游任务在日线跑完后自动接力，
   而不是赌一个固定时刻（今天 9/17 20:05 就赌输了，见 §3.3）。

## 1. 你的使用习惯模型

| 场景 | 在线窗口 | 时长 | 可容纳的排期密度 |
|---|---|---|---|
| 工作日（周一~周五） | **19:00 – 23:00** | 4 小时 | 紧凑，只放主链 + 紧邻任务 |
| 周末（周六、周日） | **08:00 – 23:00** | 15 小时 | 宽松，可放重任务与全量重扫 |
| 节假日 | **不确定**，可能连续数天 0 小时 | — | 不能排任何"必须当天跑"的任务，只能靠开机补偿 |

对比现状：**当前任务时段跨度是 3:00 – 23:00，共 20 小时**——排期隐含假设了「机器常开」，
与你的实际作息是两套时间表（详见 v1 文档 §1）。

### 1.1 一个必须澄清的认知

「工作日只有 4 小时在线」听起来很紧张，但**实际主链只需 90~140 分钟**（实测，见 §2.3），
4 小时窗口是够的——只要**排期不把任务摊到凌晨和白天的空档里**。

这决定了「离线几天」是致命伤还是小麻烦。逐表核查结果（附代码依据）：

### 2.1 可回补性矩阵

### 2.2 结论

> **「节假日好几天不开机」对采集数据而言是安全的**：开机后主链跑一次，日线与物化表自动补齐全部缺口。
> 唯一会丢的是新闻，且可以用一次改造（回看补采）解决。

这一点直接否定了「必须上云才能保证数据完整」的假设。

### 2.4 一个被忽视的真相：失败 ≠ 任务有问题

近 60 天失败率看起来吓人（日线 50%、`stock_status_sync` 43%），但错因几乎全是：

```
[启动自愈] 进程重启中断，已自动标记为 failed（非任务本身失败）
进程重启中断，已由运维脚本标记为 failed（非任务本身失败）
```

即**任务跑到一半时你关机了**——这不是缺陷，而是「任务时长」与「在线窗口」的错配。
把它排进 4 小时窗口、并让长任务支持断点续跑，失败率会自然下降。

## 3. 排期重排方案

### 3.1 设计原则

1. **所有时刻落在 19:00–23:00 内**（这样无论那天是工作日还是周末都在线）；
2. **依赖驱动优先**：有前后依赖的任务用「链式触发」接力，固定时刻只作兜底；
3. **重任务放周末**：非时效性重任务尽量避开工作日的 4 小时窗口；
4. **月度任务允许中断**：逐股型任务天然续跑，允许跨过 23:00。

> ⚠️ 星期语义：本项目的 `day_of_week` 是 **0=周一 … 6=周日**（APScheduler 口径，与 Unix crontab 相反）。
> 下文 `0-4` = 周一至周五，`5,6` = 周六、周日。

### 3.2 每日任务（不分工作日/周末，统一进晚间窗口）

**为什么必须有链式触发——今天（9/17）的活证据：**

```
19:43:53  stock_daily_incr   running（至今未完成）
20:05:00  market_style_sync  success  写入 5254 行
```

物化表在日线还没跑完时就执行了。`_safe_max_date()` 护栏把计算上界退回上一交易日 9/16，
**它成功写出了 9/16 的数据（覆盖原有值），但 9/17 的数据要等下一次运行**——
一次运行被白白浪费，前端看到的仍是昨天的数据。

护栏保住了「不写半量数据」（这是对的），但它保不住「及时性」。
只要触发时机仍是固定时刻，这个浪费就会在每个交易日重演。

## 4. 补跑机制（覆盖「睡眠」与「数天离线」两种场景）

现状只有一条补偿路径：**进程重启时** `start()` 调一次 `catchup_missed()`。
睡眠唤醒（进程还活着）完全不触发；`misfire_grace_time=3600` 还会把超 1 小时的班次静默丢弃。

四层补跑设计（**L1、L2 是必需的，L3 是增强，L4 是唯一的数据补救**）：

### 4.1 补跑层 1 · 开机补偿增强（覆盖「关机数天」）

现有 `catchup_missed()` 逻辑本身是对的（只补最近一个未覆盖班次，不逐天堆积），
配合 §2.1 的「一次跑即补齐」特性，**足以覆盖多天离线**。需要补两点：

1. **优先级排序**：当前 `_run_catchup()` 严格串行（`scheduler.py:412`），
   若第一个补跑的是长任务（如曾出现过 11 h 的 `financial_abstract_sync`），会阻塞后续全部。
   → 按「主链优先」排序：`stock_info_sync` → `stock_daily_incr` → 物化表 → 快照 → 体检 → 其余。
2. **补跑可见性**：把补偿清单写一条汇总记录，前端能直接看到「本次开机补了什么」。

### 4.2 补跑层 2 · 唤醒看门狗（覆盖「睡眠」）**最关键**

不依赖 APScheduler 的 misfire 处理，用**墙钟跳跃检测**判断「刚从挂起恢复」：

```
心跳每 2 分钟一次 → 记录 _last_tick
若 (now - _last_tick) > 300 秒 → 判定被冻结过 → 触发 sync_from_db() + catchup_missed()
```

判定对 APScheduler 内部实现不敏感，且幂等（`catchup_missed` 自带防重，执行走 running 保护）。

```python
class SchedulerManager:
    SLEEP_DETECT_SECONDS = 300        # 心跳 120s，超 300s 视为挂起恢复
    WATCHDOG_JOB_ID = "_watchdog"

    def start(self):
        ...
        self._last_tick = datetime.now(TZ)
        self._scheduler.add_job(
            self._watchdog_tick,
            CronTrigger.from_crontab("*/2 * * * *"),
            id=self.WATCHDOG_JOB_ID,
            coalesce=True, max_instances=1,
            misfire_grace_time=None,      # 看门狗自身永不丢弃
            replace_existing=True,
        )
        self.sync_from_db()
        ...

    def _watchdog_tick(self):
        now = datetime.now(TZ)
        gap = (now - self._last_tick).total_seconds()
        self._last_tick = now
        if gap <= self.SLEEP_DETECT_SECONDS:
            return
        logger.warning(f"⏰ 检测到系统挂起 {gap / 3600:.1f} 小时，触发唤醒补偿")
        try:
            self.sync_from_db()
            self.catchup_missed()
        except Exception:
            logger.exception("唤醒补偿异常")
```

#### ⚠️ 陷阱：看门狗会自杀（必须先修）

`sync_from_db()` 末尾会删除所有不在 `task_config` 中的 job（`scheduler.py:254-256`）：

```python
for job_id in [j.id for j in self._scheduler.get_jobs()]:
    if job_id not in want:
        self._scheduler.remove_job(job_id)     # ← _watchdog 会被误删
```

而 `sync_from_db()` 正是唤醒补偿的第一步 → **看门狗第一次工作就会把自己删掉**。必须加白名单：

```python
if job_id not in want and not job_id.startswith("_"):
    self._scheduler.remove_job(job_id)
```

### 4.3 补跑层 3 · 链式触发（解决竞态，同时缩短数据就绪时间）

在 `SchedulerManager` 维护一张依赖表，任务成功后自动提交下游：

```python
CHAIN_NEXT = {
    "stock_daily_incr":   ["market_style_sync"],
    "market_style_sync":  ["market_current_sync"],
    "market_current_sync": ["data_quality_check"],
}
```

- 执行完 `_execute(name)` 且状态为 success → 查询 `CHAIN_NEXT[name]` → 提交下游；
- 下游自身带护栏（`PREV_RATIO=0.9` / `_safe_max_date`），数据不充分时会拒绝，不会写残数据；
- 固定时刻（§3.3 兜底列）保留：若链式已跑成功则跳过，未成功则兜底再试一次。

**收益**：数据就绪时间从「固定时刻」变成「日线完成 + 数分钟」，通常能提前 30~60 分钟；
且彻底消除「物化表跑在日线前面」的空转（见 §3.3 实证）。

### 4.4 补跑层 4 · 新闻回看补采（唯一真正丢数据的通道）

`news_fetch` 当前每次只翻最新 150 条（`max_pages=3 × page_size=50`），无时间回看。

改造思路：以 `news` 表的 `MAX(published_at)` 为水位线，动态决定翻页深度：

```
读 watermark = MAX(published_at)
若 now - watermark <= 2h   → 按现有 3 页（正常增量）
若 now - watermark >  2h   → 逐页翻取，直到返回的最新条目时间 <= watermark，或达上限（如 20 页）
```

东财接口走 `sortEnd` 游标翻页，具备可行性；日产量 240~655 条 → 20 页（1000 条）足以覆盖 1~2 天缺口。

### 4.5 参数调整

| 参数 | 现值 | 建议 | 理由 |
|---|---|---|---|
| `misfire_grace_time` | `3600` | `21600`（6 h） | 让「晚间没开机、次日开机」的班次仍能被 APScheduler 补一次；不设 `None`（避免唤醒瞬间并发风暴） |
| `CATCHUP_MIN_INTERVAL` | `2 h` | 保持 | `news_fetch` 等高频任务不参与补偿，避免补跑风暴 |
| 补偿串行顺序 | 无排序 | 主链优先 | 见 §4.1 |

- **不上云**：数据可回补性已证明本地作息不丢核心数据；上云引入 akshare 数据中心 IP 可达性这个未验证风险（v1 文档 §5.3）；

- **不动电源设置**：你的作息是「主动开关机」，不是「挂机待眠」，RTC 定时唤醒（v1 的 L1 方案 B）在本场景**非必需**，跳过可少一个故障点。

### 8.4 为什么先做「新闻回看补采」而它原本排在第三期

§2.1 的可回补性矩阵决定了它的性质与其余措施不同：cron 收窗与链式触发解决的是**调度时机**，
而新闻是**唯一一个离线即永久丢失**的通道（日线可补 500 天、指数回看 7 天、物化表可全史重算）。
改动仅约 15 行却直接挽回真实数据损失，故从第三期提到与第一期同时落地。
