# 数据还原总方案

> 本文回答一个问题：**一台新机器 / 原机损毁后，怎么把 `adata` 库恢复到"和现在一样"？**
>
> 配套文档：
> - `scripts/data-bootstrap.md` —— 逐表补数**操作手册**（怎么点、怎么触发）
> - `scripts/git-only-restore.md` —— **只有 git 仓库、没有备份文件**时的兜底重建路径（含逐条命令）
> - `backend/scripts/backup_assets.py` —— 冷备**工具**（导出 / 校验 / 还原）
>
> 版本：2026-10-17（基于当天的实测调研，非文档推演）
> 口径声明：本文所有行数均为 `SELECT COUNT(*)` 实测值，**不用** `information_schema.table_rows`（估算列在本库偏差约 63 万行）。

## 0. 结论先行

| # | 结论 |
|---|---|
| 1 | 全库 59 张表按「可再生性」分 **5 类**，其中**只有 1 类必须靠备份文件**，其余 4 类都能用脚本重建 |

## 1. 调研结论：为什么"网上拉过的"也会拉不到

### 1.1 判据只有一条：接口让不让你指定时间点

这是 2026-10-17 三组实测得出的唯一可靠判据：

| 接口 | 有无时间参数 | 实测结果 | 判定 |
|---|---|---|---|
| `ak.stock_zh_a_daily(symbol, start_date, end_date)` | ✅ 区间 | 传 `19910401~19910430` → 返回 17 行，`open=49.00` 与本地首条**完全一致** | **可任意回溯** |
| `ak.stock_individual_fund_flow(stock, market)` | ❌ 无 | URL 参数 `lmt=0`（名义不限）→ **实际只返 120 条**（2026-04-20~10-16）；`lmt=500/1000/3000` → **全部 `curl_exit=56`**（服务端主动断连） | **窗口外永久丢失** |
| `ak.stock_report_fund_hold(symbol, date)` | ✅ 报告期 | 传 `2015-12-31` → 返回 **2781 行** | **可回溯，但见 1.2** |
| `ak.stock_board_concept_index_ths(symbol, start_date, end_date)` | ✅ 区间 | 传 `20180420~20180510` → **逐字段匹配**本地表（见 1.3） | **可完整重建** |

**推论**：判断一个源能不能重建历史，不要问"这个数据网上有没有"，要问"**它让不让我指定时间点**"。

### 1.2 第二层：能查到 ≠ 能拿回原版

`stock_hold_by_fund` 的 `2024-06-30` 实测对比：

| 项 | 本地表（当年存的） | 接口现在返回 |
|---|---|---|
| 行数 | 5,066 | **5,077** |
| 300750 持有基金家数 | 2,348 | **2,386** |
| 300750 持股总数 | 612,245,334 | **614,279,876** |

同一个历史时点，**少 11 行、数值全变** —— 基金季报会补充和更正。

**这意味着**：即使接口支持回溯，"数据内容"能重建，"**那一版**"不能。做数据留证时这是两回事。

### 1.3 第三层：接口比本地还全（意外收获）

拉概念行情 2018 年数据时发现：

- 本地 `ths_concept_market` 中「智能电网」最早只到 **2018-04-26**
- 接口能给到 **2018-04-02**（早 24 天）
- 且 04-26 当天 `open/high/low/volume` **逐字段完全一致**（close 仅 0.001 舍入差）

所以本地这份数据**开头本身就缺**。重建不只是"补回后来的"，而是**能比原来更全**。

## 2. 全库五分类

### L1 · 采集器可全量重建（有写入方 + 接口带时间参数）

**47 张表属于此类**（`table_meta.writers` 非空）。典型：

| 类别 | 代表表 | 重建方式 |
|---|---|---|
| 行情 | `stock_market_daily`（1858 万行） | `daily_backfill source=all_stocks`（2026-10 新增全史自举） |
| 参考类 | 交易日历 / 股票名册 / 指数成分 / 债券 / 基金 / 期货 / 申万行业 | 各自 `*_sync` 任务全量跑 |
| 宏观 | 货币流动性 10 张表 | `*_sync` 任务（官方直连 + DBnomics + BIS） |
| 概念 | `ths_concept_market` | **需补采集器**，见 L3-3 |

**判据**：`writers` 非空 且 该任务 `enabled=1` 且 接口接受时间参数。

### L2 · 只有滚动窗口 → **必须靠备份**

| 表 | 行数 | 现状 | 为什么补不回 |
|---|---|---|---|
| `stock_capital_flow` | **748,019** | 2023-08-14 ~ 2025-09-19，任务 `enabled=0` | 东财 `fflow` 接口**服务端硬限 120 条**，且拒绝 `lmt>120` 的请求 |

**这是全库唯一"确认无免费解"的缺口。**

### L3 · 有数据源但缺采集器 → 补采集器，或降级备份

| # | 表 / 范围 | 规模 | 数据源状态 | 建议 |
|---|---|---|---|---|
| L3-1 | `stock_market_daily_ex` | **16,891,313 行** | ✅ 实测「就是标准不复权日K」：2024-06-28 单日 5,330 只中 **5,096 只 close 与主表完全一致、0 处差异**；新浪接口支持任意区间 | 优先**补采集器**（`daily` 已能拉，换个落表即可）；成本高，可先靠备份 |
| L3-2 | `stock_hold_by_fund` | 113,147 行（38 个报告期） | ✅ 实测 `stock_report_fund_hold(date)` 可逐期拉（2015-12-31 已验证） | 优先**补采集器** `fund_hold_sync`；注意数值会被上游修正 |
| L3-3 | `ths_concept_market` | 580,681 行（2018-04-12 ~ 现在，2,066 个交易日） | ✅ 实测同源接口 `stock_board_concept_index_ths` 可任意区间、数值吻合 | 🟢 **无需改造**：采集器本就是水位线续跑（停跑后能自动补齐），且接口支持回溯到 2018-04-02（比本地还早 24 天） |

## 3. 人工资产方案：能不能用数据库脚本恢复？

### 3.1 先说结论

**能，但要说清"重算"和"重放"的区别**：

- **重算**（脚本里有规则，跑一遍得出同样结果）→ 只有 `stock_code_mapping` 的 235 条「简称归一」行，采集器一跑就自动生成
- **重放**（脚本里内嵌了当时的清单，跑一遍把清单灌回去）→ 其余全部

对你的设想来说，这个区别很关键：**`is_gxlstock` 的 722 只，脚本没法"重算出同样的判断"，只能"把这份名单写进脚本再灌回去"**。而一旦这么写，这份名单就成了代码的一部分 —— 可 review、可 diff、可版本化，比二进制 dump 好得多。

### 3.2 实测：人工资产到底有多大

| 资产 | 条数 | JSON 序列化体积 |
|---|---|---|
| 722 只高股息代码 | 722 | **7,220 B** |
| 7 条特殊 mapping（含 evidence 原文） | 7 | 920 B |
| 15 行 UI 偏好 | 15 | 1,510 B |
| **合计** | — | **9,650 B ≈ 9.4 KB** |

对比：`core` 冷备包 545.6 MB。**人工资产只占它的 0.0017%。**

### 3.3 建议形态：`seed_manual_assets.py`

与项目现有模式一致（`seed_table_meta.py` / `seed_dq_rules.py` 都是"常量写进代码 → seed 进库"）：

```
backend/scripts/seed_manual_assets.py
  ├─ GXL_STOCK_CODES   = ["000001", "000019", ...]        # 722 个代码
  ├─ MAPPING_OVERRIDES = [("430090","920090",...,"简称变更…"), ...]  # 7 条
  └─ DEFAULT_PREFS     = [("local","table_sort","stock_info",{...}), ...]
```

三个子命令，与 `backup_assets.py` 对齐：

| 子命令 | 作用 | 用法 |
|---|---|---|
| `export` | 从当前库**提取**这三份清单，生成/更新上面的常量文件 | 备份时跑一次 |
| `apply` | 把常量**灌回**空库（幂等 UPSERT） | 还原时跑 |
| `verify` | 比对库内现状与常量差异 | 定期巡检 |

**优点**：
1. 体积从 545 MB 降到 KB 级，能直接进 git
2. 有 diff —— 下次多标了 3 只高股息，提交里一眼看见
3. 不依赖 MySQL 版本、不依赖 `LOAD DATA` 权限
4. 空库还原时**零人工干预**

### 3.4 ⚠️ 一个必须由你拍板的风险：仓库是 **public**

`HongtaiChen/InfoData` 的 `visibility = public`。而这 9.4 KB 里有：

| 内容 | 公开的影响 |
|---|---|
| 722 只高股息股票名单 | 是你的**研究结论**，公开等于送人；但对安全性无害 |
| `user_prefs` 15 行 | 个人使用偏好，无害但不必要 |
| mapping evidence | 北交所代码迁移记录，完全无害 |

三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 新建 **private** 仓库 `InfoData-assets` 放这个脚本 + core 包索引 | 多一个仓库要维护 |
| B | 只把"无害"部分（mapping evidence）进 public，高股息名单走本地加密 | 还原时要多一步解密 |
| C | 全部进 public，认了 | 研究成果公开 |

## 4. 一键还原编排：`restore_all.py` 的阶段设计

你的想法"一整套完整的拉取脚本，耗时久点没关系"是对的，但要**可断点续跑**——否则跑到 12 小时断了要从头再来。

### 4.1 设计原则

| 原则 | 理由 |
|---|---|
| **每阶段一个独立可重入单元** | 中断后从 Stage N 续跑，不重头 |
| **每阶段自带判据** | 跑完自己验（行数 / 抽样 / DQ），不靠人肉看日志 |
| **依赖显式排序** | 名册 → 行情 → 参考类 → 轮转类，前者是后者的候选池 |
| **幂等** | 重复跑不产生重复行（靠 `uk_*` 唯一索引 + `INSERT ... ON DUPLICATE KEY`） |

### 4.2 Stage 明细

| Stage | 内容 | 命令（现有资产） | 实测/推算耗时 | 判据 |
|---|---|---|---|---|
| **S0** | 建表 + 配置 | `schema.sql` + 6 个 `seed_*.py` | **约 1 分钟**（实测 56 表零错误、49 任务、209 规则） | `information_schema` 表数 = 56 |
| **S1** | 基础名册 | `stock_info_sync` / `trade_calendar` / `concept_sync` | 数分钟 | `stock_info` ≥ 5,900 行 |
| **S2** | 日线全史 | `daily_backfill source=all_stocks` | 需自行拼批次（`max_codes` 即批大小），**参考：日线增量单次实测 1,673s** | `stock_market_daily` ≥ 1,800 万行 |
| **S3** | 参考类 | 各 `*_sync` 全量触发 | 数小时（宏观/债券/基金/指数/期货） | 逐表行数 ≥ 阈值 |
| **S4** | 概念行情全史 | `concept_market_sync`（需先改造） | 399 概念 × ~2,060 日 ≈ **82 万请求**；实测 13 req/s → **单线程 17h / 4 线程 ~4h** | 逐概念无缺口 |
| **S5** | 轮转类 | `financial_abstract_sync` / `stock_shares_sync` | 实测 1,968s/轮（800 只/轮，需 8 轮）；1,000 只/轮需 6 轮 → **跨 6~8 天** | 覆盖率 100% |
| **S6** | 人工资产 | `seed_manual_assets.py apply` | **< 1 秒** | 722 / 7 / 15 三项计数 |
| **S7** | 校验 | `backup_assets.py verify` + `dq` 全跑 | 数分钟 | 行数 + 抽样 + DQ 全绿 |

### 4.3 断点续跑的实现

每个 Stage 完成后写一行到 `restore_progress` 表（或 JSON 文件）：

```
{ "stage": "S3", "status": "done", "finished_at": "...", "detail": {...} }
```

重跑时跳过 `status=done` 的阶段。**注意**：这是"进度文件"，按项目既往踩坑经验，**进度标记不可信** —— 判据仍要以数据侧为准（`SUM(条件)` 分组统计），不能只看进度文件。

## 5. 耗时总账

### 5.1 三条路径对比

| 路径 | 耗时 | 保真度 | 适用 |
|---|---|---|---|
| **A · 整库迁移**（`migrate-machine.bat`） | **0.5~1 小时**（dump 5.3GB → gz 1.1GB，导入 10~30 分钟） | **100%**（含资金流、含所有人工标记） | 原机还在 ✅ |
| **B · 冷备 + 脚本补洞**（**推荐**） | **1~2 小时**（core 包 9 分钟导出 + 导入；small 包秒级） | core 覆盖的表 100%；L1 类按需补 | 原机没了，但有备份 |
| **C · 从零全量重建** | **20~30 小时机器时间 + 跨 6~8 天** | 约 99%（缺资金流中间段 + 老三板） | 什么都没了，且能接受长跑 |

### 5.2 路径 C 的耗时拆解

| 项 | 耗时 | 依据 |
|---|---|---|
| S0~S1 建表 + 名册 | < 10 分钟 | 实测 |
| S2 日线全史（1,858 万行） | 4~8 小时 | 日线增量单次 1,673s × 批次 |
| S3 参考类 | 3~5 小时 | 各 sync 实测均值 |
| S4 概念行情 | 4 小时（4 线程） | 82 万请求 @ 13 req/s |
| S5 轮转类 | **跨 6~8 个自然日** | 财务摘要 1,968s/轮 × 8 轮 |
| 合计 | **约 1 天机器时间 + 一周等待** | — |

**所以结论是**：能拿备份就拿备份。从零重建不是"慢一点"，是**慢 30 倍且永远缺一块**。
